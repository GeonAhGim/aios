## Triage of the highest-signal survivors

Full top-30-per-domain lists are in `mutation-report.json`. This is not an
exhaustive line-by-line triage of all 230 survivors — it calls out the patterns
with enough evidence to act on now, and defers the rest to whoever picks up the
DEEPEN follow-ups below (worker JSON task files were not created directly per
CLAUDE.md §4 — a backend/QA worker should open these from this list).

### 결함 후보 (defect candidates)

1. **Value-object immutability untested across the ledger domain.** `core/ReplaceTrueWithFalse`
   survives on `@dataclass(frozen=True, slots=True)` in `balance_rules.py:63`
   (`Balance`), and the same `frozen=True` pattern in `chart_of_accounts.py`,
   `correction.py`, `hash_chain.py`, `payout_schedule.py` (all `definition_name=None`,
   i.e. class-body decorator args, not inside a function). No test in
   `tests/foundation/unit/ledger/` attempts to mutate one of these value objects
   and asserts `FrozenInstanceError`. Money/ledger value objects (I-01/I-02
   territory per `docs/design/INVARIANTS.md`) silently becoming mutable would not
   be caught today. **Recommend a DEEPEN task**: add one immutability assertion
   test per frozen dataclass in the ledger domain.

2. **Zero-boundary guard on `held` is untested at the boundary.** `balance_rules.py:92`
   survives `core/ReplaceComparisonOperator_Lt_LtE` — `new_held < 0` could become
   `new_held <= 0` (rejecting an exact-zero `held`, which should be legal) without
   any test failing. Same pattern at `hold_state.py:69` and `payout_schedule.py:77`
   (`_is_in_period`, period-boundary inclusive/exclusive). These are exactly the
   off-by-one boundary bugs mutation testing exists to catch. **Recommend a DEEPEN
   task**: add exact-zero / exact-boundary test cases for each.

3. **`algo_slicer.py::plan_slices` deterministic arithmetic is under-asserted.**
   The densest single cluster (oms domain) is `plan_slices` — but most of it
   (`size_jitter_multiplier`, `time_jitter_sec`, the jittered `quantity` before the
   final `min(quantity, remaining)` clamp) is *intentionally* randomized
   (`rng.uniform`), so surviving a `NumberReplacer`/`ReplaceBinaryOperator_Mul_Div`
   there is expected — the test suite correctly avoids asserting exact jittered
   magnitudes (and the one invariant that matters, `is_last` remainder absorption,
   already has a dedicated gate-red-repro test — no survivor was produced on that
   line, confirming the guard works). The deterministic setup lines, however
   (`base_interval_sec = total_span_sec / req.slice_count`, `base_qty =
   req.total_quantity / req.slice_count`, the `participation_cap` capping),
   surviving is a real gap: nothing asserts their exact computed value.
   **Recommend a DEEPEN task**: assert `base_interval_sec`/`base_qty`/
   `participation_cap` precisely for a fixed (non-jittered or jitter=0) request.

### 추가 확인 필요 (needs a closer look, not dismissed as harmless)

4. **`src/core/risk/engine.py` `_bridge_legacy_inputs`/`_to_legacy_result`/
   `_reason_for`** account for roughly a third of the risk domain's survivors
   (`engine.py:74-117`). The names suggest a legacy compatibility shim rather than
   the primary decision path (see also the separate `legacy_bridge.py` in the same
   package) — risk is safety-critical (R axis, D3 floor per ADR-2026-09-09-C), so
   this should not be waved off as harmless without checking whether
   `_bridge_legacy_inputs`/`_to_legacy_result` are still on a live call path or
   fully superseded by `legacy_bridge.py`. If live, treat as defect candidates
   with the same priority as items 1-3; if dead code, that is itself worth a
   cleanup task. Deferred here because answering it requires call-graph tracing
   beyond this run's scope.

No survivor in this run's top-30 lists was confirmed harmless (e.g. logging-only
branches, truly dead code) — the ledger/risk/oms domains are money- and
execution-adjacent enough that "survived" defaulted to "needs a look" rather than
being waved through.
