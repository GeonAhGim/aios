## 3. 겹겹 방어 구조 (제안)

1. **내부 보안(코어)**: 인증·MFA·권한·테넌트 격리·주문 한도·킬스위치·감사 로그. 외부 의존 없이 단독으로 안전해야 한다.
2. **외부 보안 플러그인**: 코어 위에 얹는 추가 층(침입 탐지, 이상 접근 차단 등). 규칙: (a) **관찰·경고·거부 신호만** 보낼 수 있고 주문을 직접 내거나 바꾸지 못한다, (b) 최종 판정은 AIOS 코어, (c) 플러그인이 죽거나 오작동해도 코어는 기존 보호를 유지한다(fail-closed 쪽으로만 영향), (d) 플러그인 자체가 공격면이므로 최소 권한·서명·심사·폐기 절차를 둔다.
3. **외부 검증**: 제3자 모의해킹과 보안 감사. 회차와 시점은 §6.

## 6. 모의해킹 (사용자 결정 2026-11-19로 갱신)

사용자가 **별도 팀을 직접 구성**해 모의해킹을 한다. 본격 점검은 **패키징 전**에 한다. 지금은 CTO(자체 상시 점검)가 어느 정도 하고 있다는 전제다.

| 회차 | 담당 | 시점 | 범위 |
|---|---|---|---|
| 0 | CTO·SecEngine(자체) | 지금부터 상시 | 인증·API·주문 경로·테넌트 격리·비밀값. 쉬운 결함 소진, 회귀 테스트 축적 |
| 1 | 사용자 팀 | **패키징 전**(본격) | 외부 노출 웹·API 전체, 인증·권한·세션, 테넌트 격리, 주문·키 보관 경로, 인프라 |
| 2 | 사용자 팀(또는 외부) | LIVE 개시 전 재점검 | 1회차 지적 수정 확인 + 거래소 키·청산·플러그인 경계 [CTO 제안, 미확정] |

CTO가 사용자 팀에 준비해 주는 것(제안): 점검 대상 목록과 구조 설명, 테스트 환경(체험 스택 `docs/uat/UAT_GUIDE.md`, PAPER 전용), 지금까지의 레드팀 장부·감사 결과, 발견 사항을 `docs/RED_TEAM_FINDINGS.md`에 올리는 양식. 실계정·실자금은 점검 대상에서 제외한다.
수정 확인은 지적마다 회귀 테스트를 만들어 재시험한다.
