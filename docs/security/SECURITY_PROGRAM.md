## 3. 겹겹 방어 구조 (제안)

1. **내부 보안(코어)**: 인증·MFA·권한·테넌트 격리·주문 한도·킬스위치·감사 로그. 외부 의존 없이 단독으로 안전해야 한다.
2. **외부 보안 플러그인**: 코어 위에 얹는 추가 층(침입 탐지, 이상 접근 차단 등). 규칙: (a) **관찰·경고·거부 신호만** 보낼 수 있고 주문을 직접 내거나 바꾸지 못한다, (b) 최종 판정은 AIOS 코어, (c) 플러그인이 죽거나 오작동해도 코어는 기존 보호를 유지한다(fail-closed 쪽으로만 영향), (d) 플러그인 자체가 공격면이므로 최소 권한·서명·심사·폐기 절차를 둔다.
3. **외부 검증**: 제3자 모의해킹과 보안 감사. 회차와 시점은 §6.

## 6. 모의해킹 권고 (CTO, 제안)

원칙: 비싼 외부 점검 전에 **자체 상시 레드팀(SecEngine)으로 쉬운 결함을 먼저 소진**한다. 외부 점검이 이미 아는 결함에 돈을 쓰지 않게 한다.

| 회차 | 시점 | 범위 | 목적 |
|---|---|---|---|
| 0 | 지금부터 상시(자체) | 인증·API·주문 경로·테넌트 격리·비밀값 | 쉬운 결함 소진, 회귀 테스트 축적 |
| 1 | 웹 베타(PAPER 실사용) 개시 직전 | 외부에 노출되는 웹·API 전체, 인증·권한·세션, 테넌트 격리. 실주문 없음 | 외부 노출 첫 검증, 재작업 비용이 낮은 시점 |
| 2 | LIVE(실거래) 개시 전 | 1회차 범위 + 거래소 키 보관, 주문·청산 경로, 인프라, 플러그인 경계 | 실자금 전 최종 관문. 통과가 LIVE 전환 조건 |

- 예산: 규모·범위에 따라 편차가 커서 **2~3개 전문 업체 견적**을 받아 정한다. 대략 회차당 수천만 원 단위일 것으로 보지만 **검증하지 않은 추정**이다. 1회차는 범위를 좁히고 2회차를 넉넉히 잡는다.
- 지적 사항은 심각도별 수정 기한을 정하고, 수정 후 재시험(재검증)까지 계약에 포함한다.
- 외부 점검 결과는 `docs/security/`에 기록하고 레드팀 장부(`docs/RED_TEAM_FINDINGS.md`)에 항목으로 올린다.
