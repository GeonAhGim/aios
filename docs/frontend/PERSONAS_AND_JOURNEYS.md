# 페르소나와 여정 — 프런트엔드는 무조건 사용자 기준 (v0.1)

> 지시(사용자, 2026-11-19): 프런트엔드는 **무조건 사용자 기준**이다. 전략 생산자·구독자·전략 판매자·자산운용사·증권사·기관, 그리고 운영자·마스터(사용자 본인),
> 추후 스트리밍·제휴 증권사·방송사, 그리고 **보안·DevEngine**을 외부 플러그인으로 붙일 경우의 여정까지 필요하다(사용자 2026-11-19: 보안·DevEngine 추가).
> 결정 기록: ADR-2026-11-18-B 원칙 6(아래 §8). 표기: **[확인]** 코드·문서로 확인, **[제안]** 이 문서의 설계, **[미확인]** 아직 모름.

## 1. 지금의 기준선 (확인한 사실)

- `docs/specs/UX_JOURNEYS.md` §0의 페르소나는 **"개인 시스템 트레이더/리서처 1명"**이고, "팀/고객 개념(GIPS, 멀티 계정)은 MVP-2(U-11) 이후 범위"다. [확인]
- 화면 라우트 디렉터리(`routes/`)에는 이미 여러 주체의 흔적이 있다: `admin`, `approvals`, `compliance`, `disputes`, `marketplace`, `follow`, `signals`, `wallet`, `reports`, `mandates`, `ai`, `research`. [확인]
- 백엔드: 소속 역할 `OWNER / ADMIN / MEMBER / AUDITOR / SERVICE`(`src/foundation/trust/domain/models.py`), 법인·펀드·포트폴리오·하위계정 계층(`src/foundation/entities`),
  `marketplace`, `follow`, `mandates`, `ems`, `compliance`, `reporting`, `tax_report`, `risk_coach`, `ai`, `research_data` 모듈. [확인]
- 플러그인(외부 제공자) 개념: 코드에서 찾지 못했다(`plugin` 검색 0건). **신규 설계 영역**이다. 거래소 어댑터(`src/exchanges`)가 가장 가까운 선례다. [확인]
- 화면은 **한 사람이 모든 것을 하는 개인 도구** 구조다. 역할별 메뉴·맥락 전환(어떤 펀드/고객/조직으로 일하는가)·역할별 온보딩은 [미확인(없을 가능성이 큼)].

## 3. 여정 지도 [제안]

기존 J1~J6(+UX 문서의 J7~J9 후보)은 **P1 중심**이다. 페르소나가 늘면 여정을 "누가"가 아니라 **"무엇을"** 단위로 재편하고, 페르소나는 그 위에 접근 범위와 기본 화면을 얹는다.

| 여정 묶음 | 주 페르소나 | 상태 |
|---|---|---|
| 시작·온보딩(J1) | P1, 이후 모든 페르소나가 **자기 버전**을 가진다(예: 운용사는 고객·펀드 설정이 온보딩) | P1만 있음 |
| 발견·검증(J2), 모의 주문(J3), 감시·복구(J4), 리서치(J5), 설정·승인·감사(J6) | P1(+P2) | 있음/MVP-2 |
| **전략 제작·검증·공개**(J10) | P2 | 신규 |
| **마켓 상장·판매·정산·분쟁**(J11) | P3 | 신규 |
| **발견·구독·따라하기·해지**(J12) | P4 | 신규 |
| **다중 고객·펀드 운용, 고객 보고**(J13) | P5 | 신규 |
| **파트너 연동·고객 온보딩·라우팅**(J14) | P6 | 신규 |
| **거버넌스·승인·감사·규제 보고**(J15) | P7, P11 | 부분(J6) |
| **운영 콘솔: 검증·분쟁·안전·정합성**(J16) | P8 | 부분(`admin/*`) |
| **마스터 콘솔: 정책·수수료·파트너·킬스위치**(J17) | P9 | 신규 |
| **플러그인 등록·권한·수익 공유·심사**(J18) | P10, P9 | 신규 |

번호는 임시다(기존 J1~J9와 충돌 없이 이어 붙임). 각 여정은 `SCREEN_SPEC_TEMPLATE.md` 형식으로 화면 명세를 가진다.

## 4. 역할·권한·맥락 모델 [제안]

여러 주체를 한 앱에서 다루려면 다음이 구조여야 한다(FE-2 횡단 규칙 + FE-9 작업 공간과 맞물린다).

1. **누구로 일하는가(주체) + 무엇을 위해 일하는가(범위)**: 사용자는 여러 조직·펀드·고객·포트폴리오에 속할 수 있다. 상단 **맥락 전환기**(조직 -> 펀드/고객 -> 포트폴리오)가 FE-9의 *account scope*를 결정한다.
2. **역할별 기본 작업 공간**: 로그인 후 역할·맥락에 맞는 시작 작업 공간(P1=개인 트레이딩 보드, P5=고객 보드, P8=운영 대기열, P9=마스터 콘솔)을 연다. 메뉴는 역할이 볼 수 없는 화면을 **숨기지 않고 이유와 함께 비활성** 표시할지, 숨길지를 화면 명세에서 정한다.
3. **권한 표시 규칙**: 권한 없음(403)은 "당신의 역할로는 불가 + 누구에게 요청"을 보여 준다(ERRORS 규칙). 승인 체인(2인 승인 등)은 상태가 보여야 한다.
4. **역할 겸임**: 한 사용자가 생산자·판매자·구독자를 겸하면 같은 계정 안에서 작업 공간만 바꾼다(재로그인 없이).
5. **감사 가능성**: 역할 전환·대리 행동(운영자가 고객을 대신하는 행동)은 화면에 표시되고 기록된다.
6. 현재 백엔드 역할은 5종(OWNER/ADMIN/MEMBER/AUDITOR/SERVICE)이라 위 페르소나와 1:1이 아니다. 페르소나->역할->권한 매핑표는 [미확인] — Phase 0 조사 항목.

## 5. 외부 플러그인 모델 [제안, 개념 수준]

스트리밍·방송사·제휴 증권사·데이터 제공자가 AIOS 위에 붙는 방식. **구현이 아니라 계약을 먼저** 정의한다.

| 확장점 | 설명 | 선례/연결 |
|---|---|---|
| 데이터·스트림 공급자 | 시세·뉴스·방송 영상/오디오 메타·신호를 피드로 제공 | 시장 데이터 도메인·`signals` 소스 |
| 브로커/시장 어댑터 | 새 증권사·거래소 연동 | `src/exchanges` 어댑터, `ExchangeAdapter` 포트 [확인] |
| 패널(위젯) 플러그인 | FE-9 작업 공간에 끼워 넣는 외부 패널(예: 방송 영상 패널, 제휴 리서치 패널) | FE-9 패널 모델 |
| 이벤트·웹훅 | 외부가 AIOS 이벤트를 구독/발행 | `event_bus` [확인: 내부용] |
| 보안 플러그인 | 사용자 정의 2026-11-19: **해킹을 막기 위한 보안 시스템**을 붙인다. 구체 기능(침입 탐지·계정 탈취 방어·이상 접근 차단 등)은 [미확인] | 인증·MFA(`auth`)·감사·킬스위치 [확인: 내부 구현] |
| DevEngine 플러그인 | 사용자 정의 2026-11-19: DevEngine은 **유지보수자**(AIOS를 고치고 유지하는 쪽)와 연결된다(설명이 "유지보수자나"에서 끊겨 나머지는 [미확인]) | DevEngine/AIOS 관계(메모리 `devengine_aios_project`) |

보안·DevEngine 플러그인은 앞의 4종과 성격이 다르다. 보안은 주문·인증 경로의 **관찰·경고·거부권**을 원할 수 있고, DevEngine은 코드·배포 권한을 다루는 **개발자 쪽 연결**일 수 있다. 그래서 아래 제약 (3)을 "플러그인은 주문을 직접 내거나 바꿀 수 없다, 보안 플러그인은 거부 신호(veto)만 보낼 수 있고 최종 판정은 AIOS가 한다"로 구체화하고, DevEngine 플러그인은 실주문·실자금 경로와 격리된 권한 등급으로 둔다(둘 다 [제안]).

공통 제약(제안): (1) 권한 범위(scope)를 설치 시 사용자·조직이 승인, (2) 샌드박스(패널은 격리된 프레임, 데이터는 계약된 API로만), (3) **금전·주문 경로에는 플러그인이 직접 접근 금지**(주문은 항상 AIOS 위임·확인 경로), (4) 심사·서명·폐기 절차(마스터/운영자 콘솔), (5) 수익 공유·정산 기록, (6) 플러그인 장애가 코어를 막지 않는 격리.
**[미확인]**: 서버 측 플러그인 등록·격리 구조, 법적 계약 형태. 이 모델은 MVP-3 이후이므로 Phase 0에서는 확장점 이름과 불변 규칙(3번)만 확정한다.

## 6. 프런트가 달라지는 점

- **정보 구조**: 메뉴가 기능 나열(현재 약 50개)에서 **역할 + 맥락 + 작업 공간** 중심으로 바뀐다(FE-9). 개인 모드는 그대로 단순하게 유지한다.
- **명세 단위**: 화면 명세(`SCREEN_SPEC_TEMPLATE.md` §1)에 **페르소나 열**을 필수화한다(누가 쓰는 화면인가, 다른 역할이 보면 무엇이 달라지는가).
- **테스트**: 실스택 e2e를 페르소나별 시나리오로 만든다(역할 계정 시드가 필요 — `seed_demo`를 역할 시드로 확장).
- **국제화·규제**: 기관·운용사·증권사는 지역별 규제(고객 분류, 보고 형식)가 다르다. FE-4와 연결한다.

## 7. 단계 [제안]

| 단계 | 페르소나 | 산출 |
|---|---|---|
| MVP-1 종결(현재) | P1 (+P8 기본) | 변경 없음. 이 문서는 설계 기준만 제공 |
| Phase 0 (종결 전, 문서) | 전체 | 페르소나->역할->권한 매핑 조사, 화면 명세에 페르소나 열, J10~J18 개요(1페이지씩) |
| Phase 1 (MVP-2 UI) | P2, P3, P4, P9, P11 | 생산자·판매자·구독자 여정과 마스터 콘솔, 역할 전환기, 페르소나별 e2e |
| Phase 2~3 | P5, P6, P7, P10 | 운용사·증권사·기관 포털, 플러그인 계약과 샌드박스 |

## 8. ADR-2026-11-18-B 원칙 6 (추가)

> **6. 사용자 기준(Persona-first)**: 모든 화면과 흐름은 "누가, 무엇을 이루려고" 쓰는지로 정의한다. 기능 목록이나 내부 모듈 구조가 아니라 **페르소나와 그 여정**이 프런트의 단위다.
> 페르소나는 P1~P11(`PERSONAS_AND_JOURNEYS.md`)이고, 신규 화면·여정 명세는 주 페르소나를 반드시 명시한다.

## 9. 열린 질문

1. P2(생산자)와 P3(판매자)를 한 작업 공간으로 묶을까, 분리할까? (겸임이 많을 것으로 예상: 묶고 탭으로 구분하는 안을 권장)
