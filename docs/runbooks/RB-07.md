# RB-07: 인증 남용 (잠금 · rate limit 폭주)

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A6, §7.5.

## 트리거 알림

- `A6_AuthAbuseSurge`(warn) — `increase(aios_auth_lockout_count_total[10m]) > 10` 또는
  `increase(aios_auth_rate_limited_count_total{policy="auth_login"}[10m]) > 20`.

## 증상

짧은 시간에 다수의 계정이 잠기거나(`lockout.register_failed_attempt`가 임계
초과), 로그인 엔드포인트가 rate limit(정책 `auth_login`, 73 §8)에 반복적으로
걸리고 있다. 전형적으로 자격증명 스터핑(credential stuffing) 또는 브루트포스
공격의 신호다.

## 진단

1. 잠긴 계정 목록이 소수 IP/User-Agent에 집중되는지 확인(`ip_hash`, `ua_hash`
   — `auth_session`/rate limiter 로그).
2. 대상 계정이 무작위(랜덤 사용자명 시도)인지, 특정 계정에 집중(타겟 공격)
   인지 구분 — 후자는 계정 탈취 목적일 가능성이 더 높다.
3. 동일 IP에서 여러 계정을 순회하는 패턴이면 credential stuffing, 동일 계정에
   반복 시도면 단일 계정 브루트포스.
4. 성공한 로그인(`aios_auth_login_count_total{outcome="success"}`)이 공격
   구간과 겹치는지 — 겹치면 뚫린 계정이 있을 수 있음(최우선 확인 사항).

## 조치

- 공격 IP가 명확하면 rate limit 정책의 `key="ip"` 특성을 활용해 임시 차단
  목록에 추가(인프라 방화벽/WAF 레벨 차단 권장 — 애플리케이션 레벨 rate
  limit만으로는 볼륨 공격을 못 버틴다).
- 뚫린 계정이 확인되면 해당 사용자 세션 전체 `logout_all` + 강제 비밀번호
  재설정 안내.
- 공격이 아니라 정상 사용자의 실수(비밀번호 오기억 등)로 판정되면(예: 사내
  배포/설정 변경 직후 다수 사용자가 동시에 재인증 실패) 잠금 임계값 조정
  여부만 검토하고 별도 조치 없이 종료.

## 에스컬레이션

성공한 로그인이 공격 패턴과 겹치는 경우 즉시 보안 담당자에게 에스컬레이션
(계정 탈취 가능성 — 최우선 사고).

## 사후 조치

공격 패턴이 반복되면 CAPTCHA·IP 평판 기반 사전 차단 등 상위 방어 계층 도입을
검토한다. 잠금 임계값(73 §8)이 실제 공격 규모 대비 적절한지 재평가한다.
