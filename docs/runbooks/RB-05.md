# RB-05: 키 회전 절차

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A9, §9 PLT-34,
`scripts/rotate_credential_keys.py`.

## 트리거 알림

- `A9_AdapterFatalRatioHigh`(warn) — 거래소 어댑터 fatal 응답 비율 5분간 5% 초과.
  자격증명 복호 실패(오래된 kid 참조, 회전 중 불일치)가 원인 중 하나일 수 있어
  키 회전 절차와 함께 다룬다.

## 사전 조건

- `KeyRing.from_env("PAPER")`로 신규 kid(예: `v2`)가 이미 환경변수에 등록되어
  있어야 한다(`CREDENTIAL_ENCRYPTION_KEYS_PAPER="v1:hex64,v2:hex64"`).
- `CREDENTIAL_ENCRYPTION_ACTIVE_KID_PAPER`를 신규 kid로 바꾸는 **순서가 중요하다**:
  먼저 활성 kid를 신규 kid로 바꾸고 배포한 다음(신규 등록/재등록 자격증명부터
  새 kid로 암호화되기 시작), 회전 스크립트로 기존 행을 따라잡는다. 활성 kid를
  아직 바꾸지 않은 채로 회전만 먼저 돌리면 그사이 신규 등록되는 행이 계속
  구 kid로 쓰이므로 회전이 끝나지 않는다.
- `exchange_credentials`는 PLT-31 포맷(`aios1$<kid>$b64`)으로 레코드 본문을
  KeyRing 키로 직접 암호화한다 — PLT-32 봉투 암호화(DEK, `envelope.rewrap`)가
  적용되는 wrapped_dek 컬럼이 없으므로, 이 스크립트는 옛 kid로 복호 후 새
  kid로 재암호화한다(본문까지 다시 암호화됨, DEK만 재래핑하는 경량 경로가
  아니다). LIVE 스코프 행은 애초에 조회 대상이 아니다(PLT-33 §10-8).

## 절차

0. 모든 명령은 **저장소 루트에서 모듈 형태(`python -m scripts.rotate_credential_keys`)**로
   실행한다. `python scripts/rotate_credential_keys.py`처럼 파일 경로로 직접 실행하면
   sys.path에 `scripts/`만 실려 `ModuleNotFoundError: No module named 'src'`로 즉시
   실패한다(`scripts/export_openapi.py`와 동일 규칙). 배선은
   `tests/platform/integration/test_key_rotation_negative.py`가 subprocess로 증명한다.
1. 대상 행 수를 먼저 확인한다(§2.2 계약, 아무것도 쓰지 않는다):
   `python -m scripts.rotate_credential_keys --dry-run` — 또는 동일한 검증 쿼리
   `SELECT count(*) FROM exchange_credentials WHERE scope='PAPER' AND key_version <> '<신규 kid>'`.
2. `python -m scripts.rotate_credential_keys --batch-size 100` 실행 — 대상이
   없어질 때까지 배치 단위로 자동 반복한다. 처리 건수만 stdout에 출력되고
   평문 자격증명은 어디에도 로그되지 않는다. 한 번에 처리할 행 수를 제한하려면
   `--max-rows N`을 추가한다(운영 중 부하 조절, 단계적 롤아웃).
3. 각 행은 자체 트랜잭션 + `UPDATE ... WHERE id=$1 AND scope='PAPER' AND key_version=$2`
   조건부 갱신이므로, 스크립트가 배치 중 예외로 중단돼도 이미 성공한 행은
   그대로 남고 재실행 시 남은 행만 처리한다(멱등).
4. 완료 후 `aios_security_key_rotation_count_total{scope="PAPER",outcome="success"}`
   증가와 `audit_log`의 `security.key_rotated` 이벤트(행당 1건, `target_id`=
   `exchange_credentials.id`, `decision_data`에 `from_kid`/`to_kid`만 포함하고
   평문은 없음)가 기록됐는지 확인한다.
5. 검증 쿼리: 1번 쿼리를 다시 실행해 0이 나오는지 확인
   (`WHERE scope='PAPER' AND key_version <> '<신규 kid>'`가 0행).
6. 검증 통과 후 일정 기간(최소 1 회전 주기) 지나면 구 kid를
   `CREDENTIAL_ENCRYPTION_KEYS_PAPER` 목록에서 제거한다(그 전까지는 롤백
   대비 복호 폴백으로 남겨둔다).

## 롤백

새 kid로 전환 후 문제가 발견되면 **이전 kid를 그대로 유지**한다 — 회전된
행은 신규 kid로 재암호화됐으므로, 롤백은 "활성 kid를 구 kid로 되돌리는 것"이
아니라 신규 kid 키 자체를 `CREDENTIAL_ENCRYPTION_KEYS_PAPER`에서 제거하지
않고 유효하게 유지하는 것이다. 활성 kid 지정만 되돌리면 이후 신규 등록
행이 구 kid로 암호화되어 혼재 상태가 길어지므로 지양한다.

## 에스컬레이션

회전 스크립트가 배치 중 예외로 중단되면 재실행 전에 원인을 확인한다. 예외는
항상 `CredentialRotationError: id=<행 id> <stage> 실패(kid='<구 kid>', cause=<예외 타입명>)`
형태이고 stage는 `reencrypt`(복호/재암호화 — 구 kid가 환경변수에서 빠짐 등),
`update`(조건부 UPDATE DB 오류·락 경합), `audit`(감사 INSERT DB 오류) 중 하나다.
원인 예외는 **의도적으로 체인하지 않는다**(원인 예외의 traceback 프레임이 평문 인자를
붙들 수 있으므로) — 메시지·stderr에는 행 id·kid·스테이지·예외 타입명만 남고 평문은
어디에도 나오지 않는다. 어느 스테이지든 실패한 행은 트랜잭션이 롤백돼 구 kid 상태
그대로 남고 `aios_security_key_rotation_count_total{scope="PAPER",outcome="failure"}`
가 1 증가한다(UPDATE·감사 INSERT의 DB 오류도 포함; 스크립트는 첫 실패에서 즉시
멈추며 뒤 행은 건드리지 않는다).
원인 제거 후 재실행하면 이미 회전된 행은 건너뛰고(감사 이벤트도 행당 1건만)
남은 행부터 이어진다 — 스크립트 자체는 멱등하므로 재실행은 안전하다.

## 사후 조치

회전 완료 후 `aios_adapter_request_count_total{outcome="fatal"}` 비율이
정상으로 돌아왔는지 확인해 A9가 자격증명 원인이었는지 결론짓는다.
