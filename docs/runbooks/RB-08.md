# RB-08: 동시성 충돌 급증 (105 §1 재발 패턴 탐색)

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A1, §7.5, 105 §1/§2.

## 트리거 알림

- `A1_ConcurrencyConflictSpike`(warn, `source: logs`) — `<aggregate>_concurrency_conflict`
  로그 이벤트 비율이 1시간 이동평균 대비 3배 이상 급증(108 §5-1 공용 alert).

## 배경

105번 문서(동시성 규칙)는 모든 쓰기 경로가 조건부 UPDATE(`expected_revision`
등)를 쓰도록 요구한다. 실패한 조건부 갱신은 도메인 무관하게 항상
`<aggregate>_concurrency_conflict` 이벤트로 로깅된다(108 §4). 평상시에도
동시 요청이 겹치면 소량 발생하는 것이 정상이지만, 급증은 105 §1에 기록된
"재발 패턴"(같은 결함이 다른 곳에서도 발생 중)의 조기 신호다.

## 진단

1. 로그에서 `event=~".*_concurrency_conflict"`를 `aggregate`(또는 `component`)
   라벨로 그룹핑해 급증이 특정 애그리게잇(주문, membership, 세션 등)에
   집중되는지 전체적인지 확인.
2. 특정 애그리게잇에 집중: 해당 도메인의 최근 배포/변경 이력을 확인 —
   `expected_revision` 비교 로직이 최근에 바뀌었는지, 재시도 로직이 없어서
   정상적인 동시 요청도 전부 실패로 노출되는지 확인.
3. 전체적으로 분산: 인프라 레벨 문제(DB 커넥션 지연으로 read-then-write 간격이
   길어져 충돌 확률 자체가 상승) 가능성 — DB 응답 지연 지표를 함께 확인.
4. 충돌이 재시도 없이 사용자에게 그대로 에러로 노출되고 있는지(사용자 영향
   범위 판단) 확인 — 105 설계상 조건부 갱신 실패는 멱등하게 재시도 가능해야
   하므로, 재시도 로직 부재 자체가 별도 결함일 수 있다.

## 조치

- 특정 애그리게잇의 로직 결함이면: 조건부 갱신 비교 대상(revision/state)이
  잘못됐는지 코드 리뷰, 핫픽스.
- 인프라 지연이 원인이면: RB-01과 동일하게 DB 가용성 점검.
- 재시도 로직 부재가 확인되면: 즉시 코드 수정 대상은 아니더라도(별도 리프),
  현재 실패 중인 사용자 영향 범위를 파악해 안내.

## 에스컬레이션

여러 애그리게잇에서 동시다발적으로 급증하면 105번 규칙 자체의 공용 구현(예:
`conditional_write` 헬퍼)에 결함이 있을 수 있다 — 플랫폼 엔지니어링 리드에게
즉시 에스컬레이션.

## 사후 조치

재발 패턴으로 확인되면 105 §1에 사례를 추가하고, 같은 결함 클래스가 있는
다른 애그리게잇을 전수 점검하는 후속 작업을 만든다.
