# RB-03: LIVE 차단 관측 (설정 오류 vs 공격)

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A4/A11, §7.5.

## 트리거 알림

- `A4_LiveBlockedInPaper`(critical) — `aios_foundation_paper_control_order_intent_count_total{mode="live_blocked"}` 5분 내 증가.
- `A11_LiveSecretDecryptInPaper`(critical) — PAPER 런타임에서 `scope="LIVE"` 비밀 복호 시도 관측.

## 배경

FROZEN_PAPER_ONLY 런타임(`AIOS_RUNTIME_MODE=PAPER`)은 LIVE 자격증명을 물리적으로
풀 수 없어야 한다(R6). 이 알림은 그 방어선이 **작동했다는** 신호이지 방어선이
뚫렸다는 신호가 아니다 — 그러나 왜 LIVE 경로가 시도됐는지는 반드시 조사해야
한다: 배포 설정 실수일 수도, 외부 공격 시도일 수도 있다.

## 진단 — 설정 오류 vs 공격 구분

1. 시도한 actor(`actor_subject_id`)가 내부 서비스 계정인지 실제 사용자
   세션인지 확인.
2. 같은 trace_id로 직전에 어떤 API 호출이 있었는지(로그 `trace_id` grep) —
   정상 사용자 플로우 중 우연히 LIVE 경로를 태운 것이면 라우팅/설정 버그.
3. 짧은 시간에 다수의 서로 다른 actor/IP에서 반복되면 공격(자격증명 스캐닝,
   권한 상승 시도) 가능성 — `aios_auth_rate_limited_count_total`도 같이 확인.
4. `AIOS_RUNTIME_MODE`, `CREDENTIAL_ENCRYPTION_KEYS_LIVE*` 계열 환경변수가
   이 인스턴스에 실수로 설정돼 있지 않은지 배포 설정을 직접 확인(있으면
   기동이 거부돼야 정상 — 거부되지 않았다면 그 자체가 P0 결함).

## 조치

- 설정 오류로 판정: 원인 배포/설정을 롤백하고 재발 방지를 위해 CI에
  `AIOS_RUNTIME_MODE=PAPER`에서 LIVE 변수 존재 시 실패하는 게이트가
  있는지 확인(`test_key_ring.py`).
- 공격으로 판정: 해당 actor/세션을 즉시 revoke(`logout_all`), 관련 IP를
  rate limit/차단 목록에 추가, break-glass 없이도 세션 강제 종료 가능한
  관리자 절차를 사용.

## 에스컬레이션

공격으로 의심되는 즉시 보안 담당자를 호출한다. 설정 오류라도 LIVE 경로가
실제로 열렸는지(주문이 거래소로 나갔는지)는 반드시 확인 — `outcome=accepted`
가 하나라도 있으면 최우선 사고로 격상한다.

## 사후 조치

원인·판정·조치를 사고 기록에 남기고, 같은 실수가 재발하지 않도록 설정
검증을 배포 파이프라인 단계로 옮기는 것을 검토한다.
