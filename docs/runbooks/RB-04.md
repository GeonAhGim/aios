# RB-04: tenant mismatch (confused deputy 조사 절차)

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A5, §7.5, R3.

## 트리거 알림

- `A5_TenantMismatchOnTrace`(critical) — `increase(aios_auth_tenant_mismatch_count_total[5m]) > 0`.

## 배경

같은 `trace_id`(하나의 요청)에서 둘 이상의 `tenant_id`가 바인딩되면
`tenant_binding.rebind_tenant()`가 이 카운터를 증가시킨다(§2.1). 이는 confused
deputy 패턴의 초기 신호일 수 있다 — 예: 요청 경로 A에서 tenant X로 인증됐는데
경로 B(하위 서비스 호출 등)에서 tenant Y의 데이터에 접근을 시도.

## 진단

1. 해당 `trace_id`로 전체 요청 로그를 재구성한다(`event=http_request_completed`
   포함) — 어떤 라우트에서 처음 tenant가 바인딩됐고, 어디서 다른 tenant_id로
   재바인딩이 발생했는지 순서대로 나열.
2. 요청의 `X-Tenant-Id` 헤더 값과 인증된 사용자의 실제 membership(`resolve_tenant_context`
   결과)을 비교 — 헤더 위조 시도인지, 코드가 잘못된 tenant_id를 넘긴 버그인지 구분.
3. 실제로 다른 테넌트의 행이 반환/변경됐는지 확인한다(RLS가 이중 방어선이므로
   `tenant_transaction`이 걸린 채로 실행됐다면 DB 레벨에서 막혔을 가능성이 높지만,
   확인 없이 안전하다고 가정하지 않는다).
4. 같은 actor에서 반복되는지, 다수 actor에서 산발적인지 — 반복이면 코드 버그
   우선 의심, 산발적이면 악의적 시도 우선 의심.

## 조치

- 코드 버그로 판정: 잘못된 tenant_id를 넘기는 호출부를 식별해 핫픽스, 영향받은
  요청 목록을 확보해 데이터 노출 여부를 별도로 검증.
- 악의적 시도로 판정(confused deputy 공격): 해당 세션 즉시 revoke, membership이
  없는 테넌트에 대한 접근이었다면 계정 자체를 잠정 정지하고 보안팀에 인계.
- 어느 쪽이든: 실제 데이터가 유출/변경됐는지 `test_rls_scoping.py`/
  `test_cross_tenant_membership.py`류 시나리오로 재현 시도해 영향 범위를 확정한다.

## 에스컬레이션

데이터 유출이 확인되거나 의심되면 즉시 보안 담당자 + 컴플라이언스에 통지
(R3 요구사항 위반은 규제 보고 대상일 수 있음).

## 사후 조치

원인이 코드 버그였다면 회귀 테스트를 추가하고, 같은 클래스의 다른 호출부에도
동일한 결함이 없는지 전수 점검한다.
