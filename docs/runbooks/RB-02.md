# RB-02: 감사(audit) append 실패

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A7, §7.5.

## 트리거 알림

- `A7_AuditAppendFailed`(critical) — `increase(aios_audit_append_count_total{outcome="error"}[5m]) > 0`.

## 거래 중단 판단 기준

**`audit_event`(또는 `audit_log`) append가 한 번이라도 실패하면 신규 배포를
시작하지 않는다.** 감사 기록은 사후 조사·컴플라이언스의 유일한 증거이므로,
실패를 방치한 채 배포를 계속하면 실패 구간이 넓어져 조사가 불가능해진다.
이미 진행 중인 거래(주문 제출 등)를 강제로 멈출 필요는 없지만, 신규 리스크
결정·주문 경로를 여는 배포·마이그레이션은 원인 파악 전까지 보류한다.

## 증상

`sink=audit_log` 또는 `sink=audit_event` 라벨의 `outcome=error` 카운터가
증가. 애플리케이션 요청 자체는 대개 성공(감사 실패가 요청을 막지 않는
fail-open 설계인 경로가 있는지부터 확인 — 108 R2 요구는 실패 시 최소한
관측은 되어야 한다는 뜻이지 요청 차단을 의미하지 않는다).

## 진단

1. `component=<sink 기록 지점>` 로그에서 `event=audit_append_failed`(또는 동급)
   예외 메시지 확인 — DB 제약 위반(스키마 drift), 커넥션 실패, 직렬화 오류 중
   무엇인지 구분한다.
2. 실패가 특정 tenant/actor에 집중되는지, 전역적인지 확인(전역이면 인프라
   문제 가능성 높음).
3. `alembic_version`이 `audit_log`/`audit_event` 테이블의 기대 스키마와
   일치하는지 확인(마이그레이션 누락 시 컬럼 불일치로 INSERT 실패).

## 조치

- 스키마 drift면: 누락된 마이그레이션을 즉시 적용.
- 커넥션/인프라 문제면: RB-01과 동일한 풀·DB 가용성 점검을 수행.
- 원인 불명이면: 실패한 이벤트의 payload를 별도 로그(가능하면 파일 fallback)로
  보존해 사후 재기록(backfill) 근거를 남긴다 — 유실을 방치하지 않는다.

## 에스컬레이션

원인 파악 없이 5분 이상 지속되면 즉시 온콜 리드 + 컴플라이언스 담당자에게
알린다(R2/R9 게이트 요구사항).

## 사후 조치

실패 구간 동안의 감사 공백을 다른 로그(구조화 로그, DB WAL 등)로 재구성할 수
있는지 확인하고, 재구성한 레코드는 `backfilled=true` 플래그로 원본과 구분한다.
