# RB-01: 루프 정지 / readiness 실패

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A2/A3/A10, §7.5.

## 트리거 알림

- `A2_EventBusQueueDepthHigh`(warn) — `aios_event_bus_queue_depth_gauge > 800` 5분 지속.
- `A3_LoopStale`(critical) — `aios_loop_last_success_age_seconds > 900` 2분 지속.
- `A10_ReadinessDown`(critical) — `aios_readiness_check_status == 0` 1분 지속.

## 증상

백그라운드 루프(4개 — `main.py` 등록 목록 참조) 중 하나가 tick을 멈췄거나,
이벤트 버스 큐가 소비 속도를 못 따라가 쌓이고 있다. `GET /readyz`가 503을
반환하면 로드밸런서가 이 인스턴스를 트래픽에서 제외한다(의도된 동작).

## 진단

1. `GET /readyz` 응답 본문(`ReadinessReport`)에서 어떤 check가 실패했는지 확인
   (`checks[].name`, `checks[].ok`).
2. `component=safety.<loop_name>` 필터로 최근 로그에서 `event=loop_tick_failed`를
   찾아 예외 스택을 확인한다(108 §4 어휘).
3. `aios_event_bus_handler_count_total{outcome="error"}`가 같은 구간에 늘었는지
   확인 — 핸들러 예외가 큐 소비를 막고 있을 가능성.
4. DB 커넥션 풀 고갈 여부(`pool ping` 단계 실패)와 `alembic_version` 불일치
   여부(배포 중 마이그레이션 누락)를 `/readyz` 세부 항목에서 구분한다.

## 조치

- 풀 고갈이면: 느린 쿼리를 찾아 종료하거나 풀 크기를 임시 확대하고 원인 조사를
  후속 작업으로 남긴다.
- 특정 루프의 예외 반복이면: 해당 루프만 재시작 가능한 배포라면 재시작, 아니면
  프로세스 전체 재기동.
- 이벤트 버스 큐 적체면: 소비 실패 핸들러를 식별해 격리(dead-letter 유사 처리)
  하고, 재처리는 별도 스크립트로 수행 — 큐를 비우려고 무작정 재기동하지 않는다
  (in-flight 이벤트 유실 위험).
- readiness가 `alembic_version` 불일치로 실패하면 마이그레이션을 즉시 적용하거나
  해당 리비전을 배포한 인스턴스를 롤백한다.

## 에스컬레이션

2분 내 원인이 안 잡히면 온콜 리드를 호출한다. 여러 인스턴스가 동시에 503이면
배포 롤백을 우선 고려(신규 리비전이 원인일 가능성).

## 사후 조치

근본 원인을 `docs/RED_TEAM_FINDINGS.md` 또는 사고 기록에 남기고, 재발 시
자동 복구(재시작 정책)가 필요한지 판단한다.
