# RB-06: break-glass 사용 (사후 리뷰)

Spec: `docs/specs/L4_platform_observability_tenancy_api_v1.0.md` §7.4 A8, §7.5, §2.2 `break_glass.py`.

## 트리거 알림

- `A8_BreakGlassUsed`(critical, 정보성) — `increase(aios_security_break_glass_count_total{phase="used"}[1h]) > 0`.

## 배경

break-glass는 정상 승인 절차를 우회하는 비상 권한(`kill_switch_override`,
`tenant_read`, `credential_revoke`)이다. 요청자(`admin_id`)와 승인자
(`approved_by`)가 서로 달라야 하고 둘 다 MFA 인증 상태여야 하며, grant는
60분 이내 만료, 1회만 소비 가능(조건부 UPDATE `used_at IS NULL`). 이 알림은
막아야 할 사고가 아니라 **반드시 사람이 검토해야 하는 사용 기록**이다.

## 사후 리뷰 체크리스트 (24시간 이내 수행)

1. 요청 사유(`BreakGlassGrant.reason`)가 실제 상황과 부합하는지 확인.
2. 요청자·승인자가 각각 해당 scope에 대한 정당한 권한을 가진 admin인지 확인.
3. `consume()` 시점과 실제로 수행된 작업(kill switch 발동, tenant 읽기,
   자격증명 해지 등)의 로그가 일치하는지 — grant된 scope 밖의 작업을 하지
   않았는지 확인.
4. grant 발급 시각과 소비 시각 사이 간격이 비정상적으로 짧거나(사전 조율된
   우회 남용) 만료 직전이었는지(60분 제한 회피 시도 패턴) 확인.
5. 같은 admin이 짧은 기간 내 반복적으로 break-glass를 쓰고 있다면 —
   정상 절차(권한 신청)로 전환해야 할 반복 업무인지 검토.

## 조치

- 정당한 비상 사용으로 확인되면: 리뷰 결과를 감사 기록에 첨부하고 종료.
- 부적절한 사용으로 확인되면: 관련 admin 계정을 즉시 재검토(권한 축소 또는
  MFA 재설정 요구), 보안 담당자에게 인계.

## 에스컬레이션

리뷰에서 승인 사유가 불명확하거나 요청자·승인자 관계가 의심스러우면 즉시
보안 리드에게 에스컬레이션한다 — break-glass 남용은 confused deputy나 내부
위협의 신호일 수 있다.

## 사후 조치

반복적으로 같은 유형의 break-glass가 필요하다면, 그 작업을 위한 정규 권한
경로(role 추가 등)를 만드는 것을 검토해 비상 경로 사용 빈도를 낮춘다.
