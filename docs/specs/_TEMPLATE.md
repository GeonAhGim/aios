# L4 구현 명세 템플릿 (기관·자산운용사급)

모든 L4 명세는 이 구조를 따른다. 목적: "형식상 기초"가 아니라 기관이 실제로
운용에 쓰는 수준의 요구를, 한 세션이 리프 하나(파일 하나, ≤300줄)씩 바로 구현할
수 있게 쪼개는 것.

## 0. 문서 메타
status / owner role / supersedes / depends on / implemented by(파일 경로) / verification evidence(테스트 경로)

## 1. 기관급 요구 (왜 기초 수준으로는 부족한가)
- 자산운용사·기관이 이 도메인에 요구하는 것(규제·감사·성능·결정론·복구)을 항목별로.
- 현재 코드의 수준(docs/FULL_AUDIT_2026-09-02.md 인용)과의 격차.

## 2. 모듈 분해 (최소단위)
표: `파일 경로 | 단일 책임 | 공개 계약(함수/클래스 시그니처) | 의존(포트) | 줄수 상한 | Zone`
- 도메인 규칙은 순수 함수/클래스(외부 I/O 없음). I/O는 어댑터.
- 한 파일 = 한 책임. 300줄 초과 시 분할 지점을 명세에 미리 적는다.

## 3. 계약 (Contract)
- 입력/출력 DTO(pydantic) 필드·타입·단위·정밀도(Decimal, tz-aware UTC).
- 버전(`schema_version`)·호환 규칙(107번).
- 에러 taxonomy: 코드 / 재시도 가능 여부 / 호출자 조치.

## 4. 불변조건·상태기계
- 위반 시 fail-closed인지 fail-open인지 명시. DB 제약으로 강제되는 것과 코드로 강제되는 것 구분.
- 상태 전이표(from, event, guard, to, side-effect, 감사 이벤트).

## 5. 동시성·멱등성·트랜잭션 경계 (105번 표준)
- 어떤 쓰기가 조건부 UPDATE/FOR UPDATE/advisory lock인지, 멱등키 스코프·digest, outbox 여부.

## 6. 실패 모드와 복구
- 표: `실패 | 감지 방법 | 즉시 조치 | 복구 절차 | 감사 기록`
- 재시작·네트워크 분리·부분체결·공급자 불명 상태·시계 드리프트.

## 7. 성능·SLO·관측성 (108번)
- 지연/처리량 목표(수치), 측정 지점, 메트릭 이름, 로그 필드(trace_id, tenant_id, component, event, duration_ms), 알림 조건.

## 8. 테스트 계획
- 단위(순수 규칙) / 통합(실DB) / 적대적(경합·변조·교차 테넌트) / 계약(스키마) / 성능. 각 리프에 최소 negative test 1개.

## 9. 리프 목록 (구현 순서)
표: `리프 ID | 파일 | 선행 리프 | DoD(검증 명령·기대 결과) | 예상 크기`
- 리프 하나 = 커밋 하나. 각 리프는 독립적으로 CI 통과 가능해야 한다.

## 10. 미확정·리스크
- 외부 사실 확인 필요 항목(거래소 문서, 규제)은 "미확인"으로 정직하게.
