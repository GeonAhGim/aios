&nbsp;&nbsp;&nbsp;&nbsp;↓
**② FROZEN-PAPER-ONLY 경계(FD-8)** — ADR-2026-08-29-E로 PAPER 모드

전까지 코드 레벨 하드가드로 계속 차단. ①이 끝나야 이 "경계선"이 무엇을

**③ 안전·거버넌스 계층(FD-9~10)** — ①②가 만든 실행 파이프라인을 감시·

&nbsp;&nbsp;&nbsp;&nbsp;↓
**④ 사용자 대면 계층(FD-11~21)** — v1.0 이후 신규 추가된 멀티테넌시·
마켓플레이스·프론트엔드. ①②③이 만든 "단일 파이프라인"을 여러 사용자가
안전하게 나눠 쓰게 만드는 계층이라 반드시 ①②③ 이후. **이 그룹 내부는

되고, 유일한 예외는 `FD-11.5`(회원탈퇴, 리프 단위) — 이건 FD-16(실행

## FD-2 시장 데이터 처리

### FD-2.1 시세 조회 (REST)

- **목적**: 특정 심볼의 현재가·호가 스냅샷을 즉시 조회한다.
- **트리거**: Scanner(FD-5.2), 또는 다른 모듈의 명시적 요청.
- **입력**: `symbol: str`, `exchange: str`
- **처리 단계**:
  1. 해당 거래소의 `ExchangeAdapter.get_ticker(symbol)` 호출
  2. 응답을 `Parser.parse_ticker()`(FD-2.5)로 정규화
  3. `source_type="primary"`로 태깅
- **출력**: `Ticker` 모델(01번 §1.3)
- **예외 상황**:
  - 존재하지 않는 심볼 → `FatalExchangeError`(11번 §11.3), 재시도 없음
  - API 타임아웃 → `RetryableExchangeError`, 지수백오프 최대 5회(05번 §5.5)
  - Rate Limit 초과 → 응답 헤더의 재시도 대기시간 준수(거래소별 상이, 실제 문서 확인 필요)
- **완료조건**: Bitget Demo 계정으로 5개 심볼(06번 §6.2) 각각 조회 성공, 없는 심볼 요청 시 명확한 예외 발생 확인.
- **관련 스펙**: 02번(ExchangeAdapter), 01번 §1.3(Ticker)
- **작업 트리 매핑**: 6.4(BitgetAdapter Market Data), 5.4(Parser)

### FD-2.2 실시간 시세 구독 (WebSocket)

- **목적**: 심볼의 시세 변화를 지속적으로 수신해 Event Bus에 발행한다.
- **트리거**: 시스템 시작 시 Phase 1 대상 심볼(06번 §6.2) 전체에 대해 자동 구독.
- **입력**: `symbol: str`, `callback: TickerCallback`(02번 §6.1)
- **처리 단계**:
  1. `ExchangeAdapter.subscribe_ticker_stream(symbol, callback)` 호출
  2. 콜백 내부에서 수신 데이터를 `Parser.parse_ticker()` 통과
  3. `event_bus.publish("market.ticker.updated", ticker)` (05번 §5.3 Topic)
- **출력**: 없음(부수효과로 Event Bus에 지속 발행)
- **예외 상황**:
  - 연결 끊김 → Adapter 내부에서 재연결 시도(02번 §2.3), 재연결 중 `market.distrust.entered` 발행
  - 재연결 성공 → `market.distrust.exited` 발행
  - 재연결 반복 실패(Draft: 5회 초과) → `CRITICAL` 레벨 로그(07번 §7.1) + `audit_log` 기록
- **완료조건**: 구독 시작 후 최소 60초간 끊김 없이 이벤트 수신, 강제로 연결을 끊었을 때 재연결 및 distrust 이벤트 발행 확인(통합 테스트로 시뮬레이션).
- **관련 스펙**: 02번 §2.3, 05번 §5.3
- **작업 트리 매핑**: 6.5

### FD-2.3 캔들 조회

- **목적**: 특정 타임프레임의 OHLCV 이력 데이터를 조회한다(초기 스캐닝·향후 백테스트 대비).
- **트리거**: Scanner, 또는 수동 요청.
- **입력**: `symbol: str`, `timeframe: str`, `limit: int = 100`
- **처리 단계**: FD-2.1과 동일 패턴, `get_ohlcv()` 호출 → `Parser.parse_candles()`(FD-2.5)
- **출력**: `list[Candle]`
- **예외 상황**: FD-2.1과 동일 + `limit` 과다 요청 시 거래소 최대치로 자동 축소(Draft, 거래소별 최대값 확인 필요)
- **완료조건**: 5개 심볼 × 3개 타임프레임(1m/5m/1h) 조합 조회 성공.
- **관련 스펙**: 02번, 01번 §1.3(Candle)
- **작업 트리 매핑**: 6.4, 5.5

### FD-2.4 호가창 조회

- **목적**: 매수/매도 호가 스냅샷 조회(향후 슬리피지 계산·TWAP 실행 설계에 필요).
- **트리거**: FD-8.4(주문 실행 트리거, FROZEN)가 슬리피지 추정을 위해 호출,
  또는 FD-2.1과 동일한 주기적 폴링.
- **입력/처리/출력**: FD-2.1과 동일 패턴, `get_orderbook()` → `Parser.parse_orderbook()`(FD-2.5)
- **예외 상황**: FD-2.5(파싱)가 예상 필드 누락으로 실패하는 경우 그대로 전파
  (FD-2.5 예외 상황과 동일 — 이 계층에서 별도로 흡수하지 않는다).
- **완료조건**: depth=20 기준 5개 심볼 조회 성공, bids/asks 가격 정렬(내림차순/오름차순) 검증.
- **관련 스펙**: 02번, 01번 §1.3(OrderBook)
- **작업 트리 매핑**: 6.4, 5.6

### FD-2.5 원시 데이터 파싱

- **목적**: 거래소별 Raw JSON 응답을 내부 표준 모델(01번)로 변환 — 이 계층 덕분에 상위 모듈은 거래소 차이를 몰라도 된다.
- **트리거**: FD-2.1~2.4 내부에서 호출.
- **입력**: 거래소별 Raw `dict`, `exchange: str`
- **처리 단계**: 거래소별 필드명 매핑(예: Bitget의 `lastPr` → `Ticker.price`) → `Decimal` 변환 시 11번 §11.2 정밀도 규칙 적용 → 표준 모델 생성
- **출력**: `Ticker` | `Candle` | `OrderBook`
- **예외 상황**: 예상 필드 누락 시 `FatalExchangeError`(거래소 API 스펙 변경 가능성을 즉시 드러내기 위해 조용히 기본값 채우지 않는다)
- **완료조건**: 실제 Bitget/KIS 응답 샘플(fixture) 기준 단위 테스트 전부 통과.
- **관련 스펙**: 03번 §3.2(Parser), 01번
- **작업 트리 매핑**: 5.4, 5.5, 5.6

### FD-2.6 데이터 신뢰도 검증 (다중소스 교차확인)

- **목적**: Primary 피드와 Reference 피드 간 괴리를 감시해 오라클 왜곡을 방어한다(AIOS 정책문서 8.1-A).
- **트리거**: FD-2.2로 신규 시세가 들어올 때마다.
- **입력**: `Ticker`(primary), 최근 Reference 시세 캐시
- **처리 단계**:
  1. 괴리율 계산: `|primary.price - reference.price| / reference.price`
  2. 히스테리시스 적용(진입 1.5% / 해제 0.75%+60초, `risk_policy.yaml`의 `data_distrust` 섹션, 07번 §7.2)
  3. 임계치 초과 시 `market.distrust.entered` 발행, 신규 포지션 진입 판단(FROZEN, FD-8)에서 참조
- **출력**: 없음(상태 전이 + 이벤트 발행)
- **예외 상황**: Reference 피드 자체가 없는 경우(Phase 1은 Reference 소스 미구축 가능) → 이 검증 자체를 skip하고 WARNING 로그로 명시 — **조용히 항상 통과시키지 않는다.**
- **완료조건**: 인위적으로 괴리 데이터 주입 시 정확히 히스테리시스 규칙대로 상태 전이하는지 통합 테스트로 검증.
- **관련 스펙**: 정책문서 8.1-A, 07번 §7.2(risk_policy.yaml)
- **작업 트리 매핑**: 10번 문서에 없던 리프 — "5.11 데이터 신뢰도 검증기" 신규 추가 필요(문서 하단 참조)

## FD-3 거래소 연동

### FD-3.1 인증

- **목적**: 거래소 API 호출에 필요한 인증 토큰/세션을 확보한다.
- **트리거**: Adapter 초기화 시.
- **입력**: `.env`에서 로드한 API Key/Secret(FD-1.1)
- **처리 단계**(거래소별 상이):
  - Bitget: API Key/Secret/Passphrase 기반 서명(HMAC) — 요청마다 서명 생성
  - KIS: OAuth 2.0 2-legged — `app_key`/`app_secret`으로 access token 발급, 토큰 만료 전 갱신
- **출력**: 인증된 클라이언트 세션(내부 상태)
- **예외 상황**: 인증 실패 → `FatalExchangeError`, 재시도하지 않고 즉시 CRITICAL 로그(잘못된 키로 반복 시도 시 계정 잠금 위험)
- **완료조건**: 양쪽 거래소 모두 인증 성공 후 최소 1개 조회성 API 호출 성공.
- **관련 스펙**: 02번, 07번 §7.3(Secrets)
- **작업 트리 매핑**: 6.3, 6.9

### FD-3.2 계좌 잔고 조회

- **목적**: 자산별 총잔고·가용잔고 조회.
- **트리거**: FD-19.1(포트폴리오 조회), FD-16.1(자본배분 지정) 등 상위 기능이
  잔고 대비 검증이 필요할 때, 또는 주기적 캐시 갱신(Draft: 10초 간격).
- **입력**: `asset: str | None`
- **처리**: `get_balance()` 호출 → `AccountBalance` 리스트 반환. **11번 §11.1 원칙에 따라 반환값은 Currency 태깅 필수**(Bitget=USDT 계열, KIS=KRW).
- **출력**: `list[AccountBalance]`
- **예외 상황**: 거래소 API 호출 실패 → FD-3.6 재시도 정책 적용, 소진 시
  `RetryableExchangeError` 전파(직전 캐시값으로 조용히 대체하지 않는다 — 오래된
  잔고로 자본배분 판단이 이뤄지면 안 되므로).
- **완료조건**: 양쪽 거래소 잔고 조회 성공, 통화 필드가 올바르게 채워지는지 확인(§11.1 Money 타입 적용 후).
- **관련 스펙**: 02번, 11번 §11.1, FD-3.6
- **작업 트리 매핑**: 6.6, 6.10

### FD-3.3 포지션 조회

- **목적**: 자산별 보유 포지션(수량·평단가·미실현손익) 조회.
- **트리거**: FD-16.4(실행 모니터링)·FD-19.1(포트폴리오 조회) 등 상위 기능이 주기적으로
  호출, 또는 주문 체결 직후 정합성 확인 목적으로 즉시 호출.
- **입력**: `symbol: str | None`(없으면 전체 조회)
- **처리**: `get_positions()` 호출 → `Position` 리스트 반환. FD-3.2와 동일하게
  Currency 태깅 필수(11번 §11.1).
- **출력**: `list[Position]`(비어있을 수 있음)
- **예외 상황**: 거래소 API 자체 오류(인증 만료 등) → FD-3.6의 재시도 정책을
  그대로 따름, 재시도 소진 후에도 실패 시 `RetryableExchangeError` 전파(빈
  리스트로 조용히 대체하지 않는다 — "포지션이 없음"과 "조회 실패"를 절대
  혼동하지 않는다).
- **완료조건**: 포지션 없는 상태에서 빈 리스트 반환 확인(에러 아님), 인증 만료
  상태에서 호출 시 빈 리스트가 아니라 명시적 예외가 발생함을 확인.
- **관련 스펙**: 02번(ExchangeAdapter.get_positions), 01번 §1.4(Position)
- **작업 트리 매핑**: 6.6, 6.10

### FD-3.4 주문 상태 조회

- **목적**: 특정 주문의 현재 거래소측 상태를 재확인 — 특히 UNKNOWN 상태 해소용(7.5 멱등성 원칙).
- **트리거**: FD-4.2 주문 전송 후 상태 폴링, 또는 FD-4.5 UNKNOWN 상태 재조회 절차.
- **입력**: `order_id: str`(내부 ID 또는 거래소 ID)
- **처리**: `get_order()` 호출.
- **출력**: `Order`(현재 상태 반영)
- **예외 상황**: 거래소가 해당 주문 자체를 못 찾는 경우 — "존재하지 않음"과 "아직 시스템에 반영 안 됨"을 구분해야 함(Draft: 최근 생성된 주문은 수 초 재시도 후 최종 실패 처리).
- **완료조건**: FD-4.2에서 생성한 주문의 상태 변화(CREATED→...→FILLED)를 폴링으로 정확히 추적.
- **관련 스펙**: 02번(get_order), 04번(orders 테이블 idx_orders_unknown)
- **작업 트리 매핑**: 6.7

### FD-3.5 헬스체크

- **목적**: State DB와 무관하게 거래소 자체 응답성을 독립 확인(정책문서 8.6-A-1-2 Split-Brain 방어의 데이터 소스).
- **트리거**: FD-9.3(Split-Brain 진단)이 주기적으로 호출(Draft: 5초 간격), 또는
  FD-9.1 Watchdog이 손실 감시 중 거래소 응답성 자체를 의심할 때 즉시 호출.
- **입력**: 없음(대상 거래소 컨텍스트는 Adapter 인스턴스에 이미 바인딩됨)
- **처리**: 경량 조회 API(예: 잔고 조회) 호출, 응답 성공/실패만 판단.
- **출력**: `bool`(응답 성공 여부) + 응답 지연시간(ms, FD-9.3이 지연 자체도 판단
  재료로 쓸 수 있도록)
- **예외 상황**: 타임아웃 자체를 `False`로 취급(예외를 던지지 않음) — 헬스체크는
  "확인"이 목적이지 "실패해도 되는 API 호출"이 아니므로, 호출부가 매번
  try/except를 감쌀 필요 없이 항상 bool을 받도록 설계.
- **완료조건**: 정상 시 `True`, 강제로 네트워크 차단 시 `False` 또는 타임아웃 예외
  없이 `False` 반환.
- **관련 스펙**: 02번(health_check), 정책문서 8.6-A-1-2, FD-9.3
- **작업 트리 매핑**: 6.8

### FD-3.6 연결 끊김 및 재연결 처리

- **목적**: REST 호출 실패 시 일관된 재시도 정책을 적용한다(WebSocket 재연결은
  FD-2.2에서 이미 다룸 — 이 항목은 REST 전용).
- **트리거**: FD-3.1~3.5 중 어느 REST 호출이든 네트워크/타임아웃 오류 발생 시.
- **입력**: 실패한 원본 요청(재시도용 컨텍스트 — 메서드명, 파라미터)
- **처리**: 05번 §5.5의 재시도 정책(지수백오프, 최대 5회) 그대로 적용.
- **출력**: 재시도 성공 시 원본 API의 정상 반환값, 소진 시 예외
- **예외 상황**: 5회 재시도 모두 실패 → `RetryableExchangeError` 최종 전파(호출부가
  이걸 받아 각자의 맥락에 맞게 처리 — 예: FD-3.3은 조용히 대체하지 않고
  그대로 전파, FD-3.5 헬스체크는 `False`로 흡수).
- **완료조건**: 강제 네트워크 오류 주입 시 정확히 5회 재시도 후 `RetryableExchangeError` 최종 전파 확인.
- **관련 스펙**: 05번 §5.5, 11번 §11.3(MihwaError 계층)
- **작업 트리 매핑**: 6.4~6.7 전체에 걸쳐 공통 적용(별도 리프 아님, 공통 유틸)

## FD-6 이벤트 처리

### FD-6.1 이벤트 발행

- **목적**: 시스템 내 상태 변화를 다른 모듈에 알린다.
- **트리거**: FD-2.2, FD-4.2 등 상태 변화가 발생하는 모든 지점.
- **입력**: `topic: str`(05번 §5.3 명명규칙 준수), `payload`
- **처리**: `InProcessEventBus.publish()` → topic별 큐에 적재 → 백프레셔 검사(08번 §8.6, 큐 깊이 1000 초과 시 발행 거부+WARNING)
- **출력**: 없음(비동기 발행, 발행자는 구독자의 처리 결과를 기다리지 않음)
- **예외 상황**: 큐 깊이 초과로 발행 자체가 거부된 경우 → 호출부에 `QueueBackpressureError` 반환(조용히 유실시키지 않음), CRITICAL 등급 topic(예: `approval.request.created`)은 이 거부조차 FD-9.6 에스컬레이션 대상.
- **완료조건**: 3개 핵심 topic(market.ticker.updated, order.status.changed, audit.decision.logged) 발행·수신 왕복 확인.
- **관련 스펙**: 05번
- **작업 트리 매핑**: 4.3

### FD-6.2 이벤트 구독 및 처리

- **목적**: 등록된 handler가 이벤트를 소비한다.
- **트리거**: 시스템 초기화 시 각 모듈이 자신의 handler를 등록(FD-1 초기화 순서
  이후), 이후 매 이벤트 발행(FD-6.1)마다 자동 호출.
- **입력**: `topic: str`, `handler: Callable`, `criticality: HandlerCriticality`
- **처리**: `subscribe(topic, handler)` 등록 시 `HandlerCriticality`(SAFE/CRITICAL) 명시 필수(05번 §5.5 — 미지정 시 등록 거부).
- **출력**: 없음(등록은 부수효과, 실제 이벤트 처리 결과는 handler 자체의 책임)
- **예외 상황**: `criticality` 미지정 → 등록 자체를 거부(런타임에 조용히 SAFE로
  기본값 처리하지 않는다 — 개발자가 반드시 명시적으로 판단하게 강제).
- **완료조건**: SAFE handler 예외 발생 시 다른 handler 영향 없음, CRITICAL handler 예외 발생 시 에스컬레이션 경로 작동 확인.
- **관련 스펙**: 05번 §5.5(HandlerCriticality)
- **작업 트리 매핑**: 4.3, 4.5

### FD-6.3 Handler 에러 처리

- **목적**: Handler 내부 예외가 시스템 전체를 무너뜨리지 않으면서도, 중요한
  실패는 조용히 묻히지 않도록 등급별로 다르게 처리한다.
- **트리거**: FD-6.2로 등록된 handler 실행 중 예외 발생.
- **입력**: 발생한 예외, 해당 handler의 `criticality`
- **처리**: 05번 §5.5 내용 그대로 — SAFE는 log_and_continue, CRITICAL은 escalate_and_retry(최대 5회 후 8.6 Circuit Breaker 경고 단계 격상 + Human 알림).
- **출력**: 없음(부수효과 — 로그 기록 또는 에스컬레이션 트리거)
- **예외 상황**: CRITICAL handler가 재시도 자체도 실패하는 예외(예: 재시도 로직
  자체의 버그)를 던지는 경우 → 재시도 루프가 무한히 돌지 않도록 5회 상한을
  하드코딩(설정으로 늘릴 수 없음, 정책문서 17.9-A와 무관하게 이건 안전상 고정값).
- **완료조건**: CRITICAL handler가 5회 재시도 후에도 실패 시 실제로 Circuit Breaker 상태가 변하는지 통합 테스트.
- **관련 스펙**: 05번 §5.5, FD-9.4(Circuit Breaker 상태전이)
- **작업 트리 매핑**: 4.5

### FD-6.4 재시작 시 정합성 복구

- **목적**: 프로세스가 비정상 종료 후 재시작됐을 때, 미체결 주문 등 중간 상태가
  거래소의 실제 상태와 어긋나지 않도록 복구한다.
- **트리거**: 시스템 시작 시, FD-1(초기화) 완료 직후.
- **입력**: 없음(자체적으로 DB 조회부터 시작)
- **처리**: 05번 §5.6 내용 그대로 — 시작 시 `orders`에서 비최종 상태 행 조회 → 거래소 실제 상태 재확인 → 필요 이벤트 재발행.
- **출력**: 재동기화된 주문 건수(로그 기록용)
- **예외 상황**: 재확인(FD-3.4) 자체가 실패하는 주문 → UNKNOWN 상태로 유지하고
  FD-9.6(Reconciliation 불일치 에스컬레이션) 대상으로 등록(복구를 포기하지 않고
  상위 절차로 넘김).
- **완료조건**: 프로세스를 강제 종료 후 재시작했을 때, 미체결 주문 상태가 정확히 재동기화되는지 시나리오 테스트.
- **관련 스펙**: 05번 §5.6, FD-4.5(UNKNOWN 상태 재조회), FD-9.6
- **작업 트리 매핑**: 4.6

## FD-4 주문 처리 (전송 계층)

> 이 대분류 전체의 전제: **판단(주문을 낼지 말지, 얼마나)은 FD-8(FROZEN)의 책임이다. FD-4는 "이미 승인된 주문을 어떻게 안전하게 전송·추적하는가"만 다룬다.** 8.2-A Master Authority 원칙의 실무적 경계선이 정확히 여기다.

### FD-4.1 주문 파라미터 검증

- **목적**: Order 객체가 거래소에 전송 가능한 형식적 요건을 충족하는지 확인(Risk 통과 여부와 무관 — 그건 FD-8.3의 책임).
- **트리거**: FD-8.4가 FD-4.2를 호출하기 직전 항상 선행.
- **입력**: `Order` 객체
- **처리 단계**: `Validator.validate_order_params()`(03번 §3.3) 호출 — tick_size 배수 확인, 수량>0, `LIMIT`인데 `price=None`이면 거부.
- **출력**: `ValidationResult`(예외를 던지지 않고 `is_valid`+`errors`로 반환 — 호출부가 판단)
- **예외 상황**: 이 함수 자체는 예외를 던지지 않는다 — "검증 실패"는 정상적인 반환값이지 예외 상황이 아니다.
- **완료조건**: 08번 §8.2 단위테스트 케이스(tick_size 위반, 수량 0 이하, LIMIT+price=None) 전부 통과.
- **관련 스펙**: 03번 §3.3, 01번 §1.4
- **작업 트리 매핑**: 5.7

### FD-4.2 주문 전송

> 이 기능은 처리 단계가 복잡해 4개 하위 리프로 세분화한다(세분화 예시 — 나머지 FD도 실제 구현 중 이 정도 복잡도가 드러나면 동일하게 쪼갠다).
> **트리거**: FD-8.4(주문 실행 트리거, FROZEN)가 매매 판단을 내린 직후. **출력**(전체 흐름): `Order`(최종 상태 반영).

#### FD-4.2-a 멱등성 사전 확인

- **목적**: 동일 `client_order_id`로 이미 전송된 주문이 있는지 확인 — 재시도로 인한 중복 주문 방지.
- **입력**: `client_order_id`, 주문 파라미터(symbol, side, quantity, price 등)
- **처리**: `orders` 테이블에서 `client_order_id` 조회. 이미 존재하면 그 행을 그대로 반환(재전송 아님, 기존 상태 재확인으로 전환).
- **완료조건**: 동일 `client_order_id`로 2번 호출 시 실제 거래소 호출은 1번만 발생.

#### FD-4.2-b 거래소 전송

- **목적**: 실제 `ExchangeAdapter.place_order()` 호출.
- **처리**: 호출 → `exchange_order_id` 수신 → `Order.status = SUBMITTED`.
- **예외 상황**: 거래소 거부(REJECTED 응답) → 예외 아님, 정상 흐름으로 `status=REJECTED` 처리. 네트워크 오류 → `RetryableExchangeError`, **재시도 전 반드시 FD-4.2-a를 다시 거쳐** 실제 전송 여부부터 재확인(무작정 재전송 금지).

#### FD-4.2-c DB 영속화

- **목적**: 05번 §5.6 원칙("DB가 항상 진실의 원천") 실행 — 이벤트 발행보다 먼저 커밋.
- **처리**: `orders` 테이블에 INSERT/UPDATE.

#### FD-4.2-d 이벤트 발행

- **처리**: `event_bus.publish("order.status.changed", order)`(FD-6.1 재사용).
- **완료조건**(FD-4.2 전체): Bitget Demo 실제 주문 1건 왕복 성공, 동일 `client_order_id` 재전송 시 중복 주문 미생성 확인.
- **관련 스펙**: 02번, 04번, 05번
- **작업 트리 매핑**: 6.7

### FD-4.3 주문 취소

- **목적**: 미체결 주문 취소.
- **트리거**: 사용자의 FD-16.3 중지 액션(즉시청산 선택 시), 또는 FD-9.2 Watchdog
  판정으로 시스템이 자동 취소.
- **입력**: `order_id`
- **처리**: `cancel_order()` → DB `status=CANCELLED` → 이벤트 발행.
- **출력**: `Order`(status=CANCELLED로 갱신됨)
- **예외 상황**: 이미 체결된 주문의 취소 시도 → 거래소가 거부 → 이를 오류로 취급하지 않고 FD-3.4(상태 재조회)로 전환.
- **완료조건**: 미체결 주문 취소 성공, 체결완료 주문 취소 시도 시 적절히 상태 재조회로 전환되는지 확인.
- **관련 스펙**: 02번(cancel_order), 04번(orders 테이블)
- **작업 트리 매핑**: 6.7

### FD-4.4 주문 정정

- **목적**: 지정가 주문의 가격/수량 변경(시장가는 정정 불가).
- **트리거**: FD-8.4(FROZEN)가 기존 지정가 주문의 가격을 재산정해야 한다고
  판단할 때(예: 시장 상황 변화로 체결 가능성 낮음).
- **입력**: `order_id`, `new_price`, `new_quantity`
- **처리**: `modify_order()`.
- **출력**: `Order`(정정된 가격/수량 반영)
- **예외 상황**: 시장가 주문 정정 시도 → FD-4.1 단계에서 사전 차단(거래소까지 안 감).
- **완료조건**: 지정가 정정 성공, 시장가 정정 시도 시 거래소 호출 없이 즉시 거부 확인.
- **관련 스펙**: 02번(modify_order), FD-4.1(사전 검증)
- **작업 트리 매핑**: 6.7

### FD-4.5 UNKNOWN 상태 재조회

- **목적**: 8.3 원칙 — UNKNOWN을 실패로 단정하지 않는다.
- **트리거**: 주문 상태가 UNKNOWN으로 관측될 때마다(응답 타임아웃, 파싱 실패 등).
- **입력**: `order_id`(UNKNOWN 상태로 관측된 주문)
- **처리**: FD-3.4를 최대 3회, 2초 간격으로 재호출 → 최종 상태 확정 시 DB 갱신+이벤트 발행 → 3회 후에도 UNKNOWN → **CRITICAL 로그**(자동 해소 포기, Human 개입 신호).
- **출력**: 확정된 `Order` 상태, 또는 3회 실패 시 UNKNOWN 유지 + CRITICAL 로그
- **예외 상황**: FD-3.4 재조회 자체가 매번 다른 이유로 실패(네트워크 vs 거래소
  내부 오류)하는 경우도 동일하게 3회 상한을 적용 — 실패 원인별로 재시도
  횟수를 리셋하지 않는다(무한 재시도 방지).
- **완료조건**: 강제 UNKNOWN 시뮬레이션 시 정확히 3회 재조회 후 상태 확정 또는 CRITICAL 로그 발생 확인.
- **관련 스펙**: 04번 `idx_orders_unknown` 인덱스 활용
- **작업 트리 매핑**: 6.7

- **입력**: `ScanCriteria`

- **출력**: `list[str]`

## FD-7 감사 및 로깅

### FD-7.1 구조화 로그 기록

- **목적**: 07번 §7.1 형식으로 전 모듈이 일관되게 로그를 남긴다.
- **트리거**: 모든 모듈에서 상시.
- **입력**: `level`, `module`, `event_type`, `correlation_id`, `message`
- **처리**: logger 인스턴스에 `level/module/event_type/correlation_id/message` 전달 → JSON Lines 출력.
- **출력**: 없음(부수효과 — 로그 스트림에 append)
- **예외 상황**: 로그 출력 대상(파일/스트림) 자체가 쓰기 실패 → 애플리케이션을
  중단시키지 않고 stderr로 대체 출력(로깅 실패가 거래 로직을 막아서는 안 됨,
  단 이 경우 자체가 CRITICAL 대상 — FD-7.2 감사로그와는 별개로 운영 모니터링
  대상).
- **완료조건**: 로그 100% 유효 JSON 파싱 가능, 필수 필드 누락 없음.
- **관련 스펙**: 07번 §7.1(LogEntry 스키마)
- **작업 트리 매핑**: 7.1 (FD-1.3과 동일 리프 — 초기화와 사용은 하나의 구현 단위)

### FD-7.2 감사로그(Audit Log) 기록

- **목적**: 8.10 원칙 — 중요 판단·행위는 WORM 테이블에 별도 기록.
- **트리거**: CRITICAL 레벨 로그 발생 시, 주문 생성/체결/취소, Watchdog/Circuit Breaker 발동, Capability Token 발급/무효화(FD-7.3) 등.
- **입력**: `actor_agent`, `action_type`, `target_type/id`, `decision_data`
- **처리**: `audit_log` 테이블 INSERT(UPDATE/DELETE는 DB 권한 자체로 불가, 04번 REVOKE 제약) → **`audit.decision.logged` 이벤트 발행(FD-6.1)**("0번부터 재검토" 라운드 추가 — 05번 §5.3 명명규칙이 "모든 주요 판단은 이 토픽으로도 발행"이라고 명시했으나 지금까지 DB INSERT만 다루고 이벤트 발행이 빠져있었음. 이 이벤트로 다른 모듈이 audit_log DB를 직접 폴링하지 않고 실시간 구독 가능 — 예: 향후 대시보드 실시간 감사로그 뷰).
- **출력**: `audit_log_id`(다른 모듈이 이 기록을 참조할 때 사용, 예: FD-18.2
  분쟁처리가 특정 시점 감사기록을 조회할 때)
- **예외 상황**: INSERT 자체가 실패(DB 연결 문제) → 시스템 전체의 CRITICAL 상황으로 취급, 로컬 파일에 임시 append 후 DB 복구 시 재적재(Draft — 05번 §5.6 재시작 복구 절차와 연계해 상세화 필요). **이벤트 발행 자체가 실패하는 경우** → INSERT는 이미 성공했으므로 데이터 유실은 아니나, FD-6.3 CRITICAL 정책으로 재시도(감사기록 자체의 실시간성이 깨지는 것도 경미하지 않은 문제로 취급).
- **완료조건**: `UPDATE`/`DELETE` 시도 시 권한 오류 확인(08번 §8.3에 이미 정의), `decision_data`만으로 판단 근거가 사후 재구성 가능한 수준인지 샘플 검토. **INSERT 성공 시 `audit.decision.logged` 이벤트가 실제로 발행되는지 확인.**
- **관련 스펙**: 정책문서 8.10, 04번(audit_log 테이블), 16.3(불변 감사로그 원칙), 05번 §5.3
- **작업 트리 매핑**: 3.10(테이블), **신규 리프 "7.4 audit_log 기록 유틸"** 필요(§하단 갱신 목록 참조)

### FD-7.3 Capability Token 발급·검증·무효화

- **목적**: 16.2 — DevEngine 작업 단위 인증을 실제로 발급·검증한다.
- **트리거**: 발급(DevEngine 신규 Task 착수 시), 검증(매 작업 요청마다), 무효화(Task 완료/취소/TTL만료 시).
- **입력**(발급): `task_id, repository, branch, paths, operations, network, secrets_scope, ttl_seconds`
- **처리 단계**:
  1. (발급) `paths`를 정책문서 15.6-A Zone 분류와 대조 — **FROZEN 경로 포함 시 발급 자체를 거부**
  2. (발급) `capability_tokens` 테이블 INSERT
  3. (검증) `token_id` 조회 → `revoked_at IS NULL AND now() < issued_at + ttl_seconds` 확인
  4. (무효화) `revoked_at` 갱신 + `revoked_reason` 기록(`task_completed`/`ttl_expired`/`cancelled`)
- **출력**: (발급) `token_id`, (검증) `bool`(유효 여부), (무효화) 없음(부수효과)
- **예외 상황**: FROZEN 경로 포함 발급 시도 → `ZoneViolationError`(11번 §11.3) + **즉시 `audit_log` 기록**(이례적 시도 자체가 조사 대상 — FD-7.2와 연동).
- **완료조건**: FROZEN 경로 포함 요청 거부 확인, TTL 만료 토큰으로 작업 시도 시 거부 확인, 정상 발급→사용→자동무효화 왕복 확인.
- **관련 스펙**: 16.2(정책문서), 04번(capability_tokens 테이블)
- **작업 트리 매핑**: 3.3(테이블), **신규 리프 "6.12 Capability Token 발급기"** 필요(§하단 갱신 목록 참조)

## FD-8 판단 계층 (FROZEN-PAPER-ONLY — ADR-2026-08-29-E)

> **ADR-2026-08-29-E 반영**: 이 대분류는 더 이상 인터페이스 명세만이
> 아니다 — PAPER 모드 실행에 한해 아래 실동작 명세를 그대로 구현한다.
> LIVE 경로는 15.6-D 조건 2(실계정 MFA·이중승인) 충족 전까지 각 함수의
> 진입점에서 `execution.mode != 'PAPER'`이면 무조건
> `FrozenZoneLiveModeBlockedError`를 던지는 하드 가드로 막는다(정책
> 문서상 금지가 아니라 실행되는 코드 자체의 차단 — 03번 §3.9 참조).
> FD-4(전송 계층)와의 경계는 그대로 유지한다: FD-8은 "낼지 말지, 얼마나"
> 만 판단하고, "어떻게 전송·추적하는가"는 FD-4의 책임이다.
>
> **8.2-A Master Authority 준수** — 아래 4개 함수 중 어디에도 LLM
> 호출·Agent 판단이 개입하지 않는다. 전부 `risk_policy.yaml`·
> `FSMStrategyConfig`·현재 시세라는 결정론적 입력만으로 동작한다.
>
> **PAPER 모드의 실제 의미**: 가상의 잔고·체결 시뮬레이션이 아니라
> **Bitget 자체의 Demo Trading 환경**(`BitgetAdapter.__init__(demo_mode=
> True)`가 이미 매 요청에 `paptrading: "1"` 헤더를 붙임, 06번 §6.1 확인)
> 을 그대로 쓴다 — 실제 API 왕복·실제 체결 로직 검증이 되면서도 실자금
> 위험은 없다. 즉 FD-4.2의 완료조건("Bitget Demo 실제 주문 1건 왕복
> 성공")이 이 PAPER 개방으로 곧바로 검증 가능해진다.

### FD-8.0 FSM 실행상태 추적 (신규 — FD-8.1의 전제)

- **목적**: `strategy_executions.status`(PENDING_APPROVAL/RUNNING/PAUSED/
  RETIRED, FD-16 소관)는 "이 실행을 사용자가 껐는가 켰는가"를 추적할
  뿐, FSM 6상태(IDLE/BUY_ORDER_PENDING/HOLDING/SELL_ORDER_PENDING/
  STOP_LOSS/EMERGENCY_EXIT, 9.11) 중 지금 어디에 있는지는 별도로
  추적해야 한다 — 이 컬럼이 지금까지 없었다(FD-16 구현 시점엔 FD-8이
  FROZEN이라 필요성이 드러나지 않았음).
- **처리**: `strategy_executions`에 `fsm_state VARCHAR(20) NOT NULL
  DEFAULT 'IDLE'` 컬럼 추가(마이그레이션 신규). RUNNING 전이 시 항상
  `IDLE`에서 시작.
- **완료조건**: 컬럼 추가 후 기존 테스트 회귀 없음, `fsm_state`가 FD-8.1의
  전이 결과로만 갱신되는지(다른 경로에서 직접 UPDATE하지 않음) 확인.
- **관련 스펙**: 04번(strategy_executions 테이블), 9.11(FSM 6상태)

### FD-8.1 전략 신호 생성

- **목적**: 실행 중인 전략의 현재 FSM 상태에서 나가는 전이 조건이
  시장 상태와 맞아떨어지는지 판단해 `Signal`(방향·목표수량·손절·익절)
  을 만든다. **"의도"만 만든다** — 실제 주문 여부·수량은 FD-8.2/8.3이
  결정한다(8.2-A).
- **트리거**: 실행 루프(Draft: 실행당 1초 간격 폴링, `risk_policy.yaml`에
  `execution_loop.interval_sec` 신설 필요)가 RUNNING 상태인 모든 실행에
  대해 매 틱 호출.
- **입력**: `FSMStrategyConfig`(compiled, ConditionCompiler 산출물),
  현재 `fsm_state`(FD-8.0), `market_state: dict[str, float]`(현재
  가격+`IndicatorService.calculate()`로 계산한 지표값들, 키는
  ConditionCompiler가 조건식에 쓴 것과 동일한 이름 — 예: `"RSI"`,
  `"SMA_timeperiod20"`).
- **처리 단계**:
  1. `fsm_config.transitions`에서 `from_state == 현재 fsm_state`인
     전이(들)를 찾는다. `IDLE→BUY_ORDER_PENDING`(entry),
     `HOLDING→SELL_ORDER_PENDING`(exit),
     `HOLDING→STOP_LOSS`(stop_loss) 3가지만 이 함수의 평가 대상이다 —
     나머지 3개 전이(`BUY_ORDER_PENDING→HOLDING`,
     `SELL_ORDER_PENDING→IDLE`, `STOP_LOSS→IDLE`)의 조건은 전부
     `"ORDER_FILLED"`(예약 리터럴)라 이 함수가 아니라 FD-4.2(주문 체결
     확인)가 트리거한다 — 9.11/ConditionCompiler 자체 docstring 원칙
     그대로.
  2. `HOLDING` 상태면 exit와 stop_loss 두 전이를 **모두** 평가한다 —
     stop_loss가 우선(같은 틱에 둘 다 충족되면 STOP_LOSS 전이를 만든다,
     손절이 항상 익절보다 안전 우선).
  3. 조건식 평가 — `ConditionEvaluator`(신규, ConditionCompiler의 역).
     문법은 컴파일러가 만든 그대로 고정: `"{indicator} {연산자}
     {threshold}"`를 `" AND "`/`" OR "`로 결합. `crosses_above`/
     `crosses_below`는 직전 틱의 `market_state` 스냅샷이 필요 —
     실행별로 최근 1틱 캐시를 들고 있는다(PreviewCalculator의
     `prev_value` 로직과 동일 원칙 재사용).
  4. 평가 결과가 `False`면 `None` 반환(신호 없음, 정상 흐름).
  5. `True`면 `Signal`을 만든다: `direction`은 전이 종류로 결정
     (entry→BUY, exit→SELL, stop_loss→SELL), `target_position`은 이
     함수에서 확정하지 않는다(`FD-8.2` 책임 — 이 필드는 Draft로
     `Decimal("0")` 채워 넘기고 FD-8.2가 실제 값으로 덮어씀,
     `confidence`는 Phase 1 Draft로 `1.0` 고정(다중 조건 충족도 기반
     정교화는 후속).
- **출력**: `Signal | None`
- **예외 상황**: `market_state`에 조건식이 참조하는 지표 키가 없음
  (예: 지표 계산에 필요한 캔들 수 부족, `IndicatorService`가 빈 배열
  반환) → 판단 보류로 처리(`None` 반환 + WARNING 로그) — 데이터 부족을
  "조건 미충족"으로 오판하지 않되, 강제로 신호를 만들지도 않는다
  (FD-9.1과 동일 "판단 불가를 정상으로 취급하지 않는다" 원칙의 반대
  방향 적용 — 여기서는 "판단 불가 시 아무 행동도 하지 않는 것"이 안전한
  쪽).
- **완료조건**: 6개 전이 각각에 대해 조건 충족/미충족 케이스 단위테스트,
  `crosses_above`/`crosses_below`가 직전 틱 캐시 없이는 항상 `False`를
  반환하는지(첫 틱 안전성) 확인, `HOLDING` 상태에서 stop_loss·exit
  동시 충족 시 stop_loss 우선 확인.
- **관련 스펙**: 03번 §3.5, 9.11, `condition_compiler.py`,
  `preview_service.py`(evaluator 로직 재사용 대상)
- **작업 트리 매핑**: 신규 "8.1 StrategyEngine + ConditionEvaluator"

### FD-8.2 포트폴리오 배분 결정

- **목적**: `Signal`을 실제 주문 가능한 수량(`AllocationDecision`)으로
  변환한다. 자본 배분 **한도**는 이미 FD-16.1(실행 생성 시점)에서
  확정돼 있다 — 이 함수는 그 한도 안에서 "지금 이 신호에 얼마를 쓸지"만
  계산한다(한도 재설정이 아님).
- **트리거**: FD-8.1이 `Signal`을 반환한 직후, 같은 틱에서 즉시 호출.
- **입력**: `Signal`, `current_portfolio_state: dict`(해당 실행의
  `allocated_capital`, 현재 보유 포지션 수량, 마지막 체결가).
- **처리 단계**:
  1. `direction == BUY`(entry): `approved_quantity =
     execution.allocated_capital / signal 발생 시점 현재가`(수수료·
     슬리피지는 Phase 1 미반영, Draft). 이미 보유 포지션이 있으면(중복
     진입 시도, 정상적으로는 `IDLE`에서만 entry 전이가 나오므로 발생
     안 해야 함) 오류로 거부.
  2. `direction == SELL`(exit/stop_loss): `approved_quantity =` 현재
     보유 포지션 수량 **전량**(Phase 1은 분할청산 미지원, 06번 §6.4
     "VWAP/Iceberg/SOR 등 고급 주문 전략 제외"와 동일 원칙 — 전량
     청산만 지원).
  3. `capital_pct = (approved_quantity * 현재가) / 계좌 총자산 * 100`
     (감사 추적용 — RiskEngine이 재검증할 값).
- **출력**: `AllocationDecision`
- **예외 상황**: 현재가 조회 실패(거래소 API 오류) → `AllocationDecision`
  을 만들지 않고 이 틱을 스킵(다음 틱 재시도) — 가격 정보 없이 수량을
  추정하지 않는다. SELL인데 보유 포지션이 0 → 오류로 처리(FD-8.1 로직
  버그 신호, 정상 흐름에서 발생하면 안 됨).
- **완료조건**: entry/exit/stop_loss 각각 정상 수량 계산 확인, 포지션
  없이 SELL 신호 처리 시 명시적 오류(조용히 무시하지 않음) 확인.
- **관련 스펙**: 03번 §3.6, FD-16.1(자본배분 한도)
- **작업 트리 매핑**: 신규 "8.2 PortfolioEngine"

### FD-8.3 리스크 검사 (가장 중요)

- **목적**: `AllocationDecision`이 실제로 주문 가능한지 최종 관문에서
  결정론적 규칙만으로 승인/거부한다. **이 함수를 통과하지 못한
  Allocation은 어떤 경로로도 Executor에 도달할 수 없다**(8.2-A Master
  Authority — 이 프로젝트에서 가장 중요한 단일 불변식).
- **트리거**: FD-8.2 직후, 같은 틱.
- **입력**: `AllocationDecision`, `account_state`(계좌 총자산, 당일
  실현+미실현 손익, 현재 보유 포지션 전체 목록, 심볼별 상관계수 —
  Phase 1 Draft는 마지막 항목 생략 가능).
- **처리 단계 — `risk_policy.yaml` 8개 지표를 순서대로 확인, 하나라도
  거부되면 즉시 중단(단락 평가)**:
  1. **Daily Loss** (`daily_loss.halt_pct`): 오늘 실현+미실현 손익률이
     -5% 이하 → 거부.
  2. **Max Drawdown** (`max_drawdown.hard_stop_pct`): 계좌 peak 대비
     현재 -15% 이하 → 거부.
  3. **Leverage** (`leverage.default_max`): PAPER 모드는 Phase 1 크립토
     현물 전용이라 항상 레버리지 1.0 — **이 지표는 통과로 고정**(파생
     상품 확장 시 별도 leaf에서 실제 레버리지·마진 검사로 교체, ADR
     대상 아님 — 06번 §6.1-A 자산군 확장 원칙 그대로 적용).
  4. **Position Concentration** (`position_concentration.
     single_asset_max_pct=20%`): 이 Allocation 체결 후 해당 심볼이
     전체 포트폴리오에서 차지할 비중 예측치가 20% 초과 → 거부.
  5. **Strategy Allocation** (`strategy_allocation.*`): FD-16.1이 이미
     검증했지만, 실행 생성과 신호 발생 사이 시간차 동안 계좌 잔고가
     바뀌었을 수 있어 **여기서 재검증**한다(레드팀 감사 #03에서 확인한
     대로 이 지표는 "전략 하나당 개별 한도"이지 포트폴리오 총합 한도가
     아님 — 그 재확인).
  6. **VaR** (`var.max_pct=5%`, `confidence=0.95`, `horizon_days=1`):
     Phase 1 Draft는 정규분포 가정 단순 근사(과거 20틱 수익률
     표준편차 기반) — 이 방법론 자체의 한계는 문서화하고, 통계적으로
     엄밀한 VaR는 FD-2(시장데이터 히스토리 파이프라인) 확충 후 개선
     대상으로 명시.
  7. **Correlation Risk** (`correlation_risk.threshold=0.7`,
     `aggregate_exposure_max_pct=30%`): 기존 보유 포지션과의 상관계수가
     0.7 초과인 심볼들의 합산 노출이 30% 초과 → 거부. Phase 1은 보유
     종목 수가 적어(06번 §6.2 5개 심볼 화이트리스트) 상관계수 사전
     계산 테이블로 Draft 구현 가능.
  8. **Trade Frequency** (`trade_frequency.anomaly_multiplier=3.0`):
     이 실행의 최근 1시간 거래 횟수가 직전 24시간 평균의 3배 초과 →
     거부(Griefing/오탐 신호 폭주 방어).
  9. (8개 지표 외) **안전장치 상태 확인** — `system_safety_state.
     circuit_breaker_level`이 `restricted` 이상이면 거부(8.6-B Kill
     Switch 우선순위, Watchdog/Circuit Breaker가 Human보다 우선),
     해당 실행이 이미 `paused_by='SAFETY_LAYER'`면 거부.
- **출력**: `RiskCheckResult{approved, rejection_reason, checked_rules}`
  — `checked_rules`에는 실제로 끝까지 확인한 규칙명만 담는다(단락
  평가로 스킵된 나머지는 포함 안 함 — 감사 시 "어디서 막혔는지"가
  명확해야 함).
- **예외 상황**: 8개 지표 중 하나라도 계산에 필요한 데이터 자체가
  없음(예: VaR 계산할 과거 데이터 부족) → **거부**(판단 불가를 승인으로
  취급하지 않는다 — Master Authority의 핵심 원칙, FD-9.1과 동일
  기조지만 여기서는 훨씬 엄격하게 적용).
- **완료조건**: 8개 지표 각각 단독으로 거부를 유발하는 단위테스트,
  Circuit Breaker RESTRICTED 이상 상태에서 다른 7개 지표를 전부
  통과해도 거부되는지, 데이터 부족 시 거부(승인 아님) 확인.
- **관련 스펙**: 03번 §3.7, `risk_policy.yaml`, FD-9.4(Circuit
  Breaker), FD-16.1
- **작업 트리 매핑**: 신규 "8.3 RiskEngine — 8개 지표 순차 검사"

### FD-8.4 주문 실행 트리거

- **목적**: 승인된 `AllocationDecision`+`RiskCheckResult`만 받아 FD-4를
  호출한다. **판단하지 않는다** — `risk_result.approved=False`인 건이
  이 함수에 도달하면 그 자체가 상위 로직 버그(방어적 assert 유지, 03번
  §3.8 그대로).
- **트리거**: FD-8.3이 `approved=True`를 반환한 직후.
- **입력**: `AllocationDecision`, `RiskCheckResult`, `ExchangeAdapter`
  (해당 실행의 `CredentialResolver.get_adapter()` 산출물, `demo_mode=
  True` 고정 — PAPER 개방 범위).
- **처리 단계**:
  1. `mode != 'PAPER'`이면 `FrozenZoneLiveModeBlockedError` 즉시 발생
     (ADR-2026-08-29-E 하드 가드, 이 assert가 이 leaf의 핵심 완료조건).
  2. `Order` 객체 구성(symbol, side, quantity=`approved_quantity`,
     type=`MARKET`, `client_order_id`=`{execution_id}:{fsm_state}:
     {전이 시각}` — FD-4.2-a 멱등성 키로 재사용 가능한 형태).
  3. FD-4.1(`Validator.validate_order_params`) 호출 → 실패 시 CRITICAL
     로그(상위에서 만든 Allocation이 형식 자체를 위반했다는 뜻이라
     Executor가 아니라 FD-8.2 버그).
  4. FD-4.2(`place_order` 전체 파이프라인) 호출.
  5. 체결 성공 시(`Order.status=FILLED`) `fsm_state`를 다음 상태로
     전이(`BUY_ORDER_PENDING→HOLDING` 등, FD-8.0) — 이게 "ORDER_FILLED"
     예약 리터럴 전이가 실제로 반영되는 유일한 지점.
- **출력**: `Order`(최종 상태 반영)
- **예외 상황**: FD-4.2가 `REJECTED`/`RetryableExchangeError` 반환 →
  `fsm_state`를 되돌리지 않는다(진입 시도 자체가 실패했으니 여전히
  이전 상태) + `watchdog.decision.triggered`류와 무관하게 이 실행
  단위로 CRITICAL 로그(반복 실패 시 FD-9.2 Watchdog가 별도로 감지).
- **완료조건**: PAPER 모드로 Bitget Demo 계정 실제 주문 1건 왕복 성공
  (FD-4.2 완료조건과 동일 건으로 겸용 충족), LIVE 모드 지정 시
  `FrozenZoneLiveModeBlockedError` 100% 발생 확인(단 하나의 예외도
  없어야 함 — 이 leaf의 회귀테스트 최우선 항목).
- **관련 스펙**: 03번 §3.8, FD-4.1~4.2, ADR-2026-08-29-E
- **작업 트리 매핑**: 신규 "8.4 Executor — PAPER 전용 하드가드 포함"

## FD-9 안전장치 계층 (SCAFFOLD — Zone 재분류)

> **재분류 근거**: 이전 버전에서 이 기능군을 FD-8과 함께 FROZEN으로 묶었으나, 이는 "매매 판단(사고 팔지 얼마나)"과 "위험 감시(지금 안전한지)"를 혼동한 것이다. 안전장치는 **매매 의사결정을 하지 않는다** — 시장/시스템 상태를 감시하고 필요시 정지·경보만 한다. 06번 §6.3 Definition of Done이 "Watchdog 시뮬레이터를 Phase 1에 실행"을 요구하는 것과도 이 재분류가 일치한다. 아래는 v3.1 정책문서(8.6-A~8.6-A-1-2, 8.6-B, 8.1-A, 8.4)의 실제 판단 로직을 함수 수준으로 구체화한 것이다 — 이제부터 "FROZEN이라 나중에"가 아니라 **지금 설계·구현 대상**이다.

### FD-9.1 Watchdog 손실·응답불능 감시

- **목적**: 계좌 손실률과 메인 프로세스 응답성을 독립적으로 상시 감시한다.
- **트리거**: 별도 프로세스(정책문서 8.6-A "메인과 완전 격리된 독립 헬스체크 프로세스")로 상시 루프, Draft 주기 5초.
- **입력**: `account_state`(FD-3.2/3.3로 조회), 메인 프로세스 heartbeat(별도 IPC/파일 타임스탬프)
- **처리 단계**:
  1. 계좌 손실률 계산: `(peak_equity - current_equity) / peak_equity`, 5분 롤링 윈도우(`risk_policy.yaml`의 `watchdog.window_min`)
  2. 메인 프로세스 마지막 heartbeat로부터 경과 시간 계산
  3. FD-3.5(헬스체크)로 **거래소 API 자체의 독립 응답성**도 함께 확인 — Reconciliation(FD-9.6)에만 의존하지 않는다(정책문서 8.6-A-1-2 원칙)
- **출력**: `WatchdogSnapshot { loss_pct, unresponsive_sec, exchange_healthy: bool }`
- **예외 상황**: `account_state` 조회(FD-3.2/3.3) 자체가 실패 → 마지막으로 확인된
  값을 유지하되 `exchange_healthy=False`로 표기(FD-3.5 헬스체크 결과 반영) —
  조회 실패를 "손실 없음"으로 오판하지 않는다.
- **완료조건**: 강제로 메인 프로세스를 정지시켰을 때 Watchdog(별도 프로세스이므로 계속 동작)이 `unresponsive_sec` 증가를 정확히 관측.
- **관련 스펙**: 정책문서 8.6-A
- **작업 트리 매핑**: 신규 리프 "9.1 Watchdog 프로세스 골격" 필요(§하단 갱신)

### FD-9.2 Watchdog 정지/청산 판정

- **목적**: FD-9.1의 관측치를 바탕으로 정지(Halt)만 할지 강제청산까지 할지 판정한다(정책문서 8.6-A-1, 3차 레드팀 반영 — 안전장치의 강제청산 자체가 시장충격을 만들 수 있다는 발견).
- **트리거**: FD-9.1 관측 주기(5초)마다 자동 판정, 또는 FD-9.6 에스컬레이션이
  "신규주문 전면중지"를 통보한 직후 즉시 재판정.
- **입력**: `WatchdogSnapshot`, `risk_policy.yaml`의 `watchdog` 섹션(loss_threshold_pct=7.0, unresponsive_sec=30)
- **처리 단계(의사코드)**:
  ```
  if snapshot.unresponsive_sec >= 30 and snapshot.loss_pct < 7.0:
      → HALT만 (신규주문 중단, 기존 포지션 유지)
  elif snapshot.loss_pct >= 7.0:
      # 5차 레드팀 반영 — Griefing 방어: 시장 전체와 상관성 확인(FD-2.6 결과 참조)
      if FD-2.6 결과가 "시장 전체 급변과 상관됨":
          → 청산 진행, 8.3-A Smart Order Routing(TWAP) 가용 시 우선 적용,
            **Phase 1은 SOR 미구현(06번 §6.4 "VWAP/Iceberg/SOR 등 고급 주문
            실행 전략" 명시적 제외 대상)이므로 즉시 시장가 청산으로 폴백**
            ("DevEngine 비교 검토" 라운드에서 발견 — FD-9.2가 Phase 1 제외
            기능에 암묵적으로 의존하던 구조적 모순, 정책문서 8.6-A-1 원문의
            "유동성 급감으로 분할 실행이 불가능한 경우 즉시 시장가 청산"
            조항이 이미 이 폴백을 정당화함 — SOR 부재도 "분할 실행 불가능"의
            한 형태로 해석)
      else:  # 고립된 손실 = 조작 의심
          → 신규진입만 즉시 HALT, 기존 포지션 청산은 추가 확인(짧은 지연) 후 결정
  else:
      → 정상
  ```
- **출력**: `WatchdogDecision { action: HALT | LIQUIDATE | NORMAL, reason: str }` → `audit_log`(FD-7.2) 즉시 기록
- **예외 상황**: FD-2.6(시장 전체 상관성 판단) 자체가 데이터 부족으로 판정 불가한
  경우 → 안전한 쪽(고립된 손실=조작 의심)으로 기본값 처리 — 판단 불가를
  "정상"으로 취급하지 않는다.
- **완료조건**: 8.6-A-1-1 시뮬레이터(10번 문서 "9.7 Watchdog 오탐 검증 시뮬레이터"
  리프 — 재점검 라운드에서 "FD-9.7"로 잘못 참조되던 것을 정정. 이 시뮬레이터는
  런타임 기능이 아니라 20.1-A Go/No-Go 게이트용 배포전 검증 도구라 정식 FD로
  승격하지 않고 10번 작업트리에만 리프로 남겨둔다)로 과거 Flash Crash 데이터
  재생 시 FP<1%/FN=0% 측정.
- **관련 스펙**: 정책문서 8.6-A-1, 5차 레드팀(17.8)
- **작업 트리 매핑**: 신규 리프 "9.2 Watchdog 판정 로직"

### FD-9.3 Split-Brain 실패도메인 진단

- **목적**: State DB 연결 단절과 메인 프로세스 장애를 구분한다(정책문서 8.6-A-1-2, 8차 레드팀 발견 — 인프라 레벨 최초 결함).
- **트리거**: FD-9.1과 동일 주기(5초), Watchdog 루프 내에서 판정 직전 단계로 실행.
- **입력**: 없음(FD-3.5, heartbeat, DB 연결상태를 매 사이클 자체 조회)
- **처리 단계(의사코드)**:
  ```
  exchange_ok = FD-3.5()  # 거래소 API 직접 헬스체크, DB와 무관
  main_process_ok = heartbeat 확인
  db_ok = DB 연결 확인

  if exchange_ok and main_process_ok and not db_ok:
      → "State DB 단독 장애" 진단 — 강제청산 대상에서 제외, 신규주문만 보류
      → 거래소 API 응답을 잠정 진실 소스로 취급
  elif not exchange_ok or not main_process_ok:
      → FD-9.2 기존 판정 그대로 적용
  ```
  히스테리시스(9차 레드팀 반영): 장애판정 진입은 3초 연속 확인, 정상복귀 판정은 10초 연속 확인(비대칭) — 정확한 수치는 외부 비공개(정책문서 8.6-A-2 원칙과 동일하게 예측가능성 제거).
- **출력**: `FailureDomain { db_ok, exchange_ok, main_process_ok, diagnosis: str }`
  — FD-9.2에 전달되어 최종 판정에 반영
- **예외 상황**: 세 확인(exchange_ok/main_process_ok/db_ok) 중 판정 로직 자체가
  타임아웃되는 경우(예: DB 확인 쿼리가 응답 없이 걸림) → 해당 값을 `False`로
  간주(응답 없음=장애 의심, 낙관적으로 `True` 취급하지 않음).
- **완료조건**: DB만 강제로 차단했을 때 강제청산이 발동하지 않고 신규주문만 보류되는지 확인.
- **관련 스펙**: 정책문서 8.6-A-1-2
- **작업 트리 매핑**: 신규 리프 "9.3 Split-Brain 진단기"

### FD-9.4 Circuit Breaker 4단계 상태전이

- **목적**: API 오류율·데이터 지연·주문거부율 등을 근거로 정상→경고→거래제한→거래중지→긴급정지 단계를 관리한다.
- **트리거**: FD-6.3(Handler 에러) 재시도 소진, FD-9.6 에스컬레이션, 또는 관측
  지표(오류율 등) 갱신마다 상시 재평가.
- **입력**: API 오류율, 데이터 지연(초), 주문거부율, Daily Loss(FD-8.3 결과 참조 가능하나 이 계층 자체는 매매판단 안 함)
- **처리**: `risk_policy.yaml`의 `circuit_breaker` 섹션 임계치(07번 §7.2)를 그대로
  사용한 단순 상태기계 — 각 단계 진입조건 충족 시 상향은 자동. **하향은 단계별로
  다르게 처리한다(재점검 라운드 정정 — 정책문서 §8.6-B "재가동은 절대
  자동화하지 않는다 — 특히 Level 3(Circuit Breaker) 이상 트리거는 인간의
  명시적 재가동 승인을 거친다"를 지금까지 위반하고 있었음을 발견)**:
  - `warning`(경고): 조건 미충족 지속 시 자동 하향 허용(진동 방지 목적의
    지연 하향, 기존 설계 유지)
  - `restricted`(거래제한): 자동 하향 허용(경고와 동일 수준 리스크)
  - `halted`(거래중지)/`emergency`(긴급정지): **자동 하향 절대 금지** —
    조건이 완화돼도 상태는 그대로 유지되며, FD-10.1과 동일한 패턴의
    "재가동 승인 요청"을 인간에게 생성해야만 정상 단계로 복귀 가능. Circuit
    Breaker 재가동은 사용자 개인 계정 문제가 아니라 시스템 신뢰성 문제이므로
    **플랫폼 레벨 승인 대상으로 확정**(ADR-2026-08-10-D §②
    결정유형 목록에 이미 등재 — 승인권자 1인 체제, 180초 강제대기,
    5개 질문 가이드라인 적용)
- **출력**: `CircuitBreakerLevel` 변경 시 `risk.circuit_breaker.level_changed`
  이벤트 발행(FD-6.1, 05번 §5.3 원문 그대로 — 재점검 라운드에서 "risk." 접두어
  누락 발견해 정정). `halted`/`emergency`에서 재가동 승인이 생성되면
  `risk.circuit_breaker.reactivation_requested` 이벤트도 함께 발행(FD-17
  알림 대상 — 재점검 라운드 추가, 강제 채널로 분류 필요).
- **예외 상황**: 여러 지표가 동시에 서로 다른 단계를 가리키는 경우(예: 오류율은
  '경고', 지연은 '거래중지') → **가장 높은(위험한) 단계를 채택**(다수결이나
  평균이 아니라 최댓값 — 안전장치는 항상 보수적으로). **halted/emergency
  상태에서 재가동 승인 대기 중에 조건이 오히려 더 악화되는 경우** → 대기중인
  재가동 요청을 자동 취소하고 상태를 유지(악화된 상태로 재가동되는 경로
  원천 차단).
- **완료조건**: warning/restricted는 조건 완화 시 자동 하향 확인.
  **halted/emergency는 조건이 완화돼도 인간 승인 없이는 하향되지 않음을
  확인**(안전 원칙 실증 — 이번 정정의 핵심 테스트).
- **관련 스펙**: 정책문서 8.6, 8.6-B, FD-10.1
- **작업 트리 매핑**: 신규 리프 "9.4 Circuit Breaker 상태기계", 신규 리프
  "9.4b 재가동 승인 워크플로"(FD-10.1과 유사 패턴 재사용)

### FD-9.4b Circuit Breaker 재가동 승인 워크플로 (신규 — "0번부터 재검토" 라운드, 언급만 되고 정의 없던 것 발견)

> 근거: FD-9.4가 "halted/emergency는 자동 하향 금지, 인간의 명시적 재가동
> 승인 필요"라고 정정하면서 작업트리 매핑에 "신규 리프 9.4b"라고 언급했으나,
> 정작 이 세부기능 자체가 정식으로 작성된 적이 없었음 — FD-9.4b가 "참조는
> 있는데 정의 없는" 이전 라운드들과 동일한 패턴으로 재발.

- **목적**: `halted`/`emergency` 상태의 Circuit Breaker를 조건 완화만으로
  자동 복귀시키지 않고, 인간의 명시적 재가동 승인을 거치게 한다.
- **트리거**: FD-9.4에서 `halted`/`emergency` 상태 진입 후, 하향 조건(임계치
  미충족 지속)이 처음 충족되는 시점 — 이 시점에 자동 하향 대신 재가동
  승인 요청을 생성.
- **입력**: `circuit_breaker_level`(현재 단계), `trigger_metrics`(하향 조건이
  충족된 근거 지표 스냅샷)
- **처리**: FD-10.1과 동일한 패턴 재사용 — `ApprovalService.create_request()`
  호출(`trigger_source="circuit_breaker_reactivation"`), **180초 강제대기**
  (ADR-2026-08-10-D §③ 확정 — 플랫폼 레벨은 사용자 레벨 60초 하한보다
  엄격하게, FD-9.2/FD-10.1의 저유동성 시간대 강화값 재사용), **플랫폼
  레벨 승인으로 확정**(ADR-2026-08-10-D §① 5개 질문 가이드라인 적용 —
  이 승인은 그중 질문4 "FROZEN Zone 개방 아님", 질문5 "되돌릴 수 있음"에
  해당해 경고 없이 진행 가능한 유형). 승인 완료 시 `CircuitBreakerLevel`을
  정상 단계로 전이.
- **출력**: 승인 완료 시 `{circuit_breaker_level: "normal", reactivated_at}`,
  대기 중에는 `{status: "PENDING_REACTIVATION_APPROVAL"}`
- **예외 상황**: 승인 대기 중 조건이 재악화(지표가 다시 임계치를 넘음) →
  대기 중인 재가동 요청을 자동 취소, halted/emergency 상태 유지(FD-9.4
  예외상황과 동일 원칙 — 악화된 상태로 재가동되는 경로 원천 차단).
- **완료조건**: halted 상태에서 조건이 완화돼도 승인 없이는 자동 복귀하지
  않음을 확인, 재가동 승인 완료 시 정확히 normal 단계로 전이함을 확인,
  대기 중 재악화 시 요청이 자동 취소됨을 확인.
- **관련 스펙**: 정책문서 8.6-B, FD-9.4, FD-10.1, ADR-2026-08-10-D
- **작업 트리 매핑**: 신규 리프 "9.4b 재가동 승인 워크플로"

### FD-9.5 Data Distrust Mode 판정

- **목적**: FD-2.6에서 이미 다룬 히스테리시스 로직을 시스템 상태로 승격 — 6차 레드팀이 지적한 다중 오라클 동시 스푸핑 방어(쿼럼)까지 포함해 완성한다.
- **트리거**: FD-2.6 판정 결과가 갱신될 때마다(신규 시세 수신 시).
- **입력**: 3개 이상 Reference 소스의 최근 시세 캐시
- **처리**: FD-2.6(2소스 비교) → 6차 레드팀 반영 확장 — **Reference 소스 최소 2개 이상(총 3소스 쿼럼), 중앙값 비교** + 피드 비교와 무관한 통계적 타당성 검사(실현변동성 대비 표준편차 5배 초과 여부)를 병행, 둘 다 "이상없음"이어야 정상 유지.
- **출력**: `DataDistrustLevel`(정상/의심/불신) 변경 시 이벤트 발행(FD-6.1),
  FD-8(FROZEN) 신규 진입 판단이 이 값을 참조.
- **예외 상황**: 3소스 중 2개 이상이 동시에 조회 실패(스푸핑이 아니라 순수
  인프라 장애) → 쿼럼 자체가 성립하지 않으므로 "판정 불가" 상태로 별도 분류,
  자동으로 "정상"이나 "불신" 어느 쪽으로도 단정하지 않고 FD-9.6 에스컬레이션.
- **완료조건**: 3소스 중 1개만 왜곡됐을 때(중앙값은 정상 유지) 오탐 없이 정상 판정, 2개 이상 동시 왜곡 시 Distrust 진입 확인.
- **관련 스펙**: 정책문서 8.1-A
- **작업 트리 매핑**: 5.11(기존 리프 확장 — 단일 소스 비교에서 쿼럼으로)

### FD-9.6 Reconciliation 불일치 에스컬레이션

- **목적**: 내부 상태와 거래소 실제 상태의 불일치를 감시하고 반복 시 단계적으로 대응을 격상한다.
- **트리거**: FD-3.3/3.4(포지션·주문 조회)와 내부 DB 상태를 비교하는 매 정기
  Reconciliation 사이클(Draft: 1분 간격).
- **입력**: 내부 `orders`/`positions` 최신 스냅샷, 거래소 실제 조회 결과(FD-3.3/3.4)
- **처리(의사코드)**:
  ```
  1회 불일치 → 자동 Recovery(재조회), 신규주문 일시보류
  동일자산 1시간 내 3회 이상 → Circuit Breaker '거래제한' 단계로 자동 승격
  24시간 내 5회 이상 또는 단일 불일치가 포지션의 10% 초과 → 신규주문 전면중지 + RCA 강제
  ```
- **출력**: `reconciliation_events` 테이블(04번) INSERT, 격상 시 FD-9.4/FD-10.1
  트리거
- **예외 상황**: 불일치가 계속 반복되는데 원인이 특정되지 않는 경우(RCA 강제
  이후에도 재발) → 자동 대응을 더 격상하지 않고 사람이 직접 개입할 때까지
  "신규주문 전면중지" 상태를 유지(자동화가 스스로 판단을 확대하지 않는다,
  8.2-A Master Authority 원칙과 동일 정신). **"신규주문 전면중지"에서 정상
  복귀하는 절차(재점검 라운드 추가 — 지금까지 명시된 적 없었음)**: FD-9.4b
  (Circuit Breaker 재가동 승인 워크플로)를 그대로 재사용 — 이 상태도 조건이
  완화됐다고 시스템이 자동으로 재개하지 않고, 인간의 명시적 재가동 승인을
  거쳐야 한다(8.6-B "재가동은 절대 자동화하지 않는다" 원칙, FD-9.4 정정과
  동일 근거).
- **완료조건**: `reconciliation_events` 테이블(04번)에 인위적 불일치를 반복 삽입했을 때 정확한 임계치에서 단계 격상 확인. **전면중지 상태가 조건 완화만으로는 자동 해제되지 않고 재가동 승인을 거쳐야 함을 확인.**
- **관련 스펙**: 정책문서 8.4, 8.6-B, FD-9.4b
- **작업 트리 매핑**: 신규 리프 "9.6 Reconciliation 에스컬레이션 로직" (3.8 테이블 이후)

## FD-10 인간 승인 흐름 (SCAFFOLD — 상호작용 패턴)

> Phase 1에는 실거래 자금 규모가 작아 Critical Risk 승인이 자주 발생하지 않을 수 있지만, **패턴 자체는 지금 구현해야** 나중에 FROZEN Zone이 열렸을 때 바로 연동된다.
> **재점검 라운드 정정(ADR-2026-08-10 반영)**: 아래 트리거(FD-9.2/FD-9.6/FD-16.2)는 전부
> 특정 사용자의 계정·실행에 대한 판단이므로 **사용자 레벨** Critical Risk 승인이다
> — 정책문서 4.9가 이미 사용자 레벨은 1인(SOLO) 단독 승인을 허용하고 있고
> (FD-11.3 ApprovalMode), 이 부분은 20.1-B의 "승인권자 2인 미해결" 블로커와
> 무관하다(그 블로커는 시스템 전체 Kill Switch·DevEngine 거버넌스 같은
> **플랫폼 레벨**에만 해당 — ADR-2026-08-10-D로 정식 확정됨, 舊 ADR-2026-08-10은 Superseded). 아래
> "서로 다른 인증계정의 순차 서명"은 사용자가 FD-11.3에서 DUAL 모드를 선택한
> 경우에만 적용되고, SOLO 모드에서는 본인 1인 확인만으로 충분하다.

### FD-10.1 Critical Risk 승인 요청 생성

- **목적**: FROZEN 판단 계층(FD-8)이나 안전장치(FD-9)가 Critical Risk로 분류한
  결정을 즉시 실행하지 않고 인간 승인을 거치도록 요청을 생성한다.
- **트리거**: FD-9.2(Watchdog LIQUIDATE 판정), FD-9.6(Reconciliation 전면중지
  격상), 또는 FD-16.2(고배분 LIVE 실행 시작)에서 8.2-B 임계치 초과 시.
- **입력**: `trigger_source`(어느 하위 시스템의 요청인지), `context`(판단 근거
  스냅샷 — 재현·감사 목적), `requested_action`
- **처리**: 요청 생성 시 60초 타이머 시작(버튼 비활성화). FD-11.3
  ApprovalMode가 SOLO면 본인 1인 확인, DUAL이면 서로 다른 인증계정의 순차
  서명 요구(위 헤더 정정 참조).
- **출력**: `approval_request_id`, `status: PENDING`, `expires_at`(60초 후 —
  응답 없으면 기본값은 "거부"로 fail-safe, 4.9-A 원칙)
- **예외 상황**: 타이머 만료까지 아무 승인권자도 응답하지 않음 → 요청 자동
  거부 처리, `requested_action`은 실행되지 않음(암묵적 승인 없음).
- **완료조건**: SOLO 모드로 본인 1인 승인 시 즉시 테스트 가능(사용자 레벨은
  20.1-B 블로커와 무관), DUAL 모드는 Mock 승인자 2개 계정으로 테스트, 60초
  미응답 시 자동 거부 확인.
- **관련 스펙**: 정책문서 4.9-A, FD-11.3, ADR-2026-08-10
- **작업 트리 매핑**: 신규 리프 "10.1 승인 요청 워크플로"

### FD-10.2 SURGE 모드 판정 및 배치승인

- **목적**: 단일 시장 이벤트로 승인 요청이 폭증할 때, 승인권자가 개별 검토에
  매몰돼 정작 각 요청을 제대로 못 보는 상황을 막는다.
- **트리거**: FD-10.1 요청 생성 빈도가 10분 내 평소 대비 5배 이상 급증할 때
  자동 감지.
- **입력**: 급증 구간의 승인 요청 목록, 각 요청의 `Trigger Provenance`(요청이
  어느 시스템 상태 변화에서 파생됐는지 태그)
- **처리**: 10분 내 요청 5배 급증 시 SURGE 진입 → Trigger Provenance 필드로 요청 근원 확인 → **Kernel이 8.1-A/8.6 실제 상태와 대조해 독립 재검증**(Agent 자기주장 불신 원칙, 7차 레드팀) → 검증된 단일 이벤트 파생 요청군만 배치승인, 나머지는 개별 SURGE 절차.
- **출력**: 배치승인 대상 그룹과 개별 검토 대상 그룹으로 분리된 목록
- **예외 상황**: Trigger Provenance 태그가 시스템 실제 상태와 대조해 근거를
  찾을 수 없는 경우(위조·오류 의심) → 배치승인 대상에서 자동 제외, 최하위
  신뢰도로 개별 절차에 편입(의심스러운 요청을 자동으로 묶어서 넘기지 않는다).
- **완료조건**: 가짜 Provenance 태그(시스템 상태상 근거 없음) 주입 시 배치승인 거부하고 최하위 신뢰로 분류되는지 확인.
- **관련 스펙**: 정책문서 4.9-A, 6·7차 레드팀
- **작업 트리 매핑**: 신규 리프 "10.2 SURGE 판정기"

### FD-10.3 비상 출금 패닉 프롬프트

- **목적**: 카운터파티(거래소) 리스크 등 심각 신호 발생 시, 사용자가 신속하게
  자금을 안전한 곳으로 옮기도록 안내하되 그 프롬프트 자체가 공격 경로가
  되지 않게 한다.
- **트리거**: 카운터파티 리스크 심각 신호(정책문서 7.10-A 정의) 감지 시.
- **입력**: FD-11.5로 사전 등록된 출금 목적지 화이트리스트(정책문서 7.10-A,
  평상시 등록 — 정책문서 20.1-B에서 이미 "위기 이전 준비"로 확정, "다시
  0번부터" 라운드에서 이 화이트리스트를 채우는 FD-11.5를 신설해 연결함),
  최소 2개 독립 소스의 corroboration 결과
- **처리**: 심각 신호(카운터파티 리스크) 감지 시 사전 등록된 화이트리스트 목적지만으로 프롬프트 생성, 최소 2개 독립 소스 corroboration 확인 후에만 신속경로 활성화.
- **출력**: 화이트리스트 목적지 중 선택 가능한 패닉 프롬프트 화면(신규 목적지
  입력 필드 자체가 존재하지 않음)
- **예외 상황**: corroboration 소스가 1개뿐이거나 서로 모순되는 경우 → 신속경로
  활성화하지 않고 일반 승인 절차(FD-10.1)로 격하 — 확실하지 않은 상황에서
  "빠른 길"을 열어주지 않는다.
- **완료조건**: 목적지 화이트리스트 외 주소로는 프롬프트 자체가 생성되지 않음을 확인(시스템 레벨 제약 — Agent 권한 밖).
- **관련 스펙**: 정책문서 7.10-A
- **작업 트리 매핑**: 신규 리프 "10.3 패닉 프롬프트 생성기"

## FD-11 사용자 인증 및 계정관리 (신규 — v1.0)

> 근거: 정책문서 4.10(멀티테넌시 아키텍처), 개발명세서 13번 §13.2

### FD-11.1 회원가입/로그인

- **목적**: 사용자 계정 생성 및 인증.
- **트리거**: 프론트엔드의 명시적 가입/로그인 요청.
- **입력(가입)**: `email`, `password`
- **입력(로그인)**: `email`, `password`, (MFA 활성 시) TOTP 코드
- **처리 단계(가입)**:
  1. email 중복 확인
  2. 비밀번호 강도 검증(Draft: 최소 12자 + 대소문자·숫자·특수문자)
  3. Argon2id 해시 후 `users` 테이블 INSERT
  4. 확인 이메일 발송(Draft — 실제 발송 인프라는 착수 시 확정)
  5. 가입 완료 직후 프론트엔드가 FD-11.2(MFA 설정, 필수)로 강제 리다이렉트,
     MFA 완료 후에만 FD-15.1(적합성평가 설문)로 다음 리다이렉트(재점검
     라운드 정정 — MFA가 선택에서 필수로 바뀌면서 온보딩 순서에 삽입해야
     했으나, 애초에 FD-15.1 쪽에서만 "FD-11.1 직후"라고 참조하고 FD-11.1
     자신은 이 흐름을 언급한 적이 없어 단방향 참조였던 문제도 함께 발견.
     17번 프론트엔드 문서 §17.3의 `/onboarding/risk-assessment` 라우팅 가드가
     실제로는 그 앞에 MFA 설정 화면 경유를 먼저 거치도록 갱신 필요)
- **처리 단계(로그인)**:
  1. email로 사용자 조회
  2. 비밀번호 해시 비교
  3. `mfa_enabled=true`면 TOTP 코드 검증(FD-11.2)
  4. 세션 토큰(Draft: JWT) 발급, `last_login_at` 갱신
- **출력**: 세션 토큰 또는 인증 실패
- **예외 상황**:
  - 존재하지 않는 email → "이메일 또는 비밀번호가 올바르지 않습니다"로 일반화(계정 존재 여부 노출 방지 — 계정 열거 공격 차단)
  - 연속 로그인 실패(Draft: 5회) → 계정 임시 잠금(Draft: 15분) — 4.9 MFA와 별개의 무차별 대입 방어
  - `status='SUSPENDED'/'DELETED'` 계정 로그인 시도 → 일반화된 실패 메시지로 통일(보안상 사유 비노출 검토)
- **완료조건**: 정상 가입→로그인 왕복 성공, 5회 연속 실패 시 계정 잠금 확인, 잠긴 계정은 올바른 비밀번호로도 로그인 거부됨을 확인.
- **관련 스펙**: 13번 §13.2(users 테이블), 11번(보안 원칙)
- **작업 트리 매핑**: 신규 "11.1 인증 API"

### FD-11.2 MFA 설정 (필수 — "0번부터 재검토" 라운드 정정)

> **정정(재점검 라운드)**: 정책문서 §4.10 "교차 테넌트 리스크 3"이 "승인권자
> 2인 요건이 사용자 레벨에서는 자율화됐지만... MFA는 사용자 레벨에서도
> **예외 없이 강제한다**(자율화 대상은 '승인자 수'이지 '인증 강도'가 아니다)"
> 라고 명시하는데, 기존 서술은 "사용자가 보안 설정에서 활성화"라는 **선택
> 사항**으로 설계돼 있었음 — 정책 원문과 명백히 어긋나 정정.

- **목적**: TOTP 기반 2단계 인증을 **필수로** 활성화시킨다(선택 아님).
- **트리거**: FD-11.1 회원가입 직후, MFA 설정 완료 전까지 다른 온보딩 단계
  (FD-15.1 적합성평가 등)로 진행 불가 — 강제 게이트.
- **입력**: 없음(활성화 요청 자체), 검증 단계에서 `totp_code`(사용자가 인증앱에서
  확인한 6자리 코드)
- **처리**: TOTP secret 생성 → QR코드로 표시(Draft) → 사용자가 인증앱에 등록 후 코드 1회 검증 → `mfa_secret` 암호화 저장, `mfa_enabled=true`.
- **출력**: QR코드 이미지(secret 임베딩), 검증 성공 시 `{mfa_enabled: true}`
- **예외 상황**: 검증 코드 불일치 → `mfa_secret`을 저장하지 않고 폐기(반쯤
  활성화된 상태로 남기지 않음 — 활성화는 all-or-nothing). **MFA 설정을
  건너뛰고 다른 기능(거래소 연동 등) 접근 시도 → 403 + MFA 설정 화면으로
  강제 리다이렉트**(재점검 라운드 추가 — 선택사항이었을 때는 이런 차단이
  없었음).
- **완료조건**: 활성화 후 로그인 시 TOTP 코드 없이는 로그인 실패 확인.
  **MFA 미설정 상태에서 다른 API 호출 시도 시 전부 403으로 차단됨을 확인**
  (재점검 라운드 추가 — "예외 없이 강제"의 실증).
- **관련 스펙**: 13번 §13.2, 정책문서 §4.10 교차테넌트 리스크3
- **작업 트리 매핑**: 신규 "11.2 MFA 설정(필수 게이트)"

### FD-11.4 회원탈퇴 (신규 — v1.1)

> 근거: FD-11이 가입·로그인·MFA·승인설정만 다루고 탈퇴가 없었음을 확인(2026-08-10
> 비전 대조 갭리뷰). **법적 구속력 있는 개인정보 파기 기준(보존기간 등)은 19.4
> 법률검토 대상 — 여기서는 "탈퇴 시 진행중인 실행을 어떻게 처리할지"라는 기능적

- **트리거**: 설정 화면의 "회원탈퇴" 액션.
- **입력**: `password`(재인증 — 세션이 탈취된 상태에서 탈취범이 탈퇴를 악용하지

  1. **진행중인 RUNNING 실행(FD-16) 존재 여부 확인** — 존재 시 탈퇴 즉시 처리

     물리 삭제 아님 — 8.10 감사 원칙과 동일하게 유예기간 둠, Draft: 30일)
  3. 유예기간 중 재로그인 시 탈퇴 취소 가능(Draft)
  4. 유예기간 경과 후 실제 파기 절차는 19.4 법률검토 결과에 따라 확정(지금은
     Draft로 "PII 익명화, 거래이력은 8.10 감사 목적으로 최소 보존기간 유지"로만
     가정)
- **출력**: `{status: "PENDING_DELETION", deletion_effective_at}`(유예기간 종료일)

- **완료조건**: RUNNING 실행이 있는 상태에서 탈퇴 시도 시 차단 확인, 없는 상태
  에서는 PENDING_DELETION 전이 확인.
- **관련 스펙**: 19.4(법적 파기기준, 보류), FD-16.3, 정책문서 8.10
- **작업 트리 매핑**: 신규 "11.6 탈퇴 API"

### FD-11.5 비상 출금 목적지 화이트리스트 관리 (신규 — "다시 0번부터" 라운드,
FD-10.3이 참조만 하고 등록 기능 자체가 없었음을 발견)

> 근거: FD-10.3(비상 출금 패닉 프롬프트)이 "사전 등록된 출금 목적지
> 화이트리스트"를 입력으로 참조하지만, 정작 그 화이트리스트에 사용자가
> 주소를 등록하는 기능 자체가 어디에도 없었다. 정책문서 20.1-B가 명시한
> "위기 상황이 닥친 뒤에는 등록 자체가 시스템 원칙상 불가능하므로 평상시에
> 미리 등록"이라는 핵심 안전장치가 실제로 강제되려면, "평상시"와 "위기
> 상황"을 구분해서 위기 상황 중 신규 등록을 원천 차단하는 로직이 반드시
> 필요하다.

- **목적**: 사용자가 평상시에 안전한 출금 목적지 주소를 미리 등록해둔다.
- **트리거**: 설정 화면의 "비상 출금 목적지 관리".
- **입력**: `exchange`, `destination_address`, `label`(메모, 예: "본인 콜드월렛"),
  재인증(`password` + MFA 코드 — 자금이 향할 목적지를 정하는 만큼 FD-11.4
  탈퇴보다도 높은 보안 강도 요구)
- **처리**: `withdrawal_whitelist` 테이블(신규, 04번 DB스키마 추가 필요) INSERT
  → `audit_log`(FD-7.2) 기록(누가 언제 어떤 목적지를 등록했는지는 그 자체로
  중요한 감사 대상) → **`security.withdrawal_whitelist.added` 이벤트 발행**
  (FD-17, 강제 채널 — "다시 0번부터" 라운드에서 발견: 계정 탈취 시나리오상
  공격자가 몰래 새 출금 목적지를 등록해도 진짜 사용자가 전혀 모르는 상태가
  될 뻔했음. `approval.request.created`와 동일하게 사용자가 끌 수 없는
  강제 알림으로 분류 — 본인이 등록한 게 아니라면 즉시 알아야 하는 계정
  보안 이벤트이기 때문).
- **출력**: 등록된 목적지 목록
- **예외 상황**: **FD-9(안전장치)가 카운터파티 리스크 심각 신호를 이미 감지한
  "위기 상황" 중에는 신규 등록 시도 자체를 거부**(정책문서 20.1-B 원칙의
  실제 강제 지점 — 위기 상황에서 공격자가 새 목적지를 몰래 등록하고 패닉
  프롬프트를 유도하는 사회공학 공격을 원천 차단). 이 경우 "위기 상황
  중에는 새 목적지를 등록할 수 없습니다. 평상시에 미리 등록해주세요"로
  안내.
- **완료조건**: 평상시 등록 성공, FD-9 위기 상황 플래그가 켜진 상태에서
  등록 시도 시 거부됨을 확인(안전 원칙 실증).
- **관련 스펙**: 정책문서 7.10-A, 20.1-B, FD-10.3, FD-9

## FD-12 사용자별 거래소 연동 (신규 — v1.0)

### FD-12.1 거래소 자격증명 등록/해지

- **목적**: 사용자가 본인 거래소 API 키를 플랫폼에 안전하게 등록.
- **트리거**: "거래소 연동" 화면에서 사용자 요청.
- **입력**: `exchange`, `api_key`, `api_secret`, (KIS의 경우) `app_key`/`app_secret`
- **처리 단계**:
  1. 입력받은 키를 즉시 애플리케이션 레벨 암호화(AES-256-GCM, 07번 §7.3 암호화 키 재사용)
  2. `exchange_credentials` 테이블에 암호화된 값만 저장(평문은 메모리 최소 수명 후 폐기)
  3. **등록 직후 FD-3.2(잔고조회) 1회 테스트 호출로 키 유효성 검증** — 유효하지 않으면 저장하지 않고 즉시 에러 반환
  4. **출금 권한 조회("0번부터 재검토" 라운드 추가) — 거래소가 API 키 권한범위
     조회 엔드포인트를 제공하면 호출해 출금(withdraw) 권한 포함 여부 확인.
     출금 권한이 있으면 저장 자체를 거부**(02번 문서 명시 원칙: "이 Adapter의
     어떤 메서드도 출금 기능을 포함하지 않는다 — Trading Permission ≠
     Withdrawal Permission" — 시스템이 애초에 출금 기능을 쓸 계획이 없으므로
     최소권한 원칙상 출금권한 있는 키를 받아들일 이유가 없음, 유출 시 피해
     범위를 원천적으로 줄임). 거래소 API가 권한범위 조회를 지원하지 않는
     경우(Draft: KIS 등 일부) → 경고 문구로 대체("이 거래소는 권한 자동확인을
     지원하지 않습니다. 반드시 출금 권한이 제외된 키인지 직접 확인해주세요")
- **출력**: 등록 성공/실패
- **예외 상황**:
  - 유효하지 않은 키 → 저장 거부, 구체적 원인 안내(단 시크릿 값 자체는 로그에 남기지 않음, 07번 §7.1 마스킹 원칙)
  - **출금 권한 포함된 키 → 저장 거부**, "거래소에서 출금 권한을 제외하고
    키를 재발급해주세요" 안내(재점검 라운드 추가)
  - 이미 등록된 거래소 재등록 → `UNIQUE(user_id, exchange)` 제약으로 UPDATE(교체) 처리
- **해지 처리**: `revoked_at` 갱신(물리 삭제 아님 — 감사 추적, `audit_log`에 해지 이벤트 기록)
- **완료조건**: 유효한 Bitget Demo 키 등록 성공, 잘못된 키 등록 시도 시 저장되지 않고 명확한 에러, 해지 후 해당 거래소로 신규 주문 시도 시 거부됨을 확인. **출금 권한이 포함된 키로 등록 시도 시 저장이 거부됨을 확인**(신규).
- **관련 스펙**: 13번 §13.3, 07번 §7.3, 02번 문서(출금기능 배제 원칙)
- **작업 트리 매핑**: 신규 "12.1 자격증명 등록 API"

### FD-12.2 자격증명 조회 및 Adapter 인증 연동 (FD-3.1 개정)

- **목적**: FD-3.1(인증)이 "시스템 전역 1세트"가 아니라 **"이 요청의 user_id에 연결된 자격증명"**을 쓰도록 연동.
- **트리거**: 사용자 관련 모든 거래소 API 호출 직전.
- **입력**: `user_id`, `exchange`
- **처리**: `user_id`+`exchange`로 `exchange_credentials` 조회 → 복호화(메모리 내에서만, 로그 노출 금지) → `ExchangeAdapter` 인스턴스 생성/캐싱(Draft: 사용자당 인스턴스를 매 요청 새로 만들지 않고 짧은 TTL로 캐싱).
- **출력**: 인증된 `ExchangeAdapter` 인스턴스(내부 상태, API 응답으로 노출되지 않음)
- **예외 상황**: 자격증명 없음(미등록) → 해당 거래소 관련 기능을 UI에서 비활성화(이 계층까지 요청이 오면 시스템 오류로 취급) / `is_active=false`(해지됨) → 동일 처리.
- **완료조건**: **서로 다른 두 사용자가 동시에 각자의 Bitget 키로 조회했을 때 키가 섞이지 않음**(4.10 멀티테넌시 격리 원칙의 실증 테스트 — 이 테스트가 통과하지 못하면 플랫폼 자체가 성립하지 않는다).
- **관련 스펙**: 02번(FD-3.1 개정 대상), 13번 §13.3
- **작업 트리 매핑**: 6.3/6.9(기존 리프)에 `user_id` 파라미터 추가로 개정

## FD-13 마켓플레이스 (신규 — v1.0, 골격만)

> 리스팅 가격정책·평판시스템 등 완성형 설계는 스콥이 커서 별도 문서(14번, 예정)로 분리. 여기서는 Phase 1 병행 착수에 필요한 최소 골격만 다룬다.

### FD-13.1 전략 리스팅

- **목적**: 사용자가 본인이 만든 전략을 마켓플레이스에 등록(판매 목적).
- **트리거**: 전략 빌더에서 백테스트 완료 후 "마켓플레이스에 등록" 액션.
- **입력**: `strategy_id`, `strategy_version`, `price`
- **처리**: `strategy_listings` INSERT, `status='DRAFT'`(**재점검 라운드 정정**:
  15번 API 문서 §15.5가 이미 `POST /marketplace/listings/{id}/submit-verification`을
  별도 엔드포인트로 두고 있었음을 발견 — 즉시 자동으로 PENDING_VERIFICATION
  진입시키는 게 아니라, 판매자가 가격 등을 다시 검토할 여지를 주고 **명시적으로
  제출**하는 2단계 흐름이 더 합리적이라 판단해 이쪽으로 통일. 이하 FD-13.1b로 분리).
- **출력**: `{listing_id, status: "DRAFT"}`
- **예외 상황**: 이미 3개월 Paper Trading 이력이 없는 전략으로 등록 시도 →
  저장 자체는 허용(DRAFT는 비공개 상태이므로)하되, FD-13.1b(제출) 시점에 거부.
- **완료조건**: 리스팅 생성 시 `DRAFT` 상태로 저장, 아직 검증 대기열(FD-18.1)에
  노출되지 않음을 확인.
- **관련 스펙**: 13번 §13.5, 15번 문서 §15.5
- **작업 트리 매핑**: 신규 "13.1 리스팅 API"

### FD-13.1b 리스팅 검증 제출

- **목적**: 판매자가 DRAFT 상태 리스팅을 검증 대기열로 명시적으로 제출한다.
- **트리거**: "내 리스팅" 화면에서 "검증 요청" 버튼(FD-13.1과 분리된 별도 액션).
- **입력**: `listing_id`
- **처리**: `status: DRAFT → PENDING_VERIFICATION` 전이, FD-18.1 검증 대기열에 노출.
- **출력**: `{listing_id, status: "PENDING_VERIFICATION"}`
- **예외 상황**: 3개월 Paper Trading 이력 미달 시 이 단계에서 거부(FD-13.2
  예외상황과 동일 정신 — 검증 담당자 시간을 아끼기 위해 조기 차단).
- **완료조건**: 제출 시 검증 대기열(FD-18.1)에 실제로 노출됨을 확인, 자격
  미달 리스팅은 제출 자체가 거부됨을 확인.
- **관련 스펙**: 15번 문서 §15.5, FD-18.1
- **작업 트리 매핑**: 신규 "13.1b 검증 제출 API"

### FD-13.2 전략 검증 (9.5-A 연동, MVP 수동검증 브릿지)

- **목적**: 정책문서 9.5-A(Certified Badge) + v3.2 신설 "MVP 수동검증 브릿지" — Black/Killer Team 자동화(Phase 4 의존)가 아직 없으므로 플랫폼 운영자가 동일 기준으로 수동 검증.
- **트리거**: FD-13.1b에서 `status='PENDING_VERIFICATION'` 진입 시 자동 큐잉(FD-18.1
  검증 대기열에 노출).
- **입력**: `listing_id`, 검증담당자의 체크리스트 결과, `decision`(APPROVE/REJECT)
- **처리 단계**:
  1. 검증 담당자(플랫폼 운영자)에게 검증 요청 알림(`audit_log` 이벤트로 기록)
  2. 담당자가 오버피팅·Look-ahead Bias·Survivorship Bias 체크리스트 확인(9.5 Black/Killer Team과 동일 항목)
  3. 3개월 Paper Trading 이력 확인(9.5-A 원칙 — MVP도 동일 기간 요구, 단축하지 않음)
  4. 통과 시 `status='LISTED'`, 거부 시 `'DRAFT'`로 반려(사유 기록)
- **출력**: `{listing_id, status: LISTED|DRAFT, rejection_reason?}`
- **예외 상황**: 3개월 Paper Trading 이력이 부족한 상태로 검증 요청이 들어온 경우
  → 검증 자체를 시작하지 않고 즉시 반려(담당자의 시간을 아끼기 위해 자격
  미달 건을 대기열에서 선별)
- **완료조건**: 검증 담당자 승인 없이는 `status`가 `LISTED`로 전이 불가(DB 트리거 또는 애플리케이션 강제로 이중 방어).
- **관련 스펙**: 정책문서 9.5-A, v3.2 MVP 수동검증 브릿지, FD-18.1
- **작업 트리 매핑**: 신규 "13.2 검증 워크플로"

### FD-13.3 전략 구매

- **목적**: 다른 사용자가 리스팅된 전략을 구매.
- **트리거**: 마켓플레이스 리스팅 상세 화면의 "구매" 버튼.
- **입력**: `listing_id`, (FD-15.3 경고 발생 시) 명시적 동의 플래그
- **처리**: `strategy_purchases` INSERT, `price_paid` 기록(FD-13.7 중개수수료
  계산 포함) → 구매자에게 해당 전략 실행 권한 부여(FD-13.4).
- **출력**: `{purchase_id, status, risk_warning?}`(15번 문서 §15.5 예시 참조)
- **예외 상황**: 본인이 만든 전략을 본인이 구매 시도 → 거부(무의미한 거래, 자전거래 방지 원칙과 연결).
- **완료조건**: 구매 후 buyer가 전략을 조회·실행 가능, 미구매 사용자는 전략 상세 로직 조회 불가(10.3-B 블랙박스 원칙 실증).
- **관련 스펙**: 13번 §13.5, FD-15.3
- **작업 트리 매핑**: 신규 "13.3 구매 API"

### FD-13.4 구매한 전략 실행 연동

- **목적**: 구매자가 이 전략을 본인의 자동매매에 실제로 사용.
- **트리거**: FD-18.5b(결제 확인)에서 `payment_status: CONFIRMED` 전환 직후
  (재점검 라운드 정정 — 이전엔 "FD-13.3 구매 완료 직후"라고 돼 있었으나,
  이러면 입금 확인 전에 실행 권한이 생기는 구멍이 됨), 또는 이후 구매자가
  FD-16(실행 제어판)에서 이 전략으로 신규 실행 생성 시도.
- **입력**: `purchase_id`, 구매자의 실행 설정(FD-16.1/16.2)
- **처리**: 구매자의 `FSMStrategyConfig` 실행 인스턴스 생성(원본 정의 참조, `owner_user_id`는 원 제작자 유지, 실행 컨텍스트만 구매자 것) → FD-8.1(전략 신호 생성)이 이 인스턴스로 평가.
- **출력**: 구매자 계정에 연결된 실행 가능한 전략 인스턴스(FD-16이 이후 이 인스턴스로
  `strategy_executions` 생성)
- **리스크**(정책문서 4.10 §교차 테넌트 리스크 2 재확인): **실행 격리** — 판매자가 구매자의 실행 데이터를 관찰할 수 있는 경로가 있어서는 안 된다(10.3-B 블랙박스 원칙의 실제 구현 지점).
- **예외 상황**: 판매자가 리스팅을 사후에 DELISTED 처리해도, 이미 구매 완료된
  건의 실행 권한은 유지된다(판매자의 일방적 회수로 구매자가 갑자기 전략을
  못 쓰게 되는 상황 방지 — 이미 지불한 대가에 대한 최소 보장).
- **완료조건**: 구매자 계정에서 전략 실행 시 판매자 계정에 어떤 데이터도 노출되지 않음을 통합 테스트로 검증.
- **관련 스펙**: 정책문서 10.3-B, 4.10, FD-16
- **작업 트리 매핑**: 신규 "13.4 실행 연동"

### FD-13.7 P2P 중개수수료 계산 (신규 — 재점검 라운드 신설, 채팅 논의만 있고 FD 서술이 없던 공백 메움)

> **핵심 구분(2026-08-10 확정)**: 이건 "매매 성과에 연동된 성과보수(Performance
> Fee)"가 **아니다** — 전자는 정책문서 10.3/14.1.2에서 자본시장법 투자일임업
> 인가 문제로 이미 명시적으로 제외된 카테고리다. 이건 "전략 판매 거래 성사
> 자체"에 대한 플랫폼 중개수수료(App Store·당근마켓식 거래 수수료와 동일
> 구조)로, 매매로 번 돈의 일부를 떼는 게 아니라 **거래 1건이 성사될 때** 판매
> 가격의 일정 비율을 취득한다 — 이후 그 전략이 매매로 얼마를 벌든 잃든 이
> 수수료 계산에 영향을 주지 않는다. 이 구분이 없으면 자본시장법 이슈가 다시
> 열린다.

- **목적**: 마켓플레이스 거래 성사 시 플랫폼 수수료와 판매자 정산액을 계산한다.
- **트리거**: FD-13.3(구매) 확정 시점(결제 확인 이후, 14.1.4 수동 정산 2단계
  흐름의 `CONFIRMED` 전이와 동시).
- **입력**: `price_paid`, `platform_commission_rate`(Draft: 10~20%, 확정치는
  사업성 검토 후)
- **처리**: `platform_commission_amount = price_paid × platform_commission_rate`,
  `seller_payout_amount = price_paid - platform_commission_amount` 계산 후
  `strategy_purchases`(13번 §13.5) 3개 컬럼에 기록.
- **출력**: `{platform_commission_amount, seller_payout_amount}` — FD-13.3
  구매 처리 결과에 포함돼 함께 반환.
- **예외 상황**: `platform_commission_rate`가 Draft 상태이므로, 확정 전까지는
  임시 고정값(Draft: 15%)으로 계산하고 모든 거래 내역에 "수수료율 확정 전
  임시 계산"이라는 표기를 남긴다(사후 정산액 조정 가능성을 사용자에게 미리
  고지 — 나중에 소급 변경 시 분쟁 소지 최소화).
- **완료조건**: 계산된 두 금액의 합이 `price_paid`와 정확히 일치, 수수료율이
  "매매 성과"가 아니라 "가격"에만 연동됨을 코드 리뷰로 확인(성과보수 재유입
  방지 — 21.5 "회귀금지 목록" 위반 여부 확인 대상).
- **관련 스펙**: 정책문서 10.3/14.1.2(성과보수 제외 원칙), 14번 문서 §14.1(가격정책),

### FD-13.8 리스팅 검색·정렬 (신규 — "0번부터 재검토" 라운드, 14번 문서 §14.4 반영 누락 발견)

### FD-13.10 분쟁 접수 (신규 — "0번부터 재검토" 라운드, 14번 문서 §14.5 반영 누락 발견)

> 근거: 14번 문서 §14.5가 분쟁 시나리오·처리절차를 상세히 설계했고 FD-18.2로
> **운영자가 조회·처리하는 쪽**은 이미 구현했으나, **애초에 구매자가 분쟁을

## FD-14 전략 편집기 (신규 — v1.1)

> 근거: 2026-08-10 비전 확정 — 사용자가 마켓플레이스 구매 외에 본인이 직접 전략을
> 제작할 수 있어야 한다(정책문서 9.2 Prompt-to-Strategy/14.2 Natural Language Strategy
> Builder의 PROPOSED 개념을 Phase 1 SCAFFOLD 실행 스펙으로 격상).
>
> **Zone 경계**: 이 대분류 전체는 FSMStrategyConfig(데이터)를 생성하는 도구다.
> 그 전략을 실제로 평가해 사고팔지 "판단"하는 로직은 FD-8(FROZEN)의 배타적 책임이며,
> 이 경계는 FD-14의 어떤 하위 기능도 넘지 않는다.

### FD-14.1 기술적 지표 라이브러리 연동

- **목적**: 사용자가 전략 조건 구성에 사용할 보조지표를 제공한다.
- **트리거**: 전략 편집기 진입 시, 지표 선택 UI 렌더링 직전.
- **입력**: `symbol`, `timeframe`, 지표별 파라미터(예: RSI 기간=14)
- **처리 단계**:
  1. TA-Lib 연동 — Market Data 파이프라인(FD-2)의 캔들 데이터를 입력으로 지표값 계산
  2. 지표군: 추세(MA/EMA/MACD/Ichimoku), 모멘텀(RSI/Stochastic/CCI/Williams %R),
     변동성(Bollinger Bands/ATR/Keltner), 거래량(OBV/VWAP/MFI), Fibonacci
     Retracement/Pivot Points 등 라이브러리 표준 지표 전체(150개 이상)
  3. 계산 결과를 프론트엔드가 소비 가능한 시계열 포맷으로 반환
- **출력**: `{indicator: str, values: list[float], params: dict}`
- **예외 상황**: 지표 계산에 필요한 최소 캔들 수 미달(예: MA(200)인데 캔들 50개) →
  오류 대신 "데이터 부족, 최소 N개 필요" 안내와 함께 빈 배열 반환
- **완료조건**: 각 지표군 최소 1개씩 계산 결과가 TA-Lib 참조값과 일치.
- **관련 스펙**: FD-2(시장데이터), 9.11(FSMStrategyConfig)
- **작업 트리 매핑**: 신규 "14.1 지표 계산 계층"

### FD-14.2 전략 편집 UI

- **목적**: 지표·조건 조합을 통해 FSMStrategyConfig를 생성한다.
- **트리거**: 대시보드 "새 전략 만들기" 액션.
- **입력**: `target_asset`(06번 §6.2 화이트리스트 심볼 중 선택 — 재점검
  라운드에서 이 필드가 FD-14.2에 누락돼 있던 것을 발견해 추가, 16번 백엔드
  `StrategyCreateRequest.target_asset`과 일치), 선택된 지표 목록 + 파라미터,
  진입/청산/손절 조건(비교연산자 + 임계값 조합, AND/OR)
- **처리 단계**:
  1. `target_asset`이 06번 §6.1 시스템 공통 화이트리스트(Draft: BTC/USDT 등
     5개 내외)에 속하는지 검증 — "사용자별 상이한 심볼셋 지원은 Phase 1
     스콥 아님" 원칙 그대로, 화이트리스트 밖 심볼 선택 자체를 UI 드롭다운에서
     제공하지 않음(서버 측에서도 이중 검증)
  2. 조건 조합 UI(코드 작성 없이 조건 빌더 형태)
  3. 조합된 조건을 9.11 FSM `transitions[].condition` 문자열로 컴파일
  4. 상태(IDLE/BUY_ORDER_PENDING/HOLDING/SELL_ORDER_PENDING/STOP_LOSS/
     EMERGENCY_EXIT) 매핑 — 사용자에게는 "진입/청산/손절 조건" 3개 입력으로
     단순화하고 내부적으로 FSM 상태·전이로 자동 변환
- **출력**: 유효한 `FSMStrategyConfig` JSON (9.11 스키마 그대로 재사용, 신규 스키마
  없음)
- **예외 상황**: 조건 조합이 FSM으로 컴파일 불가(모순되는 상태 전이) → 저장 차단,
  구체적 오류 위치 명시. 화이트리스트 밖 `target_asset` 요청 시(API 직접 호출
  등으로 UI 우회 시도) → 400 거부.
- **완료조건**: 조건 빌더로 만든 전략이 9.11 스키마 검증을 통과하고 저장 가능.
  화이트리스트 밖 심볼로 API 직접 요청 시 거부됨을 확인.
- **관련 스펙**: 9.11, 9.2, 06번 §6.1/6.2
- **작업 트리 매핑**: 신규 "14.2 전략 편집 UI"

### FD-14.3 전략 저장 및 라이프사이클 진입

- **목적**: 저장된 전략이 즉시 실행되지 않고 반드시 9.1 생애주기를 거치도록

- **입력**: FD-14.2가 컴파일한 `FSMStrategyConfig` JSON, `target_asset`, `exchange`
- **처리**: `strategies` 테이블 INSERT, `owner_user_id` = 현재 사용자, 상태

- **출력**: `{strategy_id, version, lifecycle_status: "GENERATED"}`
- **예외 상황**: 저장 직후 실행 시도 → 시스템 차단, 현재 생애주기 단계 안내.
- **완료조건**: 저장 즉시 실행 시도 시 차단 확인, 생애주기 각 단계 전이가 9.1
  순서를 벗어나지 않음을 확인.
- **관련 스펙**: 9.1, 9.9, 13번 §13.5(strategies 테이블)
- **작업 트리 매핑**: 신규 "14.3 전략 저장·생애주기 연동"

### FD-14.4 프리뷰 (경량 미리보기)

- **목적**: 저장 전 조건의 대략적 작동을 확인시킨다(정식 백테스트 아님).
- **트리거**: 편집기 내 "미리보기" 버튼.
- **입력**: 아직 저장되지 않은 조건 조합(FD-14.2와 동일 형태, `strategy_id` 없음
  — 임시 계산이므로 DB에 저장하지 않고 요청 파라미터로만 전달)
- **처리**: 최근 일부 기간(Draft: 3개월) 캔들에 조건을 즉석 적용해 시각화만 제공.
- **출력**: 진입/청산 신호가 발생했을 시점 표시(차트 오버레이), 정식 지표는 아님.

### FD-15.3 위험등급-전략 매칭 경고

- **입력**: 대조 대상 전략/정책의 리스크 지표(9.4 MDD/VaR 등), 현재 사용자

- **관련 스펙**: 10.3-B 면책조항, 9.4, FD-13.3

## FD-16 전략 실행 제어판 (신규 — v1.1)

> 근거: 2026-08-10 갭 재검토 — 비전 원문의 "가상매매든 실매매든... AIOS가 전략을
> 실행해서 매매수익을 거둘 수 있게 하는" 부분이 FD-8(FROZEN, 이미 배포된 전략의
> 판단로직)과 FD-13.4(구매 즉시 실행권한 부여)만으로는 채워지지 않음을 확인.
> "자본을 얼마 배분하고, 어느 거래소에서, 어떤 모드로, 언제 시작/중지할지"를
> **사용자가 직접 제어하는 화면·API**가 어디에도 없었다.
>
> **Zone 경계**: FD-16은 사용자가 실행 파라미터(자본배분·거래소·모드)를 지정하고
> RUNNING/PAUSED 상태를 토글하는 제어판이다. 그 안에서 실제로 "사고 팔지" 판단하는
> 로직은 여전히 FD-8(FROZEN)의 배타적 책임이며, 이 경계는 넘지 않는다.

### FD-16.1 자본 배분 지정

- **목적**: 사용자가 APPROVED 상태(9.1)에 도달한 전략(직접 제작 또는 마켓플레이스
  구매)에 실제 배분할 자본 규모를 지정한다.
- **트리거**: "내 전략 목록" 화면에서 특정 전략의 "실행 설정" 액션.
- **입력**: `strategy_id`, `allocated_capital`, `currency` (16번 백엔드 문서
  `ExecutionCreateRequest`와 필드명 통일 — 재점검 라운드에서 `strategy_instance_id`로
  남아있던 것을 발견해 정정)
- **처리 단계**:
  1. 사용자 계좌 잔고(FD-3.2) 대비 배분 가능 여부 확인
  2. 07번 §7.2 `risk_policy.yaml`의 상한선과 대조 — **전략의 인증 상태에 따라
     적용 상한이 다르다**(재점검 라운드에서 구분 명시 — 이전엔 "미검증 10%"만
     언급하고 인증 전략 상한을 안 다뤘음): `strategies.certified_badge=false`
     (직접 제작 또는 미인증 구매 전략, FD-14 편집기 산출물 포함)는
     `strategy_allocation.unverified_max_pct`(Draft 10%), `certified_badge=true`
     (9.5-A 인증 통과 마켓플레이스 전략)는 `certified_level4_max_pct`(Draft
     25%) 적용. 초과 시 저장 자체를 거부(FROZEN Risk 정책을 UI가 우회하지 않음)
  3. `strategy_executions` 테이블(신규)에 배분 기록
- **출력**: 배분 확정 또는 상한 초과 거부
- **예외 상황**: 배분 요청이 8.2-B 상한을 넘으면 정확한 초과분과 현재 상한을
  안내(FD-1.2 "추측하게 하지 않는다" 원칙과 동일)
- **완료조건**: 상한 초과 배분 시도 시 저장 거부 확인, 정상 범위 배분 시 저장 확인.
- **관련 스펙**: 정책문서 8.2-B, 9.1
- **작업 트리 매핑**: 신규 "16.1 자본배분 API"

### FD-16.2 실행 거래소·모드(PAPER/LIVE) 선택

- **목적**: 사용자가 등록한 복수 거래소(FD-12) 중 이 전략을 어디서 실행할지,
  가상매매(PAPER)로 먼저 돌려볼지 실매매(LIVE)로 바로 갈지 선택한다.
- **트리거**: FD-16.1과 동일 화면.
- **입력**: `exchange`(FD-12에 등록된 것 중 선택), `mode`(PAPER | LIVE)
- **처리 단계**:
  1. 선택한 거래소가 실제로 사용자 계정에 유효한 자격증명으로 연동돼 있는지
     확인(FD-12.2)
  2. **`mode=LIVE`인데 거래소가 `kis`인 경우 즉시 거부**(06번 §6.1 Phase 1
     스콥 — "KIS는 인터페이스만이므로 실제 kr_equity 거래는 없음", 재점검
     라운드에서 이 제약이 반영 안 돼 있던 것을 발견해 추가. PAPER 모드는
     KIS도 허용 — 인터페이스 검증 목적).
  3. `mode=LIVE`이면서 9.10 자동화 수준이 Level 1~3인 경우, 배포 자체가 이미
     인간 승인을 전제(9.10 Hard Gate) — 이 선택 자체가 FD-10.1 Critical Risk
     승인 요청을 트리거할 수 있음(배분 규모에 따라, 8.2-B 임계치 연동)
  4. `mode=PAPER`는 즉시 시작 가능(자금 이동 없음, 승인 불필요)
- **출력**: 실행 설정 확정
- **예외 상황**: 미연동 거래소 선택 시도 → 선택지 자체에서 비활성화(FD-12.2
  원칙과 동일). **KIS+LIVE 조합 시도 → 400 거부**, "Phase 1은 암호화폐
  거래소만 실거래 가능합니다" 안내(추측하게 하지 않는다 원칙).
- **완료조건**: PAPER 모드는 승인 없이 즉시 시작, LIVE 모드는 배분 규모가 임계치
  초과 시 승인 요청이 실제로 생성되는지 확인. **KIS 거래소로 LIVE 시작 시도
  시 명시적으로 거부됨을 확인**(Cross-Asset 미구현 상태에서 실거래가 새는
  경로 원천 차단, 02번 §2.2 Cross-Asset 원칙 준수).
- **관련 스펙**: 9.10, FD-10.1, FD-12, 06번 §6.1, 02번 §2.2
- **작업 트리 매핑**: 신규 "16.2 실행모드 선택 API"

### FD-16.3 시작·일시정지·중지 제어

- **목적**: 전략의 RUNNING/PAUSED/RETIRED 상태를 사용자가 직접 토글한다.
- **트리거**: "내 전략 목록" 화면의 시작/일시정지/중지 버튼.
- **입력**: `execution_id`, `action`(START/PAUSE/RETIRE), (RETIRE인 경우)
  `liquidation`(IMMEDIATE_MARKET/KEEP_POSITIONS)
- **처리 단계**:
  1. **시작**: FD-16.1/16.2 설정 완료 + (LIVE인 경우) 필요 승인 완료 →
     `strategy_executions.status = RUNNING` 전이, FD-8이 이 인스턴스를 신호평가
     대상에 포함
  2. **일시정지**: `RUNNING → PAUSED` — 신규 진입 신호 무시, 기존 보유 포지션은
     유지(청산 아님, 9.8 Kill Condition의 자동 PAUSED와 동일한 상태를 사용자가
     수동으로도 트리거할 수 있게 함). 전이 시 `paused_by`를 `USER`로 태깅해
     Watchdog 자동정지(`SAFETY_LAYER`)와 구분(v1.3 후속 — 17번 프론트엔드
     문서 검토 중 "화면에서 둘을 구분 못 하면 위험한 오해"라는 점을 발견,
     04번 DB스키마에 `paused_by` 컬럼 반영)
  3. **중지**: `RUNNING/PAUSED → RETIRED` — 기존 포지션 청산 여부를 사용자에게
     별도로 명시적으로 묻는다(즉시 시장가 청산 vs 보유 유지 후 수동 정리, Draft:
     기본값은 "보유 유지"로 두어 사용자 의도치 않은 강제청산 방지)
- **출력**: `{execution_id, status, paused_by, transitioned_at}`
- **예외 상황**: Watchdog·Circuit Breaker(FD-9)가 이미 해당 전략을 PAUSED로
  전환한 상태에서 사용자가 "시작" 시도 → 시스템 트리거 우선(FD-9가 여전히
  경고 상태이면 시작 거부, 8.6-B Kill Switch 우선순위 원칙 재확인 — 사용자
  버튼이 안전장치를 우회할 수 없음)
- **완료조건**: 정상 시작/일시정지/중지 전이 확인, Watchdog PAUSED 상태에서
  사용자 시작 시도가 거부됨을 확인(안전장치 우선순위 실증).
- **관련 스펙**: 9.1, 9.8, 8.6-B
- **작업 트리 매핑**: 신규 "16.3 실행 상태 제어 API"

### FD-16.4 실행 중 전략 모니터링

- **목적**: 사용자가 각 실행중인 전략의 개별 손익·상태를 한눈에 본다.
- **트리거**: 대시보드 또는 "내 전략 목록" 화면 진입 시.
- **입력**: `user_id`
- **처리 단계**: `strategy_executions` + `orders`/`positions`(FD-3.3, 08번 스키마)
  조인해 전략별 실현/미실현 손익, 진입 이후 경과일, 현재 상태(RUNNING/PAUSED)
  집계
- **출력**: 전략별 카드 목록(손익률, MDD, 현재 상태)
- **예외 상황**: 실행중인 전략이 하나도 없음 → 오류가 아니라 "아직 실행중인
  전략이 없습니다. 마켓플레이스에서 구매하거나 편집기로 만들어보세요" 안내
  (FD-14/FD-13으로 자연스럽게 유도)
- **완료조건**: 2개 이상 전략을 동시 RUNNING 상태로 두고 각각 손익이 독립적으로
  정확히 집계됨을 확인.
- **관련 스펙**: FD-3.2/3.3, 9.4(평가지표)
- **작업 트리 매핑**: 신규 "16.4 실행 모니터링 API"

### FD-16.5 가상매매→실매매 전환

> 근거: FD-16.2가 "시작 시점"의 모드 선택만 다루고, 이미 PAPER로 돌아가던
> 전략을 LIVE로 전환하는 흐름이 빠져있었음을 확인(2026-08-10 갭리뷰 3라운드).

- **목적**: PAPER 모드로 검증해본 실행을 LIVE로 전환한다.
- **트리거**: "내 전략 목록"에서 PAPER 상태 실행에 대해 "실매매 전환" 액션.
- **입력**: `execution_id`(전환 대상 PAPER 실행), FD-16.1/16.2와 동일한
  `allocated_capital`, `exchange`(신규 LIVE 실행 설정값)
- **처리 단계**:
  1. 기존 PAPER 실행(`strategy_executions`)은 종료하지 않고 그대로 이력 보존
     (성과 비교 근거로 남김)
  2. **신규** `strategy_executions` 행 생성(`mode=LIVE`,
     `converted_from_execution_id`=원본 PAPER 실행 ID) — PAPER 인스턴스를
     변형하지 않고 별개 실행으로 취급(가상 포지션이 실제 포지션으로 "마법처럼"
     전환되는 경로 자체를 만들지 않음 — 오해·오류 소지 원천 차단)
  3. FD-16.1(자본배분)·FD-16.2(거래소·모드=LIVE) 절차를 다시 거침 — 승인 절차
     생략 불가
- **출력**: `{new_execution_id, mode: "LIVE", converted_from_execution_id}`
- **예외 상황**: 없음(신규 실행 생성과 동일 경로 재사용이므로 FD-16.1~16.3
  예외 상황 그대로 적용)
- **완료조건**: PAPER→LIVE 전환 시 PAPER 이력이 삭제되지 않고 별도 실행으로
  남아 있음을 확인, LIVE 전환도 여전히 승인 임계치 검사를 거치는지 확인.
- **관련 스펙**: FD-16.1, FD-16.2, 9.1
- **작업 트리 매핑**: 신규 "16.6 PAPER→LIVE 전환 API"

## FD-17 알림 시스템 (신규 — v1.1, 공통 기반)

> 근거: 2026-08-10 갭 재검토 3라운드 — FD-9(Watchdog 경고), FD-10(Critical Risk 승인
> 요청), FD-15.3(위험등급 경고), FD-16.3(안전장치 차단 안내)이 전부 "사용자에게
> 알린다"고만 서술하고, 실제 전달 경로(푸시/이메일)가 설계된 적이 없었음을 확인.
> **FD-17은 번호상 뒤에 있지만, 작업트리 우선순위는 9·10보다 먼저 착수 권장** —
> 알림 인프라 없이는 FD-9/10이 "발동은 하는데 아무도 모르는" 상태가 된다.
>
> **설계 원칙**: 새 인프라를 만들지 않는다 — 기존 FD-6 Event Bus(05번)를 그대로
> 재사용, 알림 게이트웨이는 특정 topic들의 **구독자(Subscriber)**로 붙는다
> (정책문서 17.9-A 과잉설계 방지 원칙).

### FD-17.1 알림 발송 게이트웨이

- **목적**: Event Bus에 발행된 특정 이벤트를 실제 채널(푸시/이메일)로 전달한다.
- **트리거**: FD-6.1(이벤트 발행)에서 FD-17.2가 정의한 대상 topic 발행 시 자동
  구독·처리.
- **입력**: 이벤트 payload(예: `approval.request.created`, `watchdog.decision.triggered`,
  `risk_profile.match.warned`, `execution.safety_block.applied`)
- **처리 단계**:
  1. `HandlerCriticality=CRITICAL`로 등록(FD-6.2 원칙 재사용) — 알림 발송 실패가
     조용히 묻히지 않도록 강제
  2. 이벤트 유형별 채널 정책(FD-17.2) 조회
  3. 각 채널 어댑터(push/email) 호출 — Draft: 이메일은 SMTP 또는 트랜잭션 메일
     서비스, 푸시는 착수 시 확정(웹푸시 또는 미보유 시 이메일로 대체)
  4. 발송 결과(성공/실패)를 `notifications` 테이블에 기록
- **출력**: 없음(부수효과로 채널 발송 + DB 기록)
- **예외 상황**: 채널 발송 실패(SMTP 오류 등) → FD-6.3 CRITICAL 정책 그대로
  적용(재시도 최대 5회) → 5회 실패 시 `audit_log`에 CRITICAL 기록(알림이
  전달됐는지 확인 못 하는 상태 자체가 안전 이슈이므로 조용히 넘기지 않음)
- **완료조건**: Critical Risk 승인요청 이벤트 발행 시 실제 이메일 발송 확인,
  강제로 채널 실패시켜도 `audit_log`에 실패 기록이 남는지 확인.
- **관련 스펙**: 05번(Event Bus), FD-6.2/6.3
- **작업 트리 매핑**: 신규 "17.1 알림 게이트웨이"

### FD-17.2 알림 유형별 채널 정책

- **목적**: 이벤트 중요도에 따라 채널·강제성을 다르게 적용한다.
- **트리거**: FD-17.1 게이트웨이가 이벤트를 받아 실제 발송 채널을 결정해야 하는
  매 순간(코드 경로가 아니라 정책 테이블 참조 — 별도 화면 트리거는 없음).
- **입력**: `event_type`
- **처리**: 아래 표를 `channel_policy` 매핑(코드 상수 또는 DB 테이블, Draft —
  변경 빈도가 낮으므로 코드 상수로 시작하고 운영 중 빈번히 바뀌면 DB로 이전)으로
  조회.

| 이벤트 | 채널 | 사용자 끌 수 있는지 |
|---|---|---|
| `approval.request.created`(FD-10.1) | 이메일+푸시 동시 | **불가** — 4.9 강제원칙과 동일하게 안전장치 관련 알림은 사용자 설정으로 무력화 불가 |
| `watchdog.decision.triggered`(FD-9.2) | 이메일+푸시 동시 | 불가 |
| `risk.circuit_breaker.reactivation_requested`(FD-9.4, "0번부터 재검토" 라운드 신설 — Level 3 이상 자동하향 금지에 따른 인간 재가동 승인 필요) | 이메일+푸시 동시 | **불가** — approval.request.created와 동일 취급 |
| `security.withdrawal_whitelist.added`(FD-11.5, "다시 0번부터" 라운드 신설 — 계정 탈취 시 공격자의 무단 등록을 사용자가 즉시 알 수 있어야 함) | 이메일+푸시 동시 | **불가** — approval.request.created와 동일 취급 |
| `execution.safety_block.applied`(FD-16.3) | 푸시(인앱) | 불가 |
| `risk_profile.match.warned`(FD-15.3) | 인앱 모달(이미 FD-15.3에서 처리) + 선택적 이메일 | 이메일만 사용자가 끌 수 있음 |
| `marketplace.purchase.requested`(FD-13.3, 재점검 라운드 이름변경 — 舊 `purchase_confirmed`) | 이메일 | 가능 |
| `marketplace.payment.confirmed`(FD-18.5b, 재점검 라운드 신설 — 결제확인 후
  진짜 실행 가능해진 시점, `purchase_confirmed`와 혼동되던 것을 분리) | 이메일 | 가능 |
| `strategy.verification.completed`(FD-13.2) | 이메일 | 가능 |

- **출력**: `{channels: [EMAIL, PUSH, IN_APP], user_overridable: bool}`
- **예외 상황**: 위 표에 없는 신규 이벤트 타입 → 기본값은 "이메일만, 사용자가
  끌 수 있음"으로 fail-safe(강제 채널은 화이트리스트 방식으로만 지정 — 새 이벤트가
  실수로 강제 채널이 되는 것을 방지, 반대 방향은 안전).
- **완료조건**: "불가" 항목은 FD-17.4 설정 화면 자체에서 토글이 렌더링되지 않음을
  확인(뒷단이 아니라 UI 단에서부터 원천 차단).
- **관련 스펙**: FD-17.1, 4.9
- **작업 트리 매핑**: FD-17.1과 동일 리프에 정책 테이블로 포함

### FD-17.3 알림 이력 조회

- **목적**: 승인요청이 실제로 언제 전달됐는지 사후 증명 가능하게 한다 — 4.9 강제
  대기(60초)·이중서명 절차의 신뢰성이 "알림이 실제로 갔다"는 사실에 의존하므로.
- **트리거**: 사용자가 설정 화면의 "알림 이력" 탭 진입, 또는 분쟁 발생 시 운영자가
  FD-18.2에서 조회.
- **입력**: `user_id`, (선택) `event_type` 필터, `date_range`
- **처리**: `notifications` 테이블 조회 API, 발송시각·채널·성공여부 노출.
- **출력**: `[{event_type, channel, status, created_at}]` 목록
- **예외 상황**: 해당 기간 알림 이력 없음 → 빈 목록(오류 아님)
- **완료조건**: 특정 승인요청 건에 대해 몇 시에 어떤 채널로 발송됐는지 조회 가능.
- **관련 스펙**: FD-10.1, 8.10(감사 원칙)
- **작업 트리 매핑**: 신규 "17.3 알림 이력 API"

### FD-17.4 알림 설정 관리

- **목적**: 사용자가 채널 수신 여부를 관리(강제 항목 제외).
- **트리거**: 설정 화면의 "알림" 탭.
- **입력**: `{marketplace_purchase_email, verification_result_email,
  risk_mismatch_email}` 중 변경할 필드(부분 업데이트 허용)
- **처리**: `notification_preferences` 테이블 UPSERT, FD-17.2 표의 "불가" 항목은
  요청 자체를 서버에서도 거부(UI 우회 시도 방어 — FD-11.3의 60초 하한 CHECK
  제약과 동일 패턴). 애초에 강제 채널 필드는 `notification_preferences` 테이블
  스키마 자체에 컬럼으로 두지 않는다(04번 DB스키마, 이중 방어).
- **출력**: 변경된 설정 전체(`{...preferences}`)
- **예외 상황**: 강제 채널 필드명을 요청 본문에 포함해 시도 → 해당 필드는 무시
  하고 나머지만 반영 + 403 응답(요청 전체를 거부하지 않고 허용된 필드는
  처리 — 부분 악의/부분 실수를 구분하지 않고 일관되게 강제 필드만 차단)
- **완료조건**: "불가" 항목을 API로 직접 끄려는 시도 시 서버가 거부.
- **관련 스펙**: FD-17.2, 04번 DB스키마
- **작업 트리 매핑**: 신규 "17.4 알림 설정 API"

## FD-18 운영자 도구 (신규 — v1.2, 최종 갭리뷰 라운드)

> 근거: 2026-08-10 갭리뷰 최종 라운드 — RBAC(15번 문서 §15.6)에 "플랫폼 운영자(Platform
> Admin)"·"검증담당자(Verifier)" 권한이 명시돼 있고 FD-13.2(검증)·14번 문서
> §14.5(분쟁처리, 마켓플레이스 상세)가 "운영자가 처리한다"고 이미 전제했으나,
> 그 처리를 실제로 수행할 화면·API가 어디에도 없었음을 확인.
>
> **선행 조건**: `users` 테이블에 `is_verifier`, `is_platform_admin` 플래그가 15번 문서 §15.6에서
> 이미 예고됐으나 미병합 상태였음 — 이번 라운드에서 04번/13번 DB스키마에 함께 반영.

### FD-18.1 검증 대기열 조회

- **목적**: 검증담당자가 `PENDING_VERIFICATION` 상태 리스팅을 조회한다.
- **트리거**: 검증담당자 대시보드 진입.
- **입력**: 없음(role 기반 자동 필터)
- **처리**: `strategy_listings WHERE status='PENDING_VERIFICATION'` 조회, 본인이
  판매자인 건은 제외(15번 문서 §15.6 이해상충 규칙 그대로 적용 — `verifier_user_id !=
  listing.seller_user_id`).
- **출력**: 대기열 목록(리스팅ID, 판매자, 제출일시)
- **예외 상황**: 대기중인 리스팅이 없음 → 빈 목록(오류 아님), 또는 본인이 제출한
  리스팅만 대기중인 경우 → 이해상충 규칙으로 전부 걸러져 빈 목록으로 보임(검증
  담당자에게 "본인 리스팅은 다른 검증담당자가 처리해야 합니다" 안내 문구 노출
  — 목록이 비어있는 이유를 오해하지 않도록).
- **완료조건**: 검증담당자가 본인 리스팅은 목록에서 아예 보이지 않음을 확인.
- **관련 스펙**: FD-13.2, 15번 문서 §15.6
- **작업 트리 매핑**: 신규 "18.1 검증 대기열 API"

### FD-18.2 분쟁 티켓 조회·처리

- **목적**: 14번 문서(마켓플레이스 상세) §14.5(분쟁처리)의 티켓을 운영자가 실제로 조회·처리한다.
- **트리거**: 운영자 대시보드의 "분쟁" 탭.
- **입력**: (목록 조회) `status` 필터(OPEN/RESOLVED), (처리 시) `dispute_id`,
  `decision`(NORMAL_RISK_REALIZATION/DELISTED_AND_REFUND), `reason`
- **처리 단계**:
  1. 접수된 분쟁 티켓 목록 조회(상태: OPEN/RESOLVED)
  2. 특정 티켓 클릭 시 14번 문서 §14.5.2가 명시한 근거자료(검증 당시 체크리스트, 실측
     데이터, `audit_log` 시점 고정 기록)를 한 화면에 조회
  3. 처리 결정 입력: "정상 리스크 실현으로 종결" 또는 "DELISTED + 환불 처리"
- **출력**: `{dispute_id, listing_status, resolved_at}` — 처리 결과가 반영된
  리스팅의 최신 상태
- **예외 상황**: 없음(14번 문서 §14.5.2 절차를 화면으로 옮긴 것뿐, 새 판단 로직 추가 아님)
- **완료조건**: 티켓 처리 시 연결된 리스팅 상태가 실제로 변경되고, 처리 이력이
  `audit_log`에 남음.
- **관련 스펙**: 14번 문서 §14.5, 8.10
- **작업 트리 매핑**: 신규 "18.2 분쟁 처리 API"

### FD-18.3 사용자 조회·상태변경

- **목적**: 15번 문서 §15.6 RBAC에 이미 명시된 "전체 사용자 조회/상태변경" 권한을 실제
  기능으로 제공.
- **트리거**: 운영자 대시보드의 "사용자" 탭.

#### FD-18.5a 결제 대기 목록 조회

- **목적**: 운영자 대시보드의 "결제 대기" 탭에 표시할 목록을 제공한다.

- **출력**: `PaginatedResponse<PurchaseResponse>`(16번 §16.0 컨벤션)
- **예외 상황**: 대기중인 건이 없음 → 빈 목록(오류 아님).
- **완료조건**: `PENDING_PAYMENT` 상태 구매 건만 노출, `CONFIRMED` 건은 제외됨을 확인.

#### FD-18.5b 결제 확인 처리

- **목적**: 운영자가 구매 건의 실제 입금(계좌이체 등, PG 미연동 Phase 1

- **트리거**: FD-18.5a 목록에서 특정 구매 건 확인 후 액션.
- **입력**: `purchase_id`, `Idempotency-Key` 헤더(금전 관련 POST, 15번 §15.1
  원칙 — 재점검 라운드에서 누락 발견해 추가. 운영자가 실수로 같은 건을 두 번
  클릭해도 이중 처리되지 않도록)
- **처리**: `strategy_purchases.payment_status: PENDING_PAYMENT → CONFIRMED`
  전이 → FD-13.4(실행 연동)의 실행 권한 부여를 이 시점에 트리거(구매만
  하고 입금 확인 전까지는 전략을 실행할 수 없어야 함 — 지금까지 FD-13.3/13.4가
  이 순서를 명시한 적이 없었던 것도 이번에 같이 정정) → FD-17
  `marketplace.payment.confirmed` 이벤트 발행(구매자에게 "이제 실행 가능"
  알림, FD-17.2 정책표 갱신 반영) → **`audit_log`(FD-7.2) 기록**(재점검
  라운드에서 누락 발견 — 금전 상태를 바꾸는 운영자 액션은 8.10 원칙상 반드시
  감사기록 대상, `actor_agent`=운영자 계정, `decision_data`={purchase_id,
  이전 상태, 이후 상태}).
- **출력**: `{purchase_id, payment_status: "CONFIRMED", confirmed_at}`
- **예외 상황**: 이미 `CONFIRMED`인 건 재확인 시도 → 멱등 처리(FD-18.4와 동일
  패턴, 에러 아님) — 이 경우 Idempotency-Key와 무관하게 상태 조회로서 취급

- **완료조건**: `PENDING_PAYMENT` 상태에서는 FD-13.4 실행 권한이 부여되지
  않고, `CONFIRMED` 전환 후에만 부여됨을 확인. 동일 Idempotency-Key로 재요청
  시 중복 이벤트 발행 없음을 확인. `audit_log`에 처리 이력이 남는지 확인.
- **관련 스펙**: 14번 문서 §14.1.4, FD-13.3, FD-13.4, FD-7.2, 15번 §15.1
- **작업 트리 매핑**: 신규 "18.5b 결제 확인 API"

### FD-19.1 통합 포트폴리오 조회

- **목적**: 사용자의 모든 RUNNING/PAUSED 실행(FD-16)을 하나의 포트폴리오 뷰로
  집계한다.
- **트리거**: 대시보드 "포트폴리오" 탭.
- **입력**: `user_id`(인증 토큰에서 자동 추출, 별도 파라미터 없음)
- **처리**: `strategy_executions`(사용자 전체) + 연동 거래소별 잔고(FD-3.2) 조인 —
  전략별 배분 비중(%), 미배분 현금 비중, 거래소별 분산, 전체 미실현손익 합산.
  **02번 §2.2 Cross-Asset 원칙 명확화(재점검 라운드 추가)**: 이 합산은 순수
  표시 목적(대시보드 집계)이며, FROZEN Risk Engine의 실시간 판단에는 전혀
  쓰이지 않는다 — 그 경계가 실제로 지켜지는 이유는 FD-16.2가 KIS를 LIVE
  모드에서 원천 차단하므로, Phase 1에서 실제로 여기 집계되는 LIVE 실행은
  전부 crypto(Bitget) 단일 자산군뿐이기 때문이다(06번 §6.1과 동일 전제).
  PAPER 모드로는 KIS 실행도 존재할 수 있으나, 이 경우 실자금이 아니므로
  Cross-Asset 리스크 자체가 발생하지 않는다.
- **출력**: 도넛차트용 데이터(전략별 비중) + 표(전략명, 배분액, 현재가치, 손익률)
- **예외 상황**: RUNNING/PAUSED 실행이 하나도 없음 → 전체 현금 100%로 표시(오류
  아님, FD-16.4와 동일하게 실행이 없는 상태를 정상 상태로 취급).
- **완료조건**: 3개 이상 전략을 동시 운용 중일 때 비중 합이 100%로 정확히
  집계됨을 확인(미배분 현금 포함).
- **관련 스펙**: FD-16.4, FD-3.2
- **작업 트리 매핑**: 신규 "19.1 포트폴리오 조회 API"

### FD-19.2 포트폴리오 재구성

- **목적**: 사용자가 기존 실행들의 자본배분을 한 화면에서 조정한다(전략을 새로
  시작하지 않고 기존 배분만 변경).
- **트리거**: 포트폴리오 화면의 "재구성" 액션.
- **입력**: `{execution_id, new_allocated_capital}[]` (여러 실행 동시 조정)
- **처리 단계**:
  1. 각 조정값에 대해 FD-16.1의 상한 검증(8.2-B) 재적용 — 재구성이라고 검증을
     생략하지 않음
  2. 배분 증가는 추가 자금 투입으로 처리(거래 없이 한도만 변경), 배분 감소는
     **초과분만큼 신규 진입 금지**로 처리 — 기존 보유 포지션을 재구성 자체가
     강제 청산하지 않는다(FD-16.3의 청산 원칙과 동일 정신, 사용자 의도치 않은
     매도 방지)
  3. LIVE 모드 실행의 배분 증가가 임계치를 넘으면 FD-10.1 승인 요청 재트리거
     (FD-16.2와 동일 원칙)
- **출력**: `{adjusted: int, pending_approval: int, approval_request_ids: [uuid]}`
  — 즉시 반영된 건수와 승인 대기로 넘어간 건수를 구분해서 반환(15번 문서 §15.5-F 예시 참조)
- **예외 상황**: 재구성 결과 배분 총합이 계좌 잔고를 초과 → 저장 거부
- **완료조건**: 배분 감소 시 기존 포지션이 강제 청산되지 않고, 배분 증가가
  임계치 초과 시 승인 요청이 생성됨을 확인.
- **관련 스펙**: FD-16.1, FD-16.2, 8.2-B
- **작업 트리 매핑**: 신규 "19.2 포트폴리오 재구성 API"

> **핵심 원칙**: FD-11~20의 REST API(15번 문서)는 이미 프론트엔드에 종속되지
> 않는다 — 모바일 앱은 **새 백엔드 기능이 아니라 같은 API를 소비하는 두 번째
> 클라이언트**다. 아래 두 개만 모바일 특유로 신규 필요하다.

### FD-21.1 디바이스 푸시 토큰 등록 (FD-17 확장)

- **목적**: FD-17(알림 시스템)의 PUSH 채널이 실제 APNs(iOS)/FCM(Android)로
  발송되도록 디바이스를 등록한다.
- **트리거**: 앱 최초 실행 시 알림 권한 승인 직후.
- **입력**: `device_token`, `platform`(iOS/Android)
- **처리**: `device_tokens` 테이블(신규) 저장, FD-17.1 게이트웨이가 PUSH 채널
  발송 시 이 테이블을 참조.
- **출력**: `{device_id, registered_at, is_active: true}`
- **예외 상황**: 토큰 만료(앱 재설치 등) → 발송 실패 시 해당 토큰 비활성화
  (FD-17.1의 CRITICAL 재시도 정책과 별개 — 토큰 자체 문제는 재시도 무의미).
- **완료조건**: 등록된 디바이스에 실제 푸시 발송 확인.
- **관련 스펙**: FD-17.1
- **작업 트리 매핑**: 신규 "21.1 디바이스 토큰 API"

### FD-21.2 생체인증 로그인 (FD-11 확장)

- **목적**: 앱에서 Face ID/지문으로 재로그인(매번 비밀번호 입력 방지).
- **트리거**: 최초 로그인 성공 후 "생체인증으로 빠른 로그인" 동의.
- **입력**: OS 생체인증 성공 결과(클라이언트 로컬 판단, 서버로 전송되는 것은
  Keychain/Keystore에 저장돼 있던 기존 세션 토큰뿐 — 생체정보 자체는 기기 밖으로
  나가지 않음)
- **처리**: 세션 토큰을 OS 보안 저장소(iOS Keychain/Android Keystore)에 저장,
  생체인증 성공 시 저장된 토큰으로 자동 로그인 — **비밀번호를 기기에 저장하지
  않는다**(토큰만 저장, FD-11.1의 Argon2id 해시 원칙과 별개 계층).
- **출력**: 기존 FD-11.1 `POST /auth/login`과 동일한 세션 토큰 응답 형태(신규
  응답 스키마 없음 — 저장된 토큰을 재사용/갱신하는 클라이언트 로직이므로)
- **예외 상황**: 생체인증 실패 3회 → 비밀번호 로그인으로 강제 전환.
- **완료조건**: 생체인증으로 로그인 성공, 3회 실패 시 비밀번호 화면 노출 확인.
- **관련 스펙**: FD-11.1
- **작업 트리 매핑**: 신규 "21.2 생체인증 연동"

## FD-9/FD-10 신설로 인한 Zone 재분류 및 작업 트리 대규모 추가

**Zone 재분류**: Watchdog·Circuit Breaker·Data Distrust·Reconciliation 에스컬레이션·Human Approval 흐름을 FROZEN에서 **SCAFFOLD로 재분류**한다 — 이들은 "매매 판단"이 아니라 "위험 감시·상호작용 워크플로"이며, 06번 §6.3 Definition of Done이 이미 Watchdog 시뮬레이터를 Phase 1 요건으로 요구하고 있어 이 재분류가 기존 스콥과도 일치한다. 정책문서 v3.2 정책문서 15.6-A에도 동일하게 반영됐다.

이로 인해 10번 작업 트리에 새 대분류 "9. 안전장치 계층"과 "10. 인간 승인 흐름"을 신설해야 한다:

```
├── 9. 안전장치 계층 (신설, FD-9 기반)
│   ├── 9.1 Watchdog 프로세스 골격 (별도 프로세스, 메인과 IPC로만 통신)
│   ├── 9.2 Watchdog 판정 로직 (정지/청산 분기, Griefing 방어)
│   ├── 9.3 Split-Brain 진단기 (히스테리시스 포함)
│   ├── 9.4 Circuit Breaker 상태기계
│   ├── 9.5 Data Distrust 쿼럼 확장 (5.11을 3소스로 확장)
│   ├── 9.6 Reconciliation 에스컬레이션 로직
│   ├── 9.7 Watchdog 오탐 검증 시뮬레이터 (8.6-A-1-1, 06번 DoD 필수항목)
│   └── 9.8 통합 테스트 — Flash Crash 데이터 재생
│
└── 10. 인간 승인 흐름 (신설, FD-10 기반)
    ├── 10.1 승인 요청 워크플로 (60초 대기, FD-11.3 ApprovalMode 따라 SOLO/DUAL)
    ├── 10.2 SURGE 판정기 (Trigger Provenance 독립검증)
    ├── 10.3 패닉 프롬프트 생성기 (화이트리스트 제약)
    └── 10.4 통합 테스트 — SOLO는 본인 1계정, DUAL은 Mock 승인자 2계정
```

**중요한 선행조건**: 9번·10번 착수 전 `risk_policy.yaml`(07번 §7.2)에 이미 존재하는 `watchdog`/`circuit_breaker`/`data_distrust` 섹션을 그대로 사용 가능 — 새 설정 파일 구조는 필요 없다.
**재점검 라운드 정정**: 이 문단은 멀티테넌시(4.9 2계층 분리, 13번 문서)가 도입되기
훨씬 전 라운드에 작성된 것으로, "10번은 플랫폼 레벨 승인 한정"이라고 서술하고
있었으나 이는 당시 1인 운영자 전제(모든 Critical Risk = 곧 플랫폼 레벨)에서
나온 낡은 문구였다. 실제로 FD-10의 트리거(FD-9.2/FD-9.6/FD-16.2)는 특정 사용자의
계정·실행에 대한 판단이므로 **사용자 레벨**이며 20.1-B 플랫폼 레벨 블로커와
무관하다 — FD-10 섹션 자체의 정정 내용(위 FD-10 헤더 참조)과 이제 일치시켰다.
