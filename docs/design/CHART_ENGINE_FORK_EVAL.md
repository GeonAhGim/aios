# CHART_ENGINE_FORK_EVAL — 차트 엔진 포크 평가 (CH-0)

- 리프: CH-0 (`docs/specs/L4_analytics_authoring_backtest_marketplace_v1.0.md` §9.6)
- 근거: ADR-2026-09-04-B(D0, D2)
- 범위: **문서 + 벤치 스크립트만.** `vendor/` 반입, `packages/chart-engine` 생성, `package.json` 의존성 추가는 전부 CH-1 몫이며 이 리프에서 하지 않았다. 결론이 나와도 CH-1은 CA(Chief Architect) 확정 전에는 착수하지 않는다.
- 벤치 스크립트: `frontend/packages/ui-web/scripts/bench_chart_candles.mjs` (실행 방법은 §5)

## 0. 채점 원칙 — ADR-2026-09-04-B D0가 최상위

> **D0. AIOS는 TradingView에 연결해 쓰는 보조 도구가 아니라, 차트·지표·전략작성·백테스트·마켓·데이터를 자체적으로 같은 수준으로 제공하는 독립 제품이다.**

이 리프의 `decision`은 이 원칙을 채점의 최상위에 두라고 명시한다: **재배포·포크를 막는 라이선스는 fps가 아무리 좋아도 탈락**이며, 사유는 라이선스 원문(조항 번호 + 원문 문장)으로 남긴다.

구체 사례로 TradingView **Advanced Charts**(구 "Charting Library" — CH-0 후보가 아니라 D0 게이트를 구체화하기 위한 대조군)를 확인했다. 공개 GitHub 저장소(`tradingview/charting_library`)는 승인된 계정만 접근 가능해 `raw.githubusercontent.com`에서 404가 반환되었고(비공개 배포 자체가 증거), 공식 문서(`tradingview.com/charting-library-docs/latest/introduction/`)는 다음과 같이 명시한다:

> "Advanced Charts is available for free provided that the TradingView attribution remains visible **and the implementation environment is public (not for private use or behind a paywall)**."

AIOS는 테넌트 인증 뒤에 있는 유료 SaaS이므로 "not... behind a paywall" 조건을 정면으로 위반한다. 소스 접근 자체가 승인제이고 배포 조건이 AIOS의 실제 배포 형태와 충돌하므로, 이런 라이선스였다면 fps·드로잉 점수와 무관하게 **탈락(0점)**으로 채점했을 것이다. 아래 4개 후보는 ADR §D2가 이미 허용적 라이선스(Apache-2.0/MIT)로 사전 필터링해 배정한 목록이므로, 넷 다 이 게이트 자체에서 탈락하지는 않는다 — 대신 라이선스가 지우는 **의무의 무게**(NOTICE·귀속·특허조항 유무)로 축1 점수를 세분화했다(§2).

## 1. 채점 축과 가중치 (CA decision가 ADR §D2 표를 대체)

ADR-2026-09-04-B §D2 원문 가중치(성능30·드로잉25·TS20·라이선스15·커뮤니티10)는 이 리프의 `decision` 필드가 지정한 순서 — **라이선스 자유도 > 드로잉/확장성 > 10만 봉 성능 > TS 모듈 경계** — 로 대체한다.

| 축 | 가중치 | 근거 |
|---|---|---|
| ① 라이선스 자유도 | 40 | D0가 최우선 원칙이므로 게이트 통과 후에도 의무 부담을 최고 가중치로 반영 |
| ② 드로잉/확장성 | 30 | CH-3·CH-4·IND 리프가 바로 이 위에 얹힌다 — 포크 후 재작성 비용을 직접 좌우 |
| ③ 10만 봉 성능 | 20 | 실측(§4)으로 대체. 벤더 주장 수치 대신 로컬 헤드리스 크롬 실측값만 사용 |
| ④ TS 모듈 경계 | 10 | `chart-engine/src/*.ts` 래퍼로 감싸는 CH-1 설계의 용이성 |

## 4. 10만 봉 성능 실측 (벤더 문서 수치 인용 없음 — 전부 로컬 실측)

### 4.1 방법
- 스크립트: `frontend/packages/ui-web/scripts/bench_chart_candles.mjs` (본 리프 산출물, 저장소에 커밋됨. package.json 미변경 — CH-0 범위 제약).
- 데이터: 시드 고정 PRNG(`mulberry32`, seed=42)로 생성한 합성 OHLCV 100,000봉(1분봉, `Date.now()`/`Math.random()` 미사용 — 재현 가능).
- 렌더 컨테이너: 1200×600px. 실행기: `puppeteer-core` + 로컬 설치된 실제 Chrome(v152.0.7977.65, headless) — Chromium 다운로드 없이 기존 브라우저 사용.
- 초기 렌더: 데이터 주입 직후 double-rAF까지의 wall time.
- 팬/줌: 줌 60스텝(전체 범위 → 약 200봉) + 팬 60스텝(200봉 윈도우를 데이터셋 전체로 슬라이드), 스텝마다 1 rAF 대기. 프레임 간 시간(`frameTimesMs`, vsync 포함 체감 프레임타임)과 API 호출 자체의 동기 실행 시간(`callTimesMs`, 순수 계산 비용)을 모두 기록. 워밍업 1샘플 제외, 유효 샘플 n=119/후보.
- 실행 환경: Windows 11 Home, Intel Core i7-1260P, RAM 16GB. **로컬 1머신 기준 참고치이며 CI 재현 벤치마크가 아니다.**
- 각 후보 3회 반복 실행, 아래 표는 **중앙값**(변동폭은 괄호).
- 실행 방법(패키지 미설치 상태에서 스크립트만 실행하면 아래처럼 우아하게 실패한다 — 실제로 이 리프에서 검증함):
  ```
  $ node frontend/packages/ui-web/scripts/bench_chart_candles.mjs --lib=klinecharts
  { "klinecharts": { "status": "UNMEASURED", "reason": "puppeteer-core not installed in cwd ...: Cannot find module 'puppeteer-core'" } }
  ```
  실측하려면 저장소 **밖의** 스크래치 디렉터리에 후보 라이브러리 + `puppeteer-core` + `esbuild`를 설치하고(`frontend/package.json`은 건드리지 않는다), 그 디렉터리를 cwd로 스크립트를 실행한다(스크립트 상단 주석에 정확한 명령 기재).

### 4.2 결과 (100,000봉, n=3 실측)

| 후보 | 초기 렌더 (ms, 중앙값) | 팬/줌 프레임타임 p50 / p95 (ms) | 팬/줌 API 호출시간 p50 / p95 (ms) | 60fps(16.7ms) 예산 대비 |
|---|---|---|---|---|
| KLineChart | 116.7 (108.6–174.0) | 16.7 / 17.3 | 0 / 0.1 | p95도 예산 내, 드롭 없음 |
| Lightweight Charts | 297.4 (288.7–298.8) | 16.7 / 17.6 | 0 / 0.1 | p95 근소 초과 가능성, 사실상 vsync 고정 |
| react-financial-charts | 99.4 (97.5–101.8) | 16.7 / 17.0 | 측정 대상 아님(React 커밋이 스케줄됨 — 동기 호출시간이 실작업을 반영 안 함, 프레임타임이 올바른 지표) | 4후보 중 가장 안정적으로 예산 내 |
| NightVision | 162.0 (159.8–174.0) | 16.8 / **61.4** | 1.8 / **59.8** | **p95가 예산의 3.5배 — 실제 프레임 드롭(약 16fps)** |

해석:
- 초기 렌더는 react-financial-charts·KLineChart가 가장 빠르고(~100–130ms), Lightweight Charts가 가장 느리다(~290–300ms, 약 3배) — 벤더 문서가 강조하는 "성능"은 인터랙션(팬/줌) 쪽이지 초기 렌더가 아님을 실측이 보여준다.
- 팬/줌은 KLineChart·Lightweight Charts·react-financial-charts 셋 다 `callTimesMs`(순수 계산)가 0에 가깝다 — 세 라이브러리 모두 내부적으로 렌더를 다음 애니메이션 프레임으로 지연시켜 그리기 때문에, 측정된 프레임타임(~16.7ms)은 **계산 비용이 아니라 디스플레이 vsync 간격에 의해 상한이 걸린 것**이다. 즉 이 셋은 10만 봉에서 팬/줌 시 60fps 예산을 소진하지 않는다(여유 있음).
- NightVision만 유일하게 계산 비용 자체가 커서(`callTimesMs` p95 59.8ms) 프레임을 규칙적으로 드롭한다(p95 프레임타임 61.4ms ≈ 16fps) — 100k봉 규모에서 실사용 시 눈에 띄는 끊김이 예상된다.
- NightVision의 팬/줌은 README에 문서화되어 있지 않다: 공개 문서에는 `chart.data` 설정 예제뿐이고, 프로그램적 범위 제어는 배포된 `dist/index-*.js`(압축 번들)를 직접 읽어 `range` get/set 접근자(`chart.range = [tMs, tMs]`, 내부적으로 `chart.setRange()`에 위임)를 발견해서 사용했다. 문서화되지 않은 내부 API에 의존한 실측이므로, 공개 API 계약이 아니라는 리스크를 그대로 남긴다.

### 1순위 추천: **KLineChart**
- 라이선스 의무가 가장 가볍다(Apache-2.0, NOTICE 파일 없음, D0가 우려하는 "TradingView 귀속 노출" 문제 없음).
- CH-3(오버레이)·CH-4(드로잉)·IND(지표) 리프가 요구하는 기능을 이미 상당 부분 내장(오버레이·멀티페인·지표 레지스트리) — 포크 후 점진 재작성 비용이 가장 낮다.
- 실측 성능이 4개 중 최상위권(초기 렌더 최속에 가깝고, 팬/줌 p95가 예산 내로 가장 안정적).
- TS 네이티브라 `chart-engine/src/*.ts` 래퍼 설계(ADR-B D2)에 바로 들어간다.

**대비되는 트레이드오프**(CA 검토용): Lightweight Charts는 TS 모듈 경계가 4개 중 가장 깨끗하고 팬/줌 안정성도 우수하지만, (a) 드로잉 도구가 전무해 CH-4를 백지에서 구현해야 하고 (b) NOTICE 의무로 인해 AIOS 화면에 영구적인 TradingView 귀속 링크를 노출해야 한다는 점이 D0의 "독립 제품" 포지셔닝과 정면으로 부딪힌다 — 이 두 가지가 라이선스·드로잉 축에서 KLineChart에 뒤지는 핵심 이유다.
