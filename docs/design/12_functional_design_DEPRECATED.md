## FD-2 시장 데이터 처리

### FD-2.1 시세 조회 (REST)

- **목적**: 특정 심볼의 현재가·호가 스냅샷을 즉시 조회한다.
- **트리거**: Scanner(FD-5.2), 또는 다른 모듈의 명시적 요청.
- **입력**: `symbol: str`, `exchange: str`
- **처리 단계**:
  1. 해당 거래소의 `ExchangeAdapter.get_ticker(symbol)` 호출
  2. 응답을 `Parser.parse_ticker()`(FD-2.5)로 정규화
  3. `source_type="primary"`로 태깅
- **출력**: `Ticker` 모델(01번 §1.3)
- **예외 상황**:
  - 존재하지 않는 심볼 → `FatalExchangeError`(11번 §11.3), 재시도 없음
  - API 타임아웃 → `RetryableExchangeError`, 지수백오프 최대 5회(05번 §5.5)
  - Rate Limit 초과 → 응답 헤더의 재시도 대기시간 준수(거래소별 상이, 실제 문서 확인 필요)
- **완료조건**: Bitget Demo 계정으로 5개 심볼(06번 §6.2) 각각 조회 성공, 없는 심볼 요청 시 명확한 예외 발생 확인.
- **관련 스펙**: 02번(ExchangeAdapter), 01번 §1.3(Ticker)
- **작업 트리 매핑**: 6.4(BitgetAdapter Market Data), 5.4(Parser)

### FD-2.2 실시간 시세 구독 (WebSocket)

- **목적**: 심볼의 시세 변화를 지속적으로 수신해 Event Bus에 발행한다.
- **트리거**: 시스템 시작 시 Phase 1 대상 심볼(06번 §6.2) 전체에 대해 자동 구독.
- **입력**: `symbol: str`, `callback: TickerCallback`(02번 §6.1)
- **처리 단계**:
  1. `ExchangeAdapter.subscribe_ticker_stream(symbol, callback)` 호출
  2. 콜백 내부에서 수신 데이터를 `Parser.parse_ticker()` 통과
  3. `event_bus.publish("market.ticker.updated", ticker)` (05번 §5.3 Topic)
- **출력**: 없음(부수효과로 Event Bus에 지속 발행)
- **예외 상황**:
  - 연결 끊김 → Adapter 내부에서 재연결 시도(02번 §2.3), 재연결 중 `market.distrust.entered` 발행
  - 재연결 성공 → `market.distrust.exited` 발행
  - 재연결 반복 실패(Draft: 5회 초과) → `CRITICAL` 레벨 로그(07번 §7.1) + `audit_log` 기록
- **완료조건**: 구독 시작 후 최소 60초간 끊김 없이 이벤트 수신, 강제로 연결을 끊었을 때 재연결 및 distrust 이벤트 발행 확인(통합 테스트로 시뮬레이션).
- **관련 스펙**: 02번 §2.3, 05번 §5.3
- **작업 트리 매핑**: 6.5

### FD-2.3 캔들 조회

- **목적**: 특정 타임프레임의 OHLCV 이력 데이터를 조회한다(초기 스캐닝·향후 백테스트 대비).
- **트리거**: Scanner, 또는 수동 요청.
- **입력**: `symbol: str`, `timeframe: str`, `limit: int = 100`
- **처리 단계**: FD-2.1과 동일 패턴, `get_ohlcv()` 호출 → `Parser.parse_candles()`(FD-2.5)
- **출력**: `list[Candle]`
- **예외 상황**: FD-2.1과 동일 + `limit` 과다 요청 시 거래소 최대치로 자동 축소(Draft, 거래소별 최대값 확인 필요)
- **완료조건**: 5개 심볼 × 3개 타임프레임(1m/5m/1h) 조합 조회 성공.
- **관련 스펙**: 02번, 01번 §1.3(Candle)
- **작업 트리 매핑**: 6.4, 5.5

### FD-2.4 호가창 조회

- **목적**: 매수/매도 호가 스냅샷 조회(향후 슬리피지 계산·TWAP 실행 설계에 필요).
- **입력/처리/출력**: FD-2.1과 동일 패턴, `get_orderbook()` → `Parser.parse_orderbook()`(FD-2.5)
- **완료조건**: depth=20 기준 5개 심볼 조회 성공, bids/asks 가격 정렬(내림차순/오름차순) 검증.
- **관련 스펙**: 02번, 01번 §1.3(OrderBook)
- **작업 트리 매핑**: 6.4, 5.6

### FD-2.5 원시 데이터 파싱

- **목적**: 거래소별 Raw JSON 응답을 내부 표준 모델(01번)로 변환 — 이 계층 덕분에 상위 모듈은 거래소 차이를 몰라도 된다.
- **트리거**: FD-2.1~2.4 내부에서 호출.
- **입력**: 거래소별 Raw `dict`, `exchange: str`
- **처리 단계**: 거래소별 필드명 매핑(예: Bitget의 `lastPr` → `Ticker.price`) → `Decimal` 변환 시 11번 §11.2 정밀도 규칙 적용 → 표준 모델 생성
- **출력**: `Ticker` | `Candle` | `OrderBook`
- **예외 상황**: 예상 필드 누락 시 `FatalExchangeError`(거래소 API 스펙 변경 가능성을 즉시 드러내기 위해 조용히 기본값 채우지 않는다)
- **완료조건**: 실제 Bitget/KIS 응답 샘플(fixture) 기준 단위 테스트 전부 통과.
- **관련 스펙**: 03번 §3.2(Parser), 01번
- **작업 트리 매핑**: 5.4, 5.5, 5.6

### FD-2.6 데이터 신뢰도 검증 (다중소스 교차확인)

- **목적**: Primary 피드와 Reference 피드 간 괴리를 감시해 오라클 왜곡을 방어한다(AIOS 정책문서 8.1-A).
- **트리거**: FD-2.2로 신규 시세가 들어올 때마다.
- **입력**: `Ticker`(primary), 최근 Reference 시세 캐시
- **처리 단계**:
  1. 괴리율 계산: `|primary.price - reference.price| / reference.price`
  2. 히스테리시스 적용(진입 1.5% / 해제 0.75%+60초, `risk_policy.yaml`의 `data_distrust` 섹션, 07번 §7.2)
  3. 임계치 초과 시 `market.distrust.entered` 발행, 신규 포지션 진입 판단(FROZEN, FD-8)에서 참조
- **출력**: 없음(상태 전이 + 이벤트 발행)
- **예외 상황**: Reference 피드 자체가 없는 경우(Phase 1은 Reference 소스 미구축 가능) → 이 검증 자체를 skip하고 WARNING 로그로 명시 — **조용히 항상 통과시키지 않는다.**
- **완료조건**: 인위적으로 괴리 데이터 주입 시 정확히 히스테리시스 규칙대로 상태 전이하는지 통합 테스트로 검증.
- **관련 스펙**: 정책문서 8.1-A, 07번 §7.2(risk_policy.yaml)
- **작업 트리 매핑**: 10번 문서에 없던 리프 — "5.11 데이터 신뢰도 검증기" 신규 추가 필요(문서 하단 참조)

## FD-3 거래소 연동

### FD-3.1 인증

- **목적**: 거래소 API 호출에 필요한 인증 토큰/세션을 확보한다.
- **트리거**: Adapter 초기화 시.
- **입력**: `.env`에서 로드한 API Key/Secret(FD-1.1)
- **처리 단계**(거래소별 상이):
  - Bitget: API Key/Secret/Passphrase 기반 서명(HMAC) — 요청마다 서명 생성
  - KIS: OAuth 2.0 2-legged — `app_key`/`app_secret`으로 access token 발급, 토큰 만료 전 갱신
- **출력**: 인증된 클라이언트 세션(내부 상태)
- **예외 상황**: 인증 실패 → `FatalExchangeError`, 재시도하지 않고 즉시 CRITICAL 로그(잘못된 키로 반복 시도 시 계정 잠금 위험)
- **완료조건**: 양쪽 거래소 모두 인증 성공 후 최소 1개 조회성 API 호출 성공.
- **관련 스펙**: 02번, 07번 §7.3(Secrets)
- **작업 트리 매핑**: 6.3, 6.9

### FD-3.2 계좌 잔고 조회

- **목적**: 자산별 총잔고·가용잔고 조회.
- **입력**: `asset: str | None`
- **처리**: `get_balance()` 호출 → `AccountBalance` 리스트 반환. **11번 §11.1 원칙에 따라 반환값은 Currency 태깅 필수**(Bitget=USDT 계열, KIS=KRW).
- **완료조건**: 양쪽 거래소 잔고 조회 성공, 통화 필드가 올바르게 채워지는지 확인(§11.1 Money 타입 적용 후).
- **관련 스펙**: 02번, 11번 §11.1
- **작업 트리 매핑**: 6.6, 6.10

### FD-3.3 포지션 조회

- FD-3.2와 동일 패턴. `get_positions()` → `Position` 리스트.
- **완료조건**: 포지션 없는 상태에서 빈 리스트 반환 확인(에러 아님).
- **작업 트리 매핑**: 6.6, 6.10

### FD-3.4 주문 상태 조회

- **목적**: 특정 주문의 현재 거래소측 상태를 재확인 — 특히 UNKNOWN 상태 해소용(7.5 멱등성 원칙).
- **입력**: `order_id: str`(내부 ID 또는 거래소 ID)
- **처리**: `get_order()` 호출.
- **예외 상황**: 거래소가 해당 주문 자체를 못 찾는 경우 — "존재하지 않음"과 "아직 시스템에 반영 안 됨"을 구분해야 함(Draft: 최근 생성된 주문은 수 초 재시도 후 최종 실패 처리).
- **완료조건**: FD-4.2에서 생성한 주문의 상태 변화(CREATED→...→FILLED)를 폴링으로 정확히 추적.
- **작업 트리 매핑**: 6.7

### FD-3.5 헬스체크

- **목적**: State DB와 무관하게 거래소 자체 응답성을 독립 확인(정책문서 8.6-A-1-2 Split-Brain 방어의 데이터 소스).
- **처리**: 경량 조회 API(예: 잔고 조회) 호출, 응답 성공/실패만 판단.
- **완료조건**: 정상 시 `True`, 강제로 네트워크 차단 시 `False` 또는 타임아웃 예외.
- **작업 트리 매핑**: 6.8

### FD-3.6 연결 끊김 및 재연결 처리

- FD-2.2에서 이미 다룸(WebSocket 재연결). 이 항목은 **REST 호출 실패**(WebSocket이 아닌 경우)의 재시도 정책을 다룬다.
- **처리**: 05번 §5.5의 재시도 정책(지수백오프, 최대 5회) 그대로 적용.
- **완료조건**: 강제 네트워크 오류 주입 시 정확히 5회 재시도 후 `RetryableExchangeError` 최종 전파 확인.
- **작업 트리 매핑**: 6.4~6.7 전체에 걸쳐 공통 적용(별도 리프 아님, 공통 유틸)

## FD-6 이벤트 처리

### FD-6.1 이벤트 발행

- **목적**: 시스템 내 상태 변화를 다른 모듈에 알린다.
- **트리거**: FD-2.2, FD-4.2 등 상태 변화가 발생하는 모든 지점.
- **입력**: `topic: str`(05번 §5.3 명명규칙 준수), `payload`
- **처리**: `InProcessEventBus.publish()` → topic별 큐에 적재 → 백프레셔 검사(08번 §8.6, 큐 깊이 1000 초과 시 발행 거부+WARNING)
- **완료조건**: 3개 핵심 topic(market.ticker.updated, order.status.changed, audit.decision.logged) 발행·수신 왕복 확인.
- **관련 스펙**: 05번
- **작업 트리 매핑**: 4.3

### FD-6.2 이벤트 구독 및 처리

- **목적**: 등록된 handler가 이벤트를 소비한다.
- **처리**: `subscribe(topic, handler)` 등록 시 `HandlerCriticality`(SAFE/CRITICAL) 명시 필수(05번 §5.5 — 미지정 시 등록 거부).
- **완료조건**: SAFE handler 예외 발생 시 다른 handler 영향 없음, CRITICAL handler 예외 발생 시 에스컬레이션 경로 작동 확인.
- **작업 트리 매핑**: 4.3, 4.5

### FD-6.3 Handler 에러 처리

- 05번 §5.5 내용 그대로 — SAFE는 log_and_continue, CRITICAL은 escalate_and_retry(최대 5회 후 8.6 Circuit Breaker 경고 단계 격상 + Human 알림).
- **완료조건**: CRITICAL handler가 5회 재시도 후에도 실패 시 실제로 Circuit Breaker 상태가 변하는지 통합 테스트.
- **작업 트리 매핑**: 4.5

### FD-6.4 재시작 시 정합성 복구

- 05번 §5.6 내용 그대로 — 시작 시 `orders`에서 비최종 상태 행 조회 → 거래소 실제 상태 재확인 → 필요 이벤트 재발행.
- **완료조건**: 프로세스를 강제 종료 후 재시작했을 때, 미체결 주문 상태가 정확히 재동기화되는지 시나리오 테스트.
- **작업 트리 매핑**: 4.6

## FD-1 설정 및 초기화

### FD-1.1 환경설정 로딩 (.env / Secrets)

- **목적**: API Key/Secret 등 민감정보를 `.env`에서 로드해 마스킹된 형태로 시스템에 공급한다.
- **트리거**: 시스템 시작 시 최우선 — Exchange Adapter 초기화(FD-3.1)보다 먼저 실행되어야 한다.
- **입력**: `.env` 파일 경로
- **처리 단계**:
  1. `.env` 파일 존재 확인
  2. 필수 키 목록(Draft: `BITGET_API_KEY`, `BITGET_API_SECRET`, `KIS_APP_KEY`, `KIS_APP_SECRET`) 존재 여부 확인
  3. `SecretBundle`로 래핑 — `__repr__`은 항상 마스킹(02번 원칙)
- **출력**: `SecretBundle`
- **예외 상황**:
  - `.env` 파일 자체가 없음 → Fatal, 시스템 시작 중단(어떤 거래소도 인증 불가능하므로 진행 의미 없음)
  - 필수 키 중 일부 누락 → Fatal, **누락된 키 이름만** 로그에 남기고 값은 절대 출력하지 않음
- **완료조건**: 정상 `.env`로 시작 성공, 키 하나 삭제 시 정확히 그 키 이름을 지목하는 에러로 실패.
- **관련 스펙**: 03번 §3.1(Loader.load_env_secrets), 07번 §7.3
- **작업 트리 매핑**: 5.3

### FD-1.2 Risk Policy 로딩

- **목적**: `risk_policy.yaml`(07번 §7.2)을 검증된 Pydantic 객체로 로드 — 이후 모든 Risk 관련 판단(FD-8.3 포함)이 이 단일 객체를 참조한다.
- **트리거**: 시스템 시작 시, Secrets 로딩(FD-1.1) 직후.
- **입력**: `config/risk_policy.yaml` 경로
- **처리 단계**:
  1. YAML 파싱
  2. Pydantic `RiskPolicy` 모델로 검증(8개 지표 + circuit_breaker + watchdog + data_distrust 섹션 전부 필수)
  3. 검증 통과 시 전역 접근 가능한 싱글턴으로 보관(구현 방식은 착수 시 확정 — 의존성 주입 vs 모듈 전역 변수)
- **출력**: `RiskPolicy` 객체
- **예외 상황**: 파일 없음/필드 누락/타입 불일치 → Fatal, **정확한 필드 경로**(예: `watchdog.loss_threshold_pct`)를 에러 메시지에 포함 — 어디가 잘못됐는지 추측하게 만들지 않는다.
- **완료조건**: 07번 §7.2 예시 파일 그대로 로드 성공, 필드 하나를 의도적으로 삭제한 파일로는 정확히 그 필드를 지목하는 에러 확인.
- **관련 스펙**: 03번 §3.1(Loader.load_config), 07번 §7.2
- **작업 트리 매핑**: 5.1, 7.3

### FD-1.3 로거 초기화

- **목적**: 07번 §7.1 `LogEntry` 형식의 구조화 로거를 시스템 전체에서 쓸 수 있도록 초기화한다.
- **트리거**: 시스템 시작 시 **가장 먼저** — FD-1.1/1.2의 실패 로그조차 이 로거가 있어야 남길 수 있으므로 순서상 최우선.
- **입력**: 로그 레벨(env var, Draft 기본값 INFO)
- **처리 단계**: JSON Lines 포맷터 구성 → stdout 핸들러 연결 → correlation_id 컨텍스트 변수 초기화
- **출력**: 전역 logger
- **예외 상황**: 로거 자체 초기화 실패는 시스템이 완전히 눈먼 상태가 되므로, 실패 시 최소 `stderr` 직접 출력으로 폴백(이중 안전장치, 이것만은 예외적으로 로거에 의존하지 않는다).
- **완료조건**: DEBUG~CRITICAL 5개 레벨 모두 유효한 JSON 라인으로 출력, 서로 다른 요청의 `correlation_id`가 섞이지 않음(비동기 컨텍스트 격리 확인).
- **관련 스펙**: 07번 §7.1
- **작업 트리 매핑**: 7.1

## FD-4 주문 처리 (전송 계층)

> 이 대분류 전체의 전제: **판단(주문을 낼지 말지, 얼마나)은 FD-8(FROZEN)의 책임이다. FD-4는 "이미 승인된 주문을 어떻게 안전하게 전송·추적하는가"만 다룬다.** 8.2-A Master Authority 원칙의 실무적 경계선이 정확히 여기다.

### FD-4.1 주문 파라미터 검증

- **목적**: Order 객체가 거래소에 전송 가능한 형식적 요건을 충족하는지 확인(Risk 통과 여부와 무관 — 그건 FD-8.3의 책임).
- **트리거**: FD-8.4가 FD-4.2를 호출하기 직전 항상 선행.
- **입력**: `Order` 객체
- **처리 단계**: `Validator.validate_order_params()`(03번 §3.3) 호출 — tick_size 배수 확인, 수량>0, `LIMIT`인데 `price=None`이면 거부.
- **출력**: `ValidationResult`(예외를 던지지 않고 `is_valid`+`errors`로 반환 — 호출부가 판단)
- **예외 상황**: 이 함수 자체는 예외를 던지지 않는다 — "검증 실패"는 정상적인 반환값이지 예외 상황이 아니다.
- **완료조건**: 08번 §8.2 단위테스트 케이스(tick_size 위반, 수량 0 이하, LIMIT+price=None) 전부 통과.
- **관련 스펙**: 03번 §3.3, 01번 §1.4
- **작업 트리 매핑**: 5.7

### FD-4.2 주문 전송

> 이 기능은 처리 단계가 복잡해 4개 하위 리프로 세분화한다(세분화 예시 — 나머지 FD도 실제 구현 중 이 정도 복잡도가 드러나면 동일하게 쪼갠다).

#### FD-4.2-a 멱등성 사전 확인

- **목적**: 동일 `client_order_id`로 이미 전송된 주문이 있는지 확인 — 재시도로 인한 중복 주문 방지.
- **처리**: `orders` 테이블에서 `client_order_id` 조회. 이미 존재하면 그 행을 그대로 반환(재전송 아님, 기존 상태 재확인으로 전환).
- **완료조건**: 동일 `client_order_id`로 2번 호출 시 실제 거래소 호출은 1번만 발생.

#### FD-4.2-b 거래소 전송

- **목적**: 실제 `ExchangeAdapter.place_order()` 호출.
- **처리**: 호출 → `exchange_order_id` 수신 → `Order.status = SUBMITTED`.
- **예외 상황**: 거래소 거부(REJECTED 응답) → 예외 아님, 정상 흐름으로 `status=REJECTED` 처리. 네트워크 오류 → `RetryableExchangeError`, **재시도 전 반드시 FD-4.2-a를 다시 거쳐** 실제 전송 여부부터 재확인(무작정 재전송 금지).

#### FD-4.2-c DB 영속화

- **목적**: 05번 §5.6 원칙("DB가 항상 진실의 원천") 실행 — 이벤트 발행보다 먼저 커밋.
- **처리**: `orders` 테이블에 INSERT/UPDATE.

#### FD-4.2-d 이벤트 발행

- **처리**: `event_bus.publish("order.status.changed", order)`(FD-6.1 재사용).
- **완료조건**(FD-4.2 전체): Bitget Demo 실제 주문 1건 왕복 성공, 동일 `client_order_id` 재전송 시 중복 주문 미생성 확인.
- **관련 스펙**: 02번, 04번, 05번
- **작업 트리 매핑**: 6.7

### FD-4.3 주문 취소

- **목적**: 미체결 주문 취소.
- **입력**: `order_id`
- **처리**: `cancel_order()` → DB `status=CANCELLED` → 이벤트 발행.
- **예외 상황**: 이미 체결된 주문의 취소 시도 → 거래소가 거부 → 이를 오류로 취급하지 않고 FD-3.4(상태 재조회)로 전환.
- **완료조건**: 미체결 주문 취소 성공, 체결완료 주문 취소 시도 시 적절히 상태 재조회로 전환되는지 확인.
- **작업 트리 매핑**: 6.7

### FD-4.4 주문 정정

- **목적**: 지정가 주문의 가격/수량 변경(시장가는 정정 불가).
- **처리**: `modify_order()`.
- **예외 상황**: 시장가 주문 정정 시도 → FD-4.1 단계에서 사전 차단(거래소까지 안 감).
- **완료조건**: 지정가 정정 성공, 시장가 정정 시도 시 거래소 호출 없이 즉시 거부 확인.
- **작업 트리 매핑**: 6.7

### FD-4.5 UNKNOWN 상태 재조회

- **목적**: 8.3 원칙 — UNKNOWN을 실패로 단정하지 않는다.
- **트리거**: 주문 상태가 UNKNOWN으로 관측될 때마다(응답 타임아웃, 파싱 실패 등).
- **처리**: FD-3.4를 최대 3회, 2초 간격으로 재호출 → 최종 상태 확정 시 DB 갱신+이벤트 발행 → 3회 후에도 UNKNOWN → **CRITICAL 로그**(자동 해소 포기, Human 개입 신호).
- **완료조건**: 강제 UNKNOWN 시뮬레이션 시 정확히 3회 재조회 후 상태 확정 또는 CRITICAL 로그 발생 확인.
- **관련 스펙**: 04번 `idx_orders_unknown` 인덱스 활용
- **작업 트리 매핑**: 6.7

## FD-5 종목 스캐닝

### FD-5.1 스캔 조건 정의

- **목적**: `ScanCriteria` 객체로 필터 기준(거래량·변동성 등)을 정의.
- **처리**: Pydantic 검증만(로직 없음) — 음수 값 등 형식 오류만 걸러낸다.
- **완료조건**: 잘못된 값(음수 거래량 등) 입력 시 `ValidationError`.
- **작업 트리 매핑**: 5.9(일부)

### FD-5.2 스캔 실행

- **목적**: 조건에 맞는 심볼 목록 반환.
- **트리거**: 주기적(Draft: 5분 간격) 또는 수동 호출.
- **입력**: `ScanCriteria`
- **처리 단계**:
  1. 활성 거래소(Bitget)의 마켓 목록 조회
  2. 각 후보 심볼에 FD-2.1/FD-2.3으로 시세·거래량 확인
  3. 조건 필터링
  4. **06번 §6.2의 5개 심볼 화이트리스트와 교집합** — Phase 1은 전체 마켓이 아니라 이 5개로 강제 제한
- **출력**: `list[str]`

- **완료조건**: 06번 §6.2 5개 심볼 기준 스캔 결과가 화이트리스트를 벗어나지 않음, 강제 API 실패 시 Stale 결과 유지 확인.
- **작업 트리 매핑**: 5.9

- **목적**: 16.2 — DevEngine 작업 단위 인증을 실제로 발급·검증한다.

## FD-9 안전장치 계층 (SCAFFOLD — Zone 재분류)

> **재분류 근거**: 이전 버전에서 이 기능군을 FD-8과 함께 FROZEN으로 묶었으나, 이는 "매매 판단(사고 팔지 얼마나)"과 "위험 감시(지금 안전한지)"를 혼동한 것이다. 안전장치는 **매매 의사결정을 하지 않는다** — 시장/시스템 상태를 감시하고 필요시 정지·경보만 한다. 06번 §6.3 Definition of Done이 "Watchdog 시뮬레이터를 Phase 1에 실행"을 요구하는 것과도 이 재분류가 일치한다. 아래는 v3.1 정책문서(8.6-A~8.6-A-1-2, 8.6-B, 8.1-A, 8.4)의 실제 판단 로직을 함수 수준으로 구체화한 것이다 — 이제부터 "FROZEN이라 나중에"가 아니라 **지금 설계·구현 대상**이다.

### FD-9.1 Watchdog 손실·응답불능 감시

- **목적**: 계좌 손실률과 메인 프로세스 응답성을 독립적으로 상시 감시한다.
- **트리거**: 별도 프로세스(정책문서 8.6-A "메인과 완전 격리된 독립 헬스체크 프로세스")로 상시 루프, Draft 주기 5초.
- **입력**: `account_state`(FD-3.2/3.3로 조회), 메인 프로세스 heartbeat(별도 IPC/파일 타임스탬프)
- **처리 단계**:
  1. 계좌 손실률 계산: `(peak_equity - current_equity) / peak_equity`, 5분 롤링 윈도우(`risk_policy.yaml`의 `watchdog.window_min`)
  2. 메인 프로세스 마지막 heartbeat로부터 경과 시간 계산
  3. FD-3.5(헬스체크)로 **거래소 API 자체의 독립 응답성**도 함께 확인 — Reconciliation(FD-9.6)에만 의존하지 않는다(정책문서 8.6-A-1-2 원칙)
- **출력**: `WatchdogSnapshot { loss_pct, unresponsive_sec, exchange_healthy: bool }`
- **완료조건**: 강제로 메인 프로세스를 정지시켰을 때 Watchdog(별도 프로세스이므로 계속 동작)이 `unresponsive_sec` 증가를 정확히 관측.
- **관련 스펙**: 정책문서 8.6-A
- **작업 트리 매핑**: 신규 리프 "9.1 Watchdog 프로세스 골격" 필요(§하단 갱신)

### FD-9.2 Watchdog 정지/청산 판정

- **목적**: FD-9.1의 관측치를 바탕으로 정지(Halt)만 할지 강제청산까지 할지 판정한다(정책문서 8.6-A-1, 3차 레드팀 반영 — 안전장치의 강제청산 자체가 시장충격을 만들 수 있다는 발견).
- **입력**: `WatchdogSnapshot`, `risk_policy.yaml`의 `watchdog` 섹션(loss_threshold_pct=7.0, unresponsive_sec=30)
- **처리 단계(의사코드)**:
  ```
  if snapshot.unresponsive_sec >= 30 and snapshot.loss_pct < 7.0:
      → HALT만 (신규주문 중단, 기존 포지션 유지)
  elif snapshot.loss_pct >= 7.0:
      # 5차 레드팀 반영 — Griefing 방어: 시장 전체와 상관성 확인(FD-2.6 결과 참조)
      if FD-2.6 결과가 "시장 전체 급변과 상관됨":
          → 청산 진행, 8.3-A Smart Order Routing(TWAP) 우선 적용
      else:  # 고립된 손실 = 조작 의심
          → 신규진입만 즉시 HALT, 기존 포지션 청산은 추가 확인(짧은 지연) 후 결정
  else:
      → 정상
  ```
- **출력**: `WatchdogDecision { action: HALT | LIQUIDATE | NORMAL, reason: str }` → `audit_log`(FD-7.2) 즉시 기록
- **완료조건**: 8.6-A-1-1 시뮬레이터(FD-9.7 예정)로 과거 Flash Crash 데이터 재생 시 FP<1%/FN=0% 측정.
- **관련 스펙**: 정책문서 8.6-A-1, 5차 레드팀(17.8)
- **작업 트리 매핑**: 신규 리프 "9.2 Watchdog 판정 로직"

### FD-9.3 Split-Brain 실패도메인 진단

- **목적**: State DB 연결 단절과 메인 프로세스 장애를 구분한다(정책문서 8.6-A-1-2, 8차 레드팀 발견 — 인프라 레벨 최초 결함).
- **처리 단계(의사코드)**:
  ```
  exchange_ok = FD-3.5()  # 거래소 API 직접 헬스체크, DB와 무관
  main_process_ok = heartbeat 확인
  db_ok = DB 연결 확인

  if exchange_ok and main_process_ok and not db_ok:
      → "State DB 단독 장애" 진단 — 강제청산 대상에서 제외, 신규주문만 보류
      → 거래소 API 응답을 잠정 진실 소스로 취급
  elif not exchange_ok or not main_process_ok:
      → FD-9.2 기존 판정 그대로 적용
  ```
  히스테리시스(9차 레드팀 반영): 장애판정 진입은 3초 연속 확인, 정상복귀 판정은 10초 연속 확인(비대칭) — 정확한 수치는 외부 비공개(정책문서 8.6-A-2 원칙과 동일하게 예측가능성 제거).
- **완료조건**: DB만 강제로 차단했을 때 강제청산이 발동하지 않고 신규주문만 보류되는지 확인.
- **관련 스펙**: 정책문서 8.6-A-1-2
- **작업 트리 매핑**: 신규 리프 "9.3 Split-Brain 진단기"

### FD-9.4 Circuit Breaker 4단계 상태전이

- **목적**: API 오류율·데이터 지연·주문거부율 등을 근거로 정상→경고→거래제한→거래중지→긴급정지 단계를 관리한다.
- **입력**: API 오류율, 데이터 지연(초), 주문거부율, Daily Loss(FD-8.3 결과 참조 가능하나 이 계층 자체는 매매판단 안 함)
- **처리**: `risk_policy.yaml`의 `circuit_breaker` 섹션 임계치(07번 §7.2)를 그대로 사용한 단순 상태기계 — 각 단계 진입조건 충족 시 상향, 조건 미충족이 일정시간 지속 시에만 하향(임의 즉시 하향 금지 — 진동 방지).
- **출력**: `CircuitBreakerLevel` 변경 시 `circuit_breaker.level_changed` 이벤트 발행(FD-6.1)
- **완료조건**: 각 단계 임계치를 인위적으로 넘겼을 때 정확한 단계로 전이, 짧은 순간적 회복으로는 하향하지 않음을 확인.
- **관련 스펙**: 정책문서 8.6, 8.6-B
- **작업 트리 매핑**: 신규 리프 "9.4 Circuit Breaker 상태기계"

### FD-9.5 Data Distrust Mode 판정

- **목적**: FD-2.6에서 이미 다룬 히스테리시스 로직을 시스템 상태로 승격 — 6차 레드팀이 지적한 다중 오라클 동시 스푸핑 방어(쿼럼)까지 포함해 완성한다.
- **처리**: FD-2.6(2소스 비교) → 6차 레드팀 반영 확장 — **Reference 소스 최소 2개 이상(총 3소스 쿼럼), 중앙값 비교** + 피드 비교와 무관한 통계적 타당성 검사(실현변동성 대비 표준편차 5배 초과 여부)를 병행, 둘 다 "이상없음"이어야 정상 유지.
- **완료조건**: 3소스 중 1개만 왜곡됐을 때(중앙값은 정상 유지) 오탐 없이 정상 판정, 2개 이상 동시 왜곡 시 Distrust 진입 확인.
- **관련 스펙**: 정책문서 8.1-A
- **작업 트리 매핑**: 5.11(기존 리프 확장 — 단일 소스 비교에서 쿼럼으로)

### FD-9.6 Reconciliation 불일치 에스컬레이션

- **목적**: 내부 상태와 거래소 실제 상태의 불일치를 감시하고 반복 시 단계적으로 대응을 격상한다.
- **처리(의사코드)**:
  ```
  1회 불일치 → 자동 Recovery(재조회), 신규주문 일시보류
  동일자산 1시간 내 3회 이상 → Circuit Breaker '거래제한' 단계로 자동 승격
  24시간 내 5회 이상 또는 단일 불일치가 포지션의 10% 초과 → 신규주문 전면중지 + RCA 강제
  ```
- **완료조건**: `reconciliation_events` 테이블(04번)에 인위적 불일치를 반복 삽입했을 때 정확한 임계치에서 단계 격상 확인.
- **관련 스펙**: 정책문서 8.4
- **작업 트리 매핑**: 신규 리프 "9.6 Reconciliation 에스컬레이션 로직" (3.8 테이블 이후)

## FD-10 인간 승인 흐름 (SCAFFOLD — 상호작용 패턴)

> Phase 1에는 실거래 자금 규모가 작아 Critical Risk 승인이 자주 발생하지 않을 수 있지만, **패턴 자체는 지금 구현해야** 나중에 FROZEN Zone이 열렸을 때 바로 연동된다. 20.1-B에서 발견된 "승인권자 2인 미해결" 문제와 직접 연결된다 — 이 기능들은 실제 승인권자가 2인 확정되기 전까지는 완전한 End-to-End 테스트가 불가능하다는 것을 완료조건에 명시한다.

### FD-10.1 Critical Risk 승인 요청 생성

- **처리**: 요청 생성 시 60초 타이머 시작(버튼 비활성화), 서로 다른 인증계정의 순차 서명 요구.
- **완료조건**: 승인권자 2인 확정 전까지는 **Mock 승인자 2개 계정으로만** 테스트(실제 운영 배포는 불가 — 20.1-B 참조).
- **관련 스펙**: 정책문서 4.9-A
- **작업 트리 매핑**: 신규 리프 "10.1 승인 요청 워크플로"

### FD-10.2 SURGE 모드 판정 및 배치승인

- **처리**: 10분 내 요청 5배 급증 시 SURGE 진입 → Trigger Provenance 필드로 요청 근원 확인 → **Kernel이 8.1-A/8.6 실제 상태와 대조해 독립 재검증**(Agent 자기주장 불신 원칙, 7차 레드팀) → 검증된 단일 이벤트 파생 요청군만 배치승인, 나머지는 개별 SURGE 절차.
- **완료조건**: 가짜 Provenance 태그(시스템 상태상 근거 없음) 주입 시 배치승인 거부하고 최하위 신뢰로 분류되는지 확인.
- **관련 스펙**: 정책문서 4.9-A, 6·7차 레드팀
- **작업 트리 매핑**: 신규 리프 "10.2 SURGE 판정기"

### FD-10.3 비상 출금 패닉 프롬프트

- **처리**: 심각 신호(카운터파티 리스크) 감지 시 사전 등록된 화이트리스트 목적지만으로 프롬프트 생성, 최소 2개 독립 소스 corroboration 확인 후에만 신속경로 활성화.
- **완료조건**: 목적지 화이트리스트 외 주소로는 프롬프트 자체가 생성되지 않음을 확인(시스템 레벨 제약 — Agent 권한 밖).
- **관련 스펙**: 정책문서 7.10-A
- **작업 트리 매핑**: 신규 리프 "10.3 패닉 프롬프트 생성기"

## 10번 문서(작업 트리) 갱신 필요 항목 — 이번 라운드에서 새로 발견된 누락

이번에 FD-1·4·5·7·8을 채우며 10번 작업 트리에 없던 리프 3개를 추가로 발견했다:

- **7.4 audit_log 기록 유틸** (FD-7.2) — 지금까지 `audit_log` 테이블(3.10)만 있었지, 이를 실제로 기록하는 공통 유틸 함수가 작업 트리에 없었다.
- **6.12 Capability Token 발급기** (FD-7.3) — `capability_tokens` 테이블(3.3)만 있었지 발급·검증·무효화 로직이 트리에 없었다.
- **5.11 데이터 신뢰도 검증기** (FD-2.6) — 직전 라운드에서 이미 발견.

세 항목 모두 **"테이블/인터페이스는 정의했지만 그걸 실제로 조작하는 로직이 작업 트리에서 빠져있었다"**는 동일 패턴이다.

## FD-9/FD-10 신설로 인한 Zone 재분류 및 작업 트리 대규모 추가

**Zone 재분류**: Watchdog·Circuit Breaker·Data Distrust·Reconciliation 에스컬레이션·Human Approval 흐름을 FROZEN에서 **SCAFFOLD로 재분류**한다 — 이들은 "매매 판단"이 아니라 "위험 감시·상호작용 워크플로"이며, 06번 §6.3 Definition of Done이 이미 Watchdog 시뮬레이터를 Phase 1 요건으로 요구하고 있어 이 재분류가 기존 스콥과도 일치한다.

이로 인해 10번 작업 트리에 새 대분류 "9. 안전장치 계층"과 "10. 인간 승인 흐름"을 신설해야 한다:

```
├── 9. 안전장치 계층 (신설, FD-9 기반)
│   ├── 9.1 Watchdog 프로세스 골격 (별도 프로세스, 메인과 IPC로만 통신)
│   ├── 9.2 Watchdog 판정 로직 (정지/청산 분기, Griefing 방어)
│   ├── 9.3 Split-Brain 진단기 (히스테리시스 포함)
│   ├── 9.4 Circuit Breaker 상태기계
│   ├── 9.5 Data Distrust 쿼럼 확장 (5.11을 3소스로 확장)
│   ├── 9.6 Reconciliation 에스컬레이션 로직
│   ├── 9.7 Watchdog 오탐 검증 시뮬레이터 (8.6-A-1-1, 06번 DoD 필수항목)
│   └── 9.8 통합 테스트 — Flash Crash 데이터 재생
│
└── 10. 인간 승인 흐름 (신설, FD-10 기반)
    ├── 10.1 승인 요청 워크플로 (60초 대기, 이중서명)
    ├── 10.2 SURGE 판정기 (Trigger Provenance 독립검증)
    ├── 10.3 패닉 프롬프트 생성기 (화이트리스트 제약)
    └── 10.4 통합 테스트 — Mock 승인자 2계정
```

**중요한 선행조건**: 9번·10번 착수 전 `risk_policy.yaml`(07번 §7.2)에 이미 존재하는 `watchdog`/`circuit_breaker`/`data_distrust` 섹션을 그대로 사용 가능 — 새 설정 파일 구조는 필요 없다. 다만 **10번(인간 승인 흐름)은 실제 운영 배포 시 20.1-B의 승인권자 2인 확정이 전제조건**이라는 것을 다시 한번 명시한다 — 코드는 지금 짤 수 있지만, 실제 자금이 걸린 테스트는 그 전까지 Mock으로만 가능하다.
