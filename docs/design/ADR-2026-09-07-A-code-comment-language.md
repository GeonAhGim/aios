# ADR-2026-09-07-A: 코드 주석은 영문, 문서는 한글 — 그리고 소급 변환은 하지 않는다

## Status
Accepted (2026-09-07, Chief Architect). 사용자 지적: "한글로 코딩하면 문제가 많다. 문서 외에는 주석도 영문이 좋겠다."

## Context
동의한다. 다만 이건 취향 문제가 아니라 **실측된 비용**이다. 2026-09-06 하루에 두 번 값을 치렀다.

1. **`ruff`가 한글을 표시폭 2로 센다.** 80자로 읽히는 줄이 E501(100자)에 걸린다.
   `check_audit_regressions.py` 한 파일에서 이 이유로 6건이 터져 CI가 적색이 됐다.
2. **cp949 콘솔에서 한글 `print()`가 `UnicodeEncodeError`를 던진다.**
   자기 재시작 경로(`selfreload.py`)와 감사 검사기가 각각 이걸로 죽었다.
   재시작 경로가 로그 출력 때문에 죽는 것은 특히 나쁘다 — 복구 장치가 복구를 못 한다.
3. 혼재된 스크립트는 식별자·산문에 대한 grep·정규식을 불안정하게 만든다.

식별자는 이미 전부 영문이다(`src` 916개 파일에서 한글 식별자 6건, 전부 오탐).
문제는 **주석·독스트링·오류 메시지**에 있다.

## Decision

### D1. 앞으로 쓰는 코드의 주석·독스트링은 영문
`src/` 아래 새 주석과 독스트링은 영문으로 쓴다. 도구가 읽는 텍스트이기 때문이다.

### D2. 한글이 남는 곳 — 사람이 읽는 텍스트
`docs/`·ADR·L4 명세·커밋 메시지·PM 지침·task note·사용자 화면 문자열은 한글을 유지한다.
도구가 폭이나 인코딩으로 해석하지 않고, 읽는 주체가 사람이다.
**제품 오류 메시지도 지금은 한글을 유지한다** — 그건 주석이 아니라 제품 텍스트이고 UX-1·UX-2의 i18n이 담당한다.

### D3. 기존 14,760줄은 소급 변환하지 않는다
`src/` 916개 파일 중 766개에 한글이 있고, 주석·독스트링 기준 13,466줄이다.
동시에 워커 8대가 커밋하는 상황에서 766개 파일을 건드리면 병합 충돌이 대량 발생하고 `git blame`이 무너진다.
기능 이득은 0이다. **ADR-2026-09-06-F가 세운 "이미 있는 것을 다시 쓰지 않는다" 원칙이 여기에도 적용된다.**
파일을 어차피 손댈 때 그 파일의 주석을 영문으로 바꾸는 방식으로 자연 감소시킨다.

### D4. 규칙이 아니라 래칫으로 강제한다
`scripts/check_code_language.py`가 주석·독스트링의 한글 줄 수를 세고
`code-language-baseline.txt`로 래칫한다. **늘면 CI 실패, 줄면 기준선 자동 갱신.**
일반 문자열 리터럴은 세지 않는다(제품 텍스트라 i18n 대상이다).

측정 방식은 `tokenize`의 COMMENT 토큰과 `ast`가 식별한 독스트링만 본다.
"한글이 있으면 무조건 실패"가 아니라 "증가가 불가능"이다 — 지침을 문장으로 적는 것보다 이쪽이 실제로 작동한다.

## Consequences
- 새 코드는 영문 주석으로 수렴하고, 기존 코드는 손대는 김에 줄어든다.
- ruff 폭 계산과 cp949 인코딩으로 CI가 깨지는 경로가 새 코드에서는 사라진다.
- 기준선 13,466에서 시작한다. 이 숫자가 프로젝트의 남은 부채를 정직하게 보여준다.

## Rejected
- **전면 소급 변환**: 766개 파일, 동시 커밋 8대, 병합 충돌과 blame 손실. 얻는 것은 일관성뿐이다.
- **한글 전면 금지(문서 포함)**: 사용자가 읽는 문서를 영문으로 바꾸면 검토 비용이 올라간다. 손해가 더 크다.
- **지침 문장으로만 관리**: 이 프로젝트에서 강제되지 않는 규칙은 지켜지지 않았다.
  `type: ignore`가 하루에 85 → 170 → 219로 늘어난 것이 증거다.
