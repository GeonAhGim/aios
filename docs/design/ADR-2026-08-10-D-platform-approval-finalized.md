# ADR-2026-08-10-D: 플랫폼 레벨 Critical Risk 승인 게이트 — 정식 확정

## Status
**Accepted (2026-08-14, 정식 확정)** — ADR-2026-08-10을 대체(Supersedes)한다.
ADR-2026-08-10은 "임시 운영 방식"으로 표시돼 있었고, Decision Step 2가
참조하는 "AIOS 내부 가이드라인"이 실제로 작성된 적이 없어 구조적으로
비어있는 스텝이었다. 이 ADR은 그 가이드라인 자체를 포함해 정식으로
확정한다.

## Context

ADR-2026-08-10이 확정한 3단계 절차:
1. 사용자(프로젝트 소유자) 1인의 명시적 결정
2. AIOS 내부 가이드라인 대조 — **이 시점까지 미작성**
3. 부합하지 않거나 불확실하면 경고 + 사전동의

이 ADR은 4가지 공백을 메운다:
- ① 플랫폼 레벨 승인 가이드라인(Step 2 실체화)
- ② 승인 대상 결정유형의 구체적 목록
- ③ 60초 강제대기 하한의 플랫폼 레벨 적용 여부
- ④ 주기적 재검토 주기

## Decision

### ① 플랫폼 레벨 승인 가이드라인 (Step 2 실체화)

**전제**: 이 가이드라인은 19장(법적 방어선 체크리스트)이 요구하는 정식
법률자문(18.3)의 대체물이 아니다 — 법률자문 완료 전까지 쓰는 **임시
체크리스트**이며, 18.3 완료 시 정식 가이드라인으로 교체한다(그때까지
이 문서 자체가 유효기간부 Draft).

플랫폼 레벨 결정을 내리기 전, 다음 5개 질문에 **전부 "예"**가 아니면
Step 3(경고+사전동의)로 넘어간다:

1. 이 결정이 사용자 자금의 커스터디(직접 보관·이체)를 새로 발생시키지
   않는가? — 정책문서 7.3 "Trading Permission ≠ Withdrawal Permission"
   원칙 위반 여부 확인.
2. 이 결정이 8.2-A Master Authority(결정론적 Risk의 LLM 상위 무효화권)
   또는 8.6-B Kill Switch 우선순위(Watchdog>Human>Circuit Breaker>Debate)
   를 약화시키지 않는가?
3. 이 결정이 9.9(자기검증 금지) 원칙 — 동일 주체가 자신이 만든 것을
   스스로 검증·승인하는 구조 — 를 새로 만들지 않는가?
4. 이 결정이 FROZEN Zone(`.aios-zone` 매니페스트 기준)의 실제 판단 로직을
   15.6-D 종료조건 충족 전에 개방하지 않는가?
5. 이 결정을 되돌릴 수 있는가(reversible)? — 되돌릴 수 없는 결정
   (예: 데이터 영구 삭제, 외부 계약 체결)일수록 Step 3 경고 임계값을
   낮춰 적용한다.

### ② 승인 대상 결정유형 목록 (구체화)

정책문서 4.9 원문의 "시스템 전체 Kill Switch, DevEngine 거버넌스, 16.6
메타통제면 관련 결정"을 실제 시스템의 이벤트/액션에 매핑한다:

| 결정 유형 | 실제 트리거 | 이 세션에서 만든 근거 |
|---|---|---|
| 시스템 전역 Circuit Breaker 재가동 | `system_safety_state.circuit_breaker_level`이 halted/emergency에서 정상으로 전환 | FD-9.4b, 04번 v1.5 |
| `.aios-zone` FROZEN 경로 재분류 | FROZEN→SCAFFOLD 전환(15.6-D 종료조건 충족 판정) | 10번 v1.6 §1.4 |
| Capability Token 발급기 자체 변경 | 16.2 발급 로직 수정(발급 대상 확대 등) | 정책문서 16.2 |
| CODEOWNERS 변경 | FROZEN 경로의 소유자 재지정 | 10번 v1.6 §1.4 |
| DevEngine 의존성 Allowlist 확장 | 16.5 신규 패키지 승인 | 정책문서 16.5 |
| 비상출금 화이트리스트 강제 무효화 | FD-11.5로 등록된 항목을 플랫폼이 직접 삭제(사용자 요청 없이) | FD-11.5, 04번 |
| 공유접점문서 §2 동결 계약 변경 | AIOSTask/FSMStrategyConfig/Order State Machine/Exchange Adapter 시그니처 수정 | 공유접점문서 §4 |

이 표에 없는 새로운 유형의 결정이 발생하면, ①의 5개 질문으로 우선
판단하고 사후에 이 표에 추가한다(표 자체가 계속 성장하는 living
document — 매 분기 재검토 시 이 표도 함께 갱신, ④ 참조).

### ③ 60초 강제대기 하한 — 플랫폼 레벨에도 적용, 단 더 엄격하게

**적용한다.** 사용자 레벨(FD-11.3 `mandatory_wait_seconds`, 하한 60초)과
동일한 원칙이되, 플랫폼 레벨은 파급 범위가 전체 사용자이므로 **하한을
180초로 상향**한다 — 이미 FD-9.2/FD-10.1이 "저유동성 시간대 강화(180초)"
개념을 쓰고 있어 그 값을 재사용, 플랫폼 레벨 결정은 항상 이 "강화된"
대기시간을 기본값으로 삼는다는 뜻이다. 1인 체제에서는 이 대기시간이
"숙고 시간"으로 기능한다(진짜 2인 승인의 대체물은 아니지만, 즉흥적
결정을 막는 최소한의 장치).

### ④ 주기적 재검토 주기

**분기별(3개월)**. 20.1-B B그룹이 이미 "인력·조직 격차는 분기별
재점검"이라는 전례를 세워뒀으므로 동일 주기로 통일한다. 재검토 항목:

- 실제 승인권자 2인이 확보됐는가(확보 시 이 ADR 전체가 자동 폐기되고
  정책문서 4.9 원문 — 서로 다른 인간 2인 서명 — 으로 복귀)
- ②의 결정유형 목록에 빠진 유형이 그동안 발생했는가
- ①의 5개 질문 중 실제로 "아니오"가 나온 사례가 있었는가(있었다면
  Step 3 경고+동의 절차가 실제로 작동했는지 audit_log로 확인)

## Rejected Alternatives
- **가이드라인을 19장 법률검토 완료까지 무기한 미룬다**: SCAFFOLD Zone
  진행 자체가 막혀 비현실적 — 기각(ADR-2026-08-10과 동일 논리 재확인).
- **60초 하한을 플랫폼 레벨에 적용하지 않는다**(플랫폼 레벨은 어차피
  1인 결정이니 대기시간이 무의미하다는 논리): 대기시간의 실질 기능은
  "즉흥적 결정 방지"이지 "2인 확인"이 아니므로, 1인 체제일수록 오히려
  더 필요하다고 판단 — 기각.
- **재검토 주기를 월별로 단축**: 1인 체제 사용자에게 과도한 관리 부담,
  분기별로도 충분히 조기 발견 가능(17.9-A 과잉설계 방지 원칙) — 기각.

## Impact
- ADR-2026-08-10은 이 ADR로 **Superseded** — Status를 "Superseded by
  ADR-2026-08-10-D"로 갱신 필요.
- 공유접점문서 §0/§4에 이 ADR 참조 추가 필요(패치 별도 제공).
- 정책문서(v3.4) 4.9 근처에 이 ADR의 존재를 각주로 남기는 것을 권장
  (직접 본문 수정은 하지 않음 — ADR 자체가 살아있는 참조 문서 역할).
- FD-9.4b(재가동승인)의 "Draft로는 플랫폼 레벨 취급"이라는 표현을
  이제 "확정: 플랫폼 레벨, 180초 하한, ①의 5개 질문 적용"으로 격상
  가능(기능설계문서 후속 반영 대상).
