## §9.2 아직 해소하지 않고 "알고 있는 채로 남겨두는" 것

- **CI 파이프라인 실제 YAML**: 08번 §8.7은 개요만 있다. 실제 GitHub Actions 문법은 Repo 생성 시점에 작성 — 지금 작성해봐야 Repo 구조 확정 전이라 추측성이 크다.
- **로그 수집기 선택(Datadog/Loki 등)**: 의도적으로 미확정 — 07번 §7.1에 명시한 대로 과잉설계 방지.
- **다중 프로세스/분산 처리**: 05번에서 Phase 1 스콥 밖으로 의도적 배제. Phase 4+ 재검토 대상.

이 3가지는 "빠뜨린 것"이 아니라 "지금 결정하면 오히려 손해인 것"으로 분류한다 — 정책문서 17.9-A 원칙과 동일한 논리.

## §9.3 FD-11~21(멀티테넌시·마켓플레이스·프론트엔드) 레드팀 공백 (v1.1 병합 —
"0번부터 재검토" 라운드에서 발견: patch-09-redteam-fd11-21-gap.md로만 존재하고
본문 미반영이었던 것 완결)

> 이 문서(09번)는 제목 그대로 "00~08 기술 스펙 대상"으로 스콥이 명시돼 있고,
> 이후 v3.1/v3.2에서 신설된 FD-11~21(13번 멀티테넌시, 14번 마켓플레이스 상세,
> 16번 백엔드 시그니처, 17번 프론트엔드)은 이 문서의 정식 레드팀 라운드를
> 거친 적이 없다.

- 실질적으로는 2026-08-10 세션의 "재점검 라운드"(기능설계문서 v1.1~v1.17
  개정이력 전체)가 이 역할을 사후적으로 상당 부분 수행했다 — 20개 이상의
  실질적 결함(엔드포인트 불일치, 타입 미정의, 페이지네이션/Idempotency
  누락, 06번 자기모순, 문서 전체 번호체계 충돌, MFA 강제화 누락, Circuit
  Breaker 자동재가동 위반 등)을 발견·수정했다.
- 다만 이는 §9.1처럼 **사전에 계획된 체계적 레드팀**이 아니라 사용자 요청에
  따른 **사후 다각도 스캔**이었다는 차이가 있다 — §9.1 방식(각 모듈을
  의도적으로 공격 관점에서 검토)을 FD-11~21에도 정식으로 적용하는 라운드는
  아직 수행되지 않았다.
- **권장**: Repository 착수 전, §9.1과 동일한 형식(표: 항목/문제/반영위치)으로
  "FD-11~21 레드팀 재검토"를 별도 라운드로 신설해 이번 세션 발견사항을
  체계적으로 재정리하는 것을 SCAFFOLD 착수 전 마지막 문서화 작업으로
  제안한다.
