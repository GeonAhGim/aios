# ADR-2026-09-06-B: T1을 넘어서는 목표 아키텍처 — 초도 완성도를 위한 공격적 결정

## Status
Accepted (2026-09-06, Chief Architect). 사용자 지시: "최대한 리팩터링을 줄여야 하니 초도에 완성도 높게 구축한다.
모든 전권을 줄 테니 T1을 넘어서는 성과까지 가자. 사람 결정이 필요한 부분도 정말 중요한 게 아니면 공격적으로 결정해 진행하라."

## Context
- 지금까지의 명세(L4 9종)는 T3 → T2 경로를 덮는다. T1(Aladdin·Charles River·Bloomberg AIM/EMSX·FlexTrade)이 추가로 요구하는 것은
  **컴플라이언스 권위, 다법인·다펀드 회계(IBOR/ABOR), 주문 라우팅·집행 알고리즘·거래비용분석, 규제 보고, 운영 연속성**이다.
- 이 중 다수는 "기능"이 아니라 **키 구조**다. `fund_id`·양시간축(bitemporal)·이벤트 소싱을 나중에 넣으면 주문·포지션·원장 전 테이블과
  모든 조회 경로를 다시 만들어야 한다. 사용자의 "리팩터링 최소화" 요구는 곧 **이 축들을 지금 결정하라**는 뜻이다.
- 반대로 FIX 회선·규제 보고 제출·HA 클러스터 운영은 나중에 얹어도 구조가 흔들리지 않는다. 포트만 지금 뚫는다.

## Decision — 지금 계약에 박는 것(구조 축)

### D1. 엔티티 계층을 4단으로 고정한다 (모든 금전·주문·포지션 테이블에 지금 반영)
`tenant → legal_entity(법인) → fund(펀드/전략계좌) → portfolio(계좌) → sub_account(배분 단위)`
- 주문·체결·포지션·원장 분개·리스크 한도·성과는 전부 `fund_id`와 `portfolio_id`를 **필수 컬럼**으로 갖는다(단일 사용자는 자동 생성된
  기본 법인·펀드·포트폴리오 1개를 쓰므로 UX는 그대로).
- **블록 주문 → 배분(allocation)**: 하나의 주문이 여러 sub_account로 평균단가 배분될 수 있어야 한다. `order.allocation_policy`와
  `allocations` 테이블을 처음부터 둔다(단일 계좌면 1:1 배분).
- 근거: 이 3개 키를 나중에 추가하는 것은 데이터 마이그레이션이 아니라 재구축이다.

### D2. 상태는 양시간축(bitemporal)으로 저장한다
- 포지션·원장·참조데이터·리스크 결정은 `valid_time`(사실이 성립한 시각)과 `transaction_time`(시스템이 안 시각)을 함께 갖는다.
  정정은 UPDATE가 아니라 새 행(append-only, 기존 WORM 규칙과 동일).
- 효과: "그때 우리가 알던 장부"(ABOR)와 "지금 아는 진실"(IBOR 정정 반영)을 같은 테이블에서 재구성한다. T1 회계의 기본기이고,
  백테스트·감사·분쟁 대응이 전부 여기에 의존한다. ADR-2026-09-06-A의 `known_at`은 이 규칙의 리서치 데이터판이다.

### D3. 쓰기 경로는 이벤트 소싱 + 재현 가능한 투영으로 정형화한다
- 모든 상태 전이는 `(stream_id, seq)` 단조 증가 이벤트로 append되고, 현재 상태 테이블은 **재구축 가능한 투영**이다.
  기존 `order_events`·감사 해시체인·원장 분개가 이미 그 형태이므로 새로 만드는 것이 아니라 **규칙으로 승격**한다.
- **결정론적 전체 재현**: 임의 날짜의 이벤트 스트림을 재생하면 그날의 투영이 바이트 단위로 동일해야 한다(CI 야간 검증).
  이것이 T1을 **넘어서는** 지점이다 — 기관 시스템도 전체 재현은 못 한다.

### D4. 컴플라이언스를 리스크와 **분리된 두 번째 권위**로 세운다
- 리스크 엔진(손실·VaR·한도)과 별개로, **규정·위임장(mandate)·금지종목·시장질서** 판정을 하는 Compliance Authority를 둔다.
  주문 경로는 `Risk ∧ Compliance` 둘 다 ALLOW여야 통과한다(어느 하나라도 DENY면 거부, fail-closed).
- 사전(pre-trade)·사후(post-trade) 양쪽에서 돌고, 규칙은 코드가 아니라 **버전이 찍힌 규칙 번들**(승인된 사람만 활성화)로 관리한다.
- 근거: T1 제품의 핵심 차별점이 컴플라이언스이고, 이 훅을 주문 경로에 나중에 끼우는 것은 실행 코어 재작업이다.

### D5. 집행 계층(EMS)을 포트로 지금 분리한다
- `Router`(벤처 선택)·`ExecutionAlgo`(TWAP/VWAP/POV/IS)·`TCA`(거래비용분석) 3개 포트를 지금 정의하고, MVP-1에는
  단순 구현(단일 벤처 라우팅 + TWAP + 기본 TCA)만 넣는다. FIX 4.4/5.0 회선은 포트 뒤 어댑터로 남긴다.
- 부모-자식 주문(parent/child) 모델을 주문 계약에 지금 넣는다 — 알고리즘 주문은 자식 주문을 낳으므로 나중에 넣으면 OMS 재작업.

### D6. 운영 연속성 목표를 지금 못박고 코드를 그에 맞춘다 (레지스터 A-01 해소)
- **RPO=0 / RTO≤5분**(금전·주문 계열). Postgres 동기 복제(streaming replication, `synchronous_commit=remote_apply`) +
  자동 페일오버(Patroni류)를 목표 배포로 확정한다. MVP-1에서는 **클러스터 운영이 아니라 코드의 HA 적합성**을 강제한다:
  긴 트랜잭션 금지, 모든 쓰기 멱등·재시도 가능, 다중 호스트 접속 문자열, 페일오버 중 리스 만료 처리(EO 리스와 일관).
- 백업: PITR(연속 아카이빙) + 일 1회 복구 리허설 스크립트. 재현(D3)이 있으므로 최악의 경우 이벤트 재생으로 복구한다.

### D7. 키·시크릿·데이터 주권
- 시크릿은 KeyRing(PLT-31/33) 유지하되 **KMS/HSM 어댑터 포트**를 지금 둔다(클라우드 이전 시 코드 변경 0).
- 테넌트별 데이터 리전 태그를 스키마에 지금 넣는다(국내 금융 규제상 국내 보관 요구가 나올 수 있음).

## Decision — 지금은 포트만, 구현은 뒤로
- FIX 회선, 규제 보고 제출(MiFID II RTS 27/28·국내 보고), GIPS 준거 성과 보고, 다중 커스터디언 대사, HA 클러스터 실배포,
  SOC2 통제 매핑 문서화. 전부 포트·계약만 MVP-1, 어댑터·운영은 MVP-2.

## Decision — 명시적으로 하지 않는 것
- **초저지연 경쟁 포기**: Python/asyncio로 마이크로초 EMS를 겨루지 않는다. AIOS의 우위는 통제·재현·분석·AI이지 지연이 아니다.
  지연 요구가 실제로 생기면 집행 핫패스만 별도 프로세스로 분리한다(포트가 이미 있으므로 국소 교체).
- 자체 청산·수탁 기능, 자체 시장조성.

## Consequences
- 새 명세 3종: `L4_compliance_and_regulatory_v1.0.md`(CM-1~20), `L4_ems_routing_algos_and_tca_v1.0.md`(EM-1~18),
  `L4_ibor_fund_accounting_and_resilience_v1.0.md`(FA-1~24). 합계 약 62 리프.
- **MVP-1 편입 기준**: 구조 축(D1·D2·D3·D4 훅·D5 포트·D6 코드 적합성·D7 포트)은 MVP-1. 깊이(FIX·규제 제출·HA 실배포·TCA 고급)는 MVP-2.
  MVP-1 리프 총계는 약 208 → 약 314(ADR-A/B 확장 포함).
- **기존 완료 리프에 대한 소급 작업**이 생긴다: 주문·포지션·원장 테이블에 `fund_id`/`portfolio_id`/양시간축 컬럼 추가 마이그레이션과
  기존 유스케이스 시그니처 확장. 지금 하면 표 몇 개, 3개월 뒤면 제품 정지 후 재구축이다 — 그래서 지금 한다(FA-1~6이 이 소급 작업).
- 일정: 기존 추정(약 1일 + α)에 구조 축 소급·신규 리프가 더해져 **MVP-1 약 3~4일**로 재추정한다.

## Rejected
- 단일 계좌 전제 유지 후 나중에 다펀드 확장: 재구축 비용이 지금 비용의 10배 이상.
- 컴플라이언스를 리스크 엔진 안에 합치는 안: 권위가 섞이면 "왜 막혔는가"를 규제기관에 설명할 수 없고, 규칙 승인 주체가 다르다.
- 이벤트 소싱 전면 도입을 위한 기존 코드 재작성: 기존 이벤트·감사·분개 구조를 규칙으로 승격하는 방식이 같은 결과를 훨씬 싸게 낸다.

## 감사 정정 (2026-09-06, 코드 대조 후)
전면 재검토에서 이 ADR의 비용 모델이 세 군데 틀렸음이 확인됐다. 결정 자체는 유지하되 범위를 정정한다.

1. **D5(부모-자식 주문)는 이미 구현돼 있다.** `orders.parent_order_id`·`algo_run_id` 컬럼과 `oms/domain/algo_slicer.py`가 존재한다.
   EM-2/EM-3은 신설이 아니라 보강이며, 새 `parent_orders`/`child_orders` 테이블은 만들지 않는다. OMS `L4-25`는 EM으로 흡수해 폐기한다.
2. **D4(컴플라이언스)의 전제가 틀렸다.** "주문 경로에 훅을 나중에 끼우면 실행 코어 재작업"이라고 했으나, `foundation_gate.py`가 이미
   리스크와 mandate 정책을 함께 평가하고 `policy_decision`이 지문·만료를 갖춘 결정 레코드로 존재한다. 별도 Compliance 컨텍스트 신설은
   `foundation/mandates` 중복이므로 **mandates 확장 + `GateDecision.policy_decision_id` + `require_mandate=True`**로 바꾼다.
3. **D2(양시간축)의 범위가 과도했다.** WORM 트리거가 걸린 append-only 테이블은 물리적으로 UPDATE가 불가하므로 트랜잭션 시간축이 무의미하다.
   양시간축은 **투영 테이블**(`pos_snapshot`·`ledger_balance`·`positions`)에만 적용한다.
4. **ADR이 놓친 진짜 비용 세 가지를 선행 리프로 신설했다(FA-0a~0d).** (a) `tenant_id`가 `users`를 FK하는 19개 테이블 — 조직 테넌트가
   생기면 전부 깨진다, (b) `portfolio_mandate UNIQUE(tenant_id)`가 테넌트당 포트폴리오 1개를 강제, (c) `ledger_account.account_code`
   문자열 문법과 `pos_snapshot.position_key`에 계층이 이미 인코딩돼 있어 컬럼 추가만으로는 두 진실이 공존한다. **이 넷을 먼저 하지 않고
   `fund_id`만 추가하면 ADR이 피하려던 재구축 비용을 그대로 치른다.**
5. **D3의 실제 공백은 도메인 테이블이 아니라 이벤트 버스다.** `order_events`·`pos_journal`·`ledger_journal_entry`는 이미 해시체인
   append-only이고 `pos_snapshot`·`ledger_balance`는 이미 재구축 가능한 투영이다. `src/core/event_bus/`가 아무것도 영속화하지 않는 것이 공백이다.
