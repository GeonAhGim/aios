## §14.1 가격정책 (Pricing Models)

### 14.1.1 Phase 1 지원 모델 — 고정가 일회성 구매만

전략 하나를 정액에 사서 무기한(또는 판매자가 명시한 기간) 사용하는 단순 모델만 지원한다.

```python
# src/data/models/marketplace.py (13번 §13.5 strategy_listings 확장)
class PricingModel(str, Enum):
    FIXED_ONE_TIME = "FIXED_ONE_TIME"  # Phase 1 유일 지원 모델
    # SUBSCRIPTION, REVENUE_SHARE 는 아래 14.1.2 참조 — 의도적 미지원
```

- `strategy_listings.price`는 이 고정가를 의미한다(13번 §13.5에 이미 존재하는 필드, 재정의 없음).
- 가격 통화: `Money`(11번 §11.1) 타입 적용 — 원화(KRW) 기준으로 통일한다(크립토 전략이든 KIS 전략이든 마켓플레이스 거래 자체는 단일 통화로 단순화, 크립토 자산 자체의 손익과는 무관).

### 14.1.2 명시적 제외 — 구독형, 수익공유형

| 모델 | 제외 이유 |
|---|---|
| 구독형(Subscription) | 반복 결제 인프라(정기 청구·해지·환불 주기 관리)가 필요하며, 사용자 10인 규모에서 이 복잡도는 과잉설계(17.9-A 원칙). Phase 2 이후 실사용 데이터로 수요 확인 후 재검토 |
| 수익공유형(Revenue Share)·성과보수(Performance Fee) | **위 선행 제약 재확인** — 타인 자금 운용 성과에 연동한 대가 수취는 자본시장법 투자일임업 인가 문제와 직결된다. 마켓플레이스가 "전략 코드 판매"가 아니라 "운용 성과 배분"으로 해석될 여지를 원천 차단하기 위해 Phase 1~MVP 전체에서 이 모델 자체를 제공하지 않는다 |

### 14.1.3 가격 변경 정책

- 판매자는 리스팅 가격을 언제든 변경할 수 있다(Draft). 단 **이미 구매한 사용자에게는 소급 적용되지 않는다** — `strategy_purchases.price_paid`는 구매 시점 가격을 불변 기록한다(8.10 감사 원칙과 동일하게, 거래 시점 사실은 이후 변경으로 덮어쓰지 않는다).
- 가격을 0으로 설정(무료 배포)하는 것은 허용한다 — 초기 마켓플레이스 활성화를 위해 판매자가 선택 가능.

### 14.1.4 결제 처리 — Phase 1은 수동 정산

13번 §13.8에서 이미 "결제 시스템(PG 연동)은 스콥 밖 — 실제 사업자 등록·정산 방식 확정 후"로 보류했다. 이를 실제 흐름으로 구체화하면:

- `POST /marketplace/listings/{id}/purchase`(15번 §15.5) 호출 시 `strategy_purchases` 행이 생성되고 전략 실행 권한이 즉시 부여되지만, **실제 대금 이동은 플랫폼 자동화 대상이 아니다** — 사용자 10인 이내 규모를 전제로, 플랫폼 운영자가 수동 확인(계좌이체 등 Off-platform)한 뒤 구매를 확정 처리하는 흐름을 Draft로 둔다.
- 이는 임시방편이 아니라 **의도적 설계**다 — 소액·소수 거래에 자동 PG를 붙이는 것은 정산수수료·환불처리 인프라 대비 실익이 낮고, 실제 결제대행 계약(전자금융업 등록 여부 포함)은 19장 법률검토 완료 후 진행하는 것이 안전하다.
- 따라서 `POST /marketplace/listings/{id}/purchase`의 실제 상태 흐름은 `PENDING_PAYMENT`(요청 접수) → 운영자 수동 확인 → `CONFIRMED`(실행 권한 부여) 2단계로 세분화한다 — 13번 §13.5 스키마에 `payment_status` 컬럼 추가 필요(Draft, 착수 시 반영).

## §14.2 평판·리뷰 시스템 — 소규모 사용자 그룹 특화 설계

### 14.2.1 문제 인식

일반적인 5점 척도 리뷰 시스템은 사용자 10인 규모에서 심각하게 왜곡된다 — 리뷰 1개가 전체 평균의 10%를 좌우하고, 서로 아는 사용자 2명이 품앗이 리뷰를 남기면 사실상 조작된다. v3.2에서 이미 이 문제의식으로 "MVP 수동검증 브릿지"를 도입했는데, 리뷰 시스템에도 동일한 논리를 적용한다.

### 14.2.2 신뢰 신호 우선순위 (별점 평균을 주 신호로 쓰지 않는다)

1. **검증 배지(1순위, 객관적·이진)** — FD-13.2(9.5-A MVP 수동검증 브릿지)를 통과했는지 여부만 표시(`인증됨` / 미표시). 별점이 아니라 통과/미통과 이진 신호.
2. **실측 성과 지표(2순위, 객관적·수치)** — 검증 과정에서 확보된 3개월 Paper Trading 실측치(승률, MDD, 샤프비율 등)를 **가공 없이 그대로** 리스팅 페이지에 노출한다. 주관적 평가가 아니라 검증담당자가 확인한 원본 수치.
3. **사용자 리뷰(3순위, 보조적·조건부 집계)** — 아래 14.2.3 참조.

### 14.2.3 리뷰 작성·집계 규칙

```python
class Review(BaseModel):
    listing_id: int
    reviewer_user_id: UUID  # buyer_user_id와 대조 검증 — 구매 이력 없으면 작성 불가
    rating: int  # 1~5
    comment: Optional[str]
    created_at: datetime
```

- **작성 자격**: `strategy_purchases`에 해당 리스팅에 대한 구매 이력이 있는 사용자만(자전거래 방지, FD-13.3과 동일 원칙 — 판매자 본인 계정으로 재구매해 리뷰 조작하는 것도 원천 차단됨).
- **집계 표시 기준**: 리뷰 수가 최소 임계치(Draft: 5건) 미만이면 평균 별점을 아예 계산·노출하지 않고 "리뷰 부족(N건)"으로만 표시한다 — 소수 리뷰로 왜곡된 평균이 신뢰 신호처럼 보이는 것을 방지.
- **개별 리뷰 원문(댓글)은 건수와 무관하게 항상 노출**한다 — 집계된 숫자만 조건부 숨김이며, 텍스트 리뷰 자체는 정보로서 가치가 있으므로 숨기지 않는다.
- **공모 리뷰 대응(Draft, 완전 차단은 어려움을 인정)**: 소수 사용자 그룹에서 "서로 사고 리뷰 남겨주기"를 완전히 막을 기술적 방법은 없다 — 대신 14.2.2에서 리뷰를 3순위 보조 신호로 격하시킨 설계 자체가 이 리스크의 실질적 완화책이다. 사용자 규모가 커지면(Draft: 100인 이상) 통계적 이상탐지(4.6-A Memory 형태기반 탐지와 유사한 원리 — 특정 사용자쌍 간 구매↔리뷰 패턴의 비정상적 상호성)를 재검토한다.

## §14.3 9.5-A Certified Badge 자동검증 전환 절차 상세

v3.2에 "리스팅 20건 초과 또는 Phase 4 착수 시 자동화 전환"이라는 트리거 조건만 있었다. 실제 전환 절차를 확정한다.

### 14.3.1 전환 트리거

`status='LISTED'`로 전환된 누적 리스팅 건수가 20건을 초과하거나, Phase 4(AIOS Kernel — Black/Killer Team 실제 구현)가 착수되는 시점 중 **먼저 도래하는 쪽**을 트리거로 삼는다.

### 14.3.2 전환 절차 (5단계)

1. **트리거 감지** — 리스팅 카운터를 상시 모니터링(신규 리프, 작업트리 반영 필요), 임계치 도달 시 플랫폼 운영자에게 알림.
2. **소급 감사(Retroactive Audit)** — 기존 수동검증(FD-13.2) 통과 건 중 표본(Draft: 5건)을 재검토해, 여러 검증담당자가 있었다면 기준이 일관되게 적용됐는지 확인. 불일치 발견 시 전환을 보류하고 기준부터 재정비한다.
3. **병행 가동(교차검증 기간)** — Black/Killer Team 자동화 파이프라인을 실제 가동하되, 즉시 전면 전환하지 않는다. 이후 신규 리스팅 N건(Draft: 10건 또는 1개월 중 먼저 도래)은 **수동검증과 자동검증을 모두 수행**하고 결과를 대조한다.
4. **일치율 확인** — 교차검증 기간의 수동·자동 판정 일치율이 임계치(Draft: 95% 이상) 이상이어야 전환을 확정한다. 이는 8.6-A-1-1(Watchdog 시뮬레이터) "구축과 검증통과는 별개"라는 원칙을 자동검증 파이프라인에도 동일하게 적용한 것이다.
5. **확정 전환** — 이후 신규 리스팅은 자동검증을 기본 경로로 하되, 자동검증이 낮은 신뢰도로 판정한 건(Draft: 명확한 승인/거부가 아닌 애매한 경계)만 검증담당자에게 에스컬레이션한다 — 완전 무인화가 아니라 "쉬운 건은 자동, 애매한 건은 사람"으로 재배치.

### 14.3.3 전환 실패 시

일치율 기준 미달 시 자동화 파이프라인을 재조정하고 교차검증 기간을 연장한다(Draft: 최대 2회 연장, 이후에도 미달 시 자동화 설계 자체를 재검토하는 것으로 승격 — ADR 기록 대상).

## §14.4 리스팅 노출·검색·정렬 로직

### 14.4.1 노출 제어

`status='LISTED'`인 리스팅만 일반 사용자에게 공개 노출된다. `DRAFT`/`PENDING_VERIFICATION`/`DELISTED`는 판매자 본인에게만 보인다(FD-13.1/13.2와 연동).

### 14.4.2 검색·필터

```python
class ListingSearchCriteria(BaseModel):
    asset_class: Optional[str] = None  # "crypto" | "kr_equity"
    exchange: Optional[str] = None
    min_backtest_months: Optional[int] = None
    max_price: Optional[Decimal] = None
```

### 14.4.3 정렬 기본값 — 최신순이 아니라 검증통과일 순

기본 정렬을 리스팅 생성일이 아니라 **검증 통과일(FD-13.2 완료 시각)** 역순으로 한다 — 생성일 기준으로 하면 판매자가 리스팅을 반복 재등록해 상단 노출을 조작할 여지가 있으나, 검증통과일은 검증담당자를 거쳐야만 갱신되므로 조작이 어렵다.

- 2차 정렬 기준(동점 시, Draft): 실측 성과지표(14.2.2 ②) 중 샤프비율 내림차순 — 별점이 아닌 객관적 수치를 랭킹에 사용한다는 원칙의 재확인.

## §14.5 분쟁 처리 (Dispute Resolution)

### 14.5.1 시나리오

구매자가 "리스팅에 표시된 성과와 실제 사용 결과가 크게 다르다"고 이의를 제기하는 경우.

### 14.5.2 Phase 1 처리 절차 (수동, 자동화 없음)

1. 구매자가 플랫폼 운영자에게 분쟁 티켓 접수(Draft: 간단한 문의 폼, 별도 정교한 티켓팅 시스템은 과잉설계).
2. 플랫폼 운영자가 FD-13.2에서 기록된 **검증 당시 체크리스트와 실측 데이터**를 근거자료로 조회 — 판매자가 리스팅 시점에 실제로 자격을 갖췄었는지 확인(사후 조작이 아니라 8.10 감사로그로 시점이 고정되어 있으므로 신뢰 가능한 근거).
3. 검증 당시 데이터에 문제가 없었다면(전략이 정당했으나 이후 시장 상황 변화로 성과가 달랐을 뿐이라면) 분쟁은 "정상 리스크 실현"으로 종결 — 마켓플레이스가 미래 성과를 보장하지 않는다는 원칙(정책문서 10.3-B 면책조항과 연동)을 근거로 안내.
4. 검증 당시 데이터 자체에 문제(오버피팅 은폐 등)가 발견되면 판매자 리스팅을 즉시 `DELISTED` 처리하고, 14.1.4의 수동 정산 원칙에 따라 개별 환불을 운영자가 중재.

### 14.5.3 반복 위반 판매자 대응

동일 판매자에 대해 분쟁이 반복(Draft: 2회 이상) 발생하면, 플랫폼 운영자(15번 §15.6 RBAC) 권한으로 해당 판매자의 신규 리스팅 권한을 정지한다 — `users.status`가 아니라 판매자 자격만 별도로 제한하는 플래그가 필요(Draft, 04번/13번 스키마에 `seller_suspended` 컬럼 추가 검토).

## §14.6 자체 재검토 — 이번 신설로 인한 리스크 (4.10 원칙 즉시 적용)

- **리스크 1**: 검증담당자 복수 운영 시 기준 비일관성 — 14.3.2 ②(소급 감사)가 이를 상시 방어책으로 흡수.
- **리스크 2**: 수동 결제(14.1.4)로 인한 정산 지연·분실 가능성 — 소규모 사용자 수(10인 이내)에서는 감내 가능한 리스크로 판단, `payment_status` 필드로 최소한의 추적성은 확보.
- **리스크 3**: 공모 리뷰(14.2.3) — 완전 차단 기술이 없음을 명시적으로 인정하고, 리뷰를 3순위 보조 신호로 격하하는 구조적 완화책만 적용. 100인 이상 규모에서 재검토 예정.
- **리스크 4(신규 발견)**: 정렬 기준을 "검증통과일"로 고정하면, 먼저 검증받은 오래된 전략이 계속 상단을 유지해 신규 우수 전략의 노출 기회가 구조적으로 낮아질 수 있다 — Phase 1(10인 이내)은 리스팅 총량 자체가 적어 문제되지 않으나, 리스팅 20건(14.3.1 자동전환 트리거와 동일 시점) 초과 시 정렬 로직 자체도 함께 재검토 대상으로 지정한다.
