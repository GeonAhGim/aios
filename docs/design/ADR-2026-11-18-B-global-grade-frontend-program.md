# ADR-2026-11-18-B: 글로벌 규모 프런트엔드 프로그램 (명세 우선 · 실스택 계약 · 미규정 액션 인입)

## Status
Accepted (2026-11-18, 사용자 전권 위임 — "글로벌 시장에 부끄럽지 않은 AIOS", CTO 결정·집행).

## Context

2026-11-18 UAT(체험 스택)를 처음 실제로 켜자, 화면 자체가 아니라 **정의되지 않은 구간**에서 결함이 연달아 나왔다.

| 구분 | 실측 결함 | 왜 mock e2e가 못 잡았나 |
|---|---|---|
| 오류 전달 | 도메인 오류 응답에 CORS 헤더 없음 -> 화면은 모든 오류를 "Failed to fetch"로 봄 | mock은 헤더·미들웨어 순서를 모른다 |
| 계약 불일치 | 프런트 ULID `X-Request-Id`를 서버가 UUID로만 파싱 -> 오류 응답 500, 로그인 불가 | 양쪽이 각자 자기 가정으로 통과 |
| 안전장치 | main이 하트비트를 안 써 워치독이 전역 킬스위치 발동(운영에도 잠재) | 화면 밖의 결함 |
| 흐름 | 첫 로그인이 MFA 설정으로 유도 — 사용자는 인증 앱이 필요함을 사전에 모름 | 여정 문서에 사용자 준비물 정의 없음 |
| 환경 차 | 테스트 픽스처가 Windows에서만 통과, 로컬/Actions 게이트 판정 불일치 | 단일 환경 검증 |

현황: 프런트 아키텍처 문서(`17_frontend_architecture.md` v1.7)는 15개 화면 기준이고, 실제 구현은 페이지 63개다. 화면별 기능 정의(상태·오류·권한·전이)와 화면을 가로지르는 규칙이 없어 워커가 화면마다 각자 해석한다. 검증은 mock 위주라 서버와 맞물리는 지점은 "써 보는 순간" 드러난다. 글로벌 규모(다국가·다통화·다규제·24시간 실시간 데이터·금전 행위)의 제품에서는 이 구조가 한계다.

## Decision

### D1. 원칙 6개 (모든 프런트 작업의 판단 기준)

1. **명세 우선(Spec-first)**: 화면·횡단 규칙이 문서로 정의된 뒤 구현한다. 리프는 해당 명세의 절을 참조해야 한다.
2. **계약 우선(Contract-first)**: 프런트·서버의 접점(오류 봉투, 요청 ID, 인증·MFA, 실시간 스트림)은 한 곳에 정의하고 **실제 스택**으로 검증한다. mock은 단위 격리용이지 계약 증거가 아니다.
3. **실패는 보이게(Fail-visible)**: 사용자는 오류의 원인 범주(내 입력 / 권한 / 서버 / 네트워크 / 점검)와 다음 행동을 항상 본다. 침묵·무한 로딩·오해를 부르는 성공 표시 금지. 금전 관련 불확실 상태는 "완료"로 보이지 않는다(fail-closed).
4. **글로벌 기본값(Global-by-default)**: 다국어, 시간대·거래소 시간, 통화·숫자 형식, 접근성, 지역별 고지가 나중에 덧붙이는 기능이 아니라 기본 구조다.
5. **측정 가능(Measure everything)**: 품질 목표는 숫자로 정하고 CI·RUM으로 측정한다(D5).
6. **사용자 기준(Persona-first)**: 모든 화면과 흐름은 "누가, 무엇을 이루려고" 쓰는지로 정의한다. 단위는 기능 목록이나 내부 모듈이 아니라 **페르소나와 그 여정**이다. 페르소나는 개인 트레이더·전략 생산자·판매자·구독자·자산운용사·증권사·기관·운영자·마스터·외부 플러그인 제공자·감사자(P1~P11, `docs/frontend/PERSONAS_AND_JOURNEYS.md`)이고, 신규 화면·여정 명세는 주 페르소나를 반드시 명시한다.

### D2. MVP-1 종결과의 관계 (섞지 않는다)

- **MVP-1 종결 게이트(ADR-2026-11-18-A의 T·U)는 그대로** 간다. 이 프로그램이 종결 조건을 늘리지 않는다.
- Phase 0(지금~종결)은 **문서 작성만** 한다: 횡단 규칙집 + J1~J3 화면 명세. 코드 변경 리프는 만들지 않는다(안정화 지표 보호, ADR-2026-09-26-C).
- 단, UAT 실스택 e2e가 찾아낸 **앱 결함의 수정**은 종결 경로에 포함한다(사용자 서명 관문 U의 전제).
- 화면 63개 전체 명세·디자인시스템·i18n·성능 예산 구현은 Phase 1(종결 뒤, MVP-2 UI 단계)이다.

### D3. 산출물 체계 (FE-1 ~ FE-9) — 위치 `docs/frontend/`

| ID | 산출물 | 내용 |
|---|---|---|
| FE-1 | 화면 기능 명세 | `SCREEN_SPEC_TEMPLATE.md` 형식. 목적·페르소나·데이터 출처·**상태 매트릭스**(로딩/빈/오류/권한없음/낡은 데이터/부분 실패)·행동·전이·오류 표시·텔레메트리·접근성·성능 예산·수용 기준. 구현 대비 갭 표 포함 |
| FE-2 | 횡단 규칙집 | `XCUT_RULES.md`. 오류 분류·표시, 세션·MFA·재인증, 요청 ID/trace, 로딩·재시도·오프라인, 데이터 신선도 표시, 금전 행위 확인 UX, 권한·위임, 알림 |

| FE-4 | i18n/l10n/지역 | 로케일(ko·en 1차, 확장 구조), 복수형, 숫자·통화·날짜, 시간대·거래소 세션, RTL 대비, 지역별 규제 고지 |

### D4. 미규정 액션 인입 절차 (Unspecified-Action Intake)

명세에 없는 동작이 발견되면(UAT, 사용자 보고, e2e, 로그):

1. `docs/frontend/UNSPECIFIED_ACTIONS.md`에 한 줄 기록(발견 경로·재현·증상).
2. 분류: **횡단 규칙**(XCUT) / **화면 명세**(FE-1) / **백엔드 계약** 중 하나로 귀속.
3. 해당 명세를 먼저 갱신하고, 그다음 구현 리프와 **실스택 테스트**를 만든다.
4. 같은 유형이 재발하지 않도록 사고사례집(`C:\AiWorkKnowledge\02_사고사례집`)에 원인 유형을 추가한다.

"고치고 끝"이 아니라 "규칙으로 승격하고 끝"이 완료 기준이다.

### D5. 정량 품질 목표 (Phase 1 종료 기준, 측정 도구는 FE-8)

| 축 | 목표 |
|---|---|
| 접근성 | 핵심 여정 전 화면 자동 검사 위반 0(axe 기준), 키보드만으로 J1~J3 완주 |
| 성능 | 핵심 화면 LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1(데스크톱 기준선), 초기 JS 번들 예산 초과 시 CI 적색 |
| 신뢰성 | 오류·예외 경로(401/403/409/423/429/5xx/네트워크 단절/세션 만료)를 실스택 e2e로 화면별 1건 이상 검증 |
| i18n | 사용자 가시 문자열 100% 키화(이미 게이트), ko·en 번역 누락 0, 숫자·통화·시간대 포맷은 단일 유틸 경유 |
| 계약 | 서버 오류 봉투·요청 ID·인증 흐름의 계약 테스트가 서버·클라이언트 양쪽 CI에서 동일 픽스처로 통과 |
| 관측 | 프런트 오류가 trace_id와 함께 수집되어 사용자 보고 하나로 서버 로그까지 추적 가능 |

### D6. 단계

- **Phase 0 (지금 ~ MVP-1 종결)**: FE-2 횡단 규칙집 초안, FE-1 J1~J3 화면 명세와 구현 갭 표, 미규정 액션 레지스트리 시작, UAT 실스택 e2e 확대(J1~J3), FE-9 설계 초안 확정(시그니처 장면 합의, 갭 조사).
- **Phase 1 (종결 직후, MVP-2 UI)**: FE-1 전체 63화면, FE-3~FE-8 구현, FE-9 패널·맥락 버스 기반과 시그니처 장면, 갭 표 기반 구현 리프(명세 참조 필수).
- **Phase 2 (글로벌 출시 준비)**: 다국어 확장, 지역 규제 고지, 성능·접근성 외부 감사, 부하·장애 훈련.

### D7. 거버넌스

- 화면·횡단 동작을 바꾸는 리프는 spec에 명세 절 링크를 포함한다(발행 게이트 확장은 Phase 1에서 기계화).
- 명세와 구현이 어긋나면 **명세가 기준**이다. 어긋남은 갭 표에 기록하고 리프로 해소한다.
- 명세 변경은 PR 경로(리뷰)를 거치고, 여정 단위 변경은 `UX_JOURNEYS.md`와 같이 갱신한다.

## Consequences

- 화면을 만드는 일이 "각자 해석"에서 "명세를 구현"으로 바뀐다. 워커 입력이 선명해져 로컬 워커 적합도도 오른다(화면 하나 = 명세 하나).
- 초기 비용: Phase 0 문서 작성(토큰), Phase 1의 63화면 명세. 대신 UAT에서 오늘처럼 뒤늦게 터지는 구간 결함이 명세 단계에서 걸러진다.
- 종결 일정은 늘리지 않는다(D2). 위험은 Phase 0 문서가 현실과 어긋나는 것 — 갭 표와 실스택 e2e로 양방향 검증한다.

## Non-goals

- 이 ADR은 백엔드 설계를 바꾸지 않는다(접점 계약만 다룬다). 모바일 앱(FD-21)은 Phase 1 이후 별도.
- MVP-1 종결 조건·일정을 변경하지 않는다.
