# ADR-2026-11-20-C: 인프라 자가개선 루프 — 운영 데이터로 비효율을 찾아 스스로 개선 (DevEngine 핵심 기능, 이식 자산)

## Status
Accepted (2026-11-20, 사용자 지시: "인프라 개선점이 발견되면 자동으로 개선하는 게 있었으면 좋겠다. 이게 자산이고 DevEngine의 핵심 기능일 것이다. 다른 프로젝트를 하게 되면 매우 중요한 부분"). 프로젝트 중립 설계는 지식 베이스 `C:\AiWorkKnowledge\18_인프라_자가개선_루프.md`가 원본이고, 이 ADR은 AIOS 적용 결정이다.

## Context

2026-11-19~20 하루 동안 CTO가 손으로 한 일은 "운영 데이터에서 비효율 발견 -> 원인 분류 -> 수정 -> 효과 측정"이었다. 결과: 머지 큐 병합 0건 배치 비율 13/33 -> 1~2, 큐 대기 38 -> 2, 8시간 병합 47건. 같은 일을 기계가 반복할 수 있다.

이미 있는 것: 세분화 자동 조치 프레임워크(`pm/remediation/`, shadow -> apply, 재발 시 자동 강등), `healthcheck` 소견, 안전 배포 게이트(`fleet_deploy.py`: 전체 pytest + 리플레이), 사전점검 그림자 장부와 자동 승격·강등, flake 등록부.
비어 있는 것: **탐지기**(병합 0건 배치 비율·무변경 비율·점유 시간을 기계가 찾지 못함), **개선 장부**(무엇을 왜 바꿨고 효과가 어땠는지의 구조화된 기록), **효과 측정 자동화**, **제안 생성**.

## Decision

### D1. 루프 7단계를 AIOS의 정식 운영 기능으로 둔다
관측 -> 탐지 -> 진단 -> 제안 -> 검증 -> 배포 -> 측정·학습. 단계 정의와 안전 원칙은 지식 베이스 18번을 따른다.

### D2. 안전 경계 (AIOS 고정값)
- **자동으로 바꿀 수 있음**: 발행 상한·알림 규칙·보류 조건 같은 설정 상수, 읽기 전용 분석 보고, 소견 생성.
- **사람(CTO) 승인 필요**: 엔진 코드(`pm/`), 게이트 단계 추가·승격, 큐·CI 동작 변경. `fleet_deploy.py`로만 반영, 로그의 성공 표시를 직접 확인한다.
- **금지**: 주문·자금·보안 통제(S-tier), 게이트·기준선 완화, 사용자 데이터. 기존 규칙("게이트 완화 금지")이 우선한다.
- 새 게이트·새 자동 조치는 항상 warn(shadow)으로 시작하고, 오탐 유형으로 막으면 자동 강등한다.

### D3. 개선 장부를 만든다
`pm/state/improvement_ledger.jsonl`(append-only). 항목: 문제, 증거(지표·창·참조), 진단(범주·확신도), 변경(종류·커밋·범위), 모드, 전후 지표, 판정(effective/neutral/regressed/unmeasured), 되돌림 방법. 장부가 다음 진단의 근거가 되며, 효과 없음·악화는 자동으로 되돌림 후보 소견을 올린다.
오늘(2026-11-19~20) 한 개선들을 소급 기록해 시드로 삼는다(전후 지표가 실측으로 남아 있는 것만).

### D4. 일일 효율 보고서(P1)
오늘 손으로 짠 분석(큐 수율, 병합 0건 배치 비율, 반려 사유, 무변경 비율, CI·큐 점유 시간 비율, 자동 복구 비율)을 읽기 전용 스크립트로 만들어 매일 기록한다. 임계를 넘으면 소견을 올리고 장부에 줄을 만든다. 코드 변경 없는 단계라 종결 지표에 영향이 없다.

### D5. DevEngine과의 관계
이 루프는 DevEngine의 핵심 기능이다. 개선 클래스는 DevEngine 플러그인 인터페이스(`PERSONAS_AND_JOURNEYS.md` §5, BYOAI D10의 사건 기록과 같은 인계 형식)로 표현해, 나중에 플러그인으로 붙은 DevEngine이 같은 입력으로 유지보수한다. 지금(플러그인 전)은 함대와 CTO가 같은 흐름을 수동·반자동으로 소비한다.

### D6. 이식
프로젝트 중립 코어(지표 스키마, 탐지 규칙 엔진, 개선 클래스 골격, 장부, 자동 강등)와 AIOS 어댑터(머지 큐 이력, CI 보고서, task 파일)를 분리해 설계한다. Day 1 시작은 지표 3개(처리량, 낭비율, 병목 점유)와 일일 보고서다. 이식 패키지(P5)는 새 프로젝트가 생길 때 지식 베이스 18번과 함께 제공한다.

## 단계
P1 장부 + 일일 효율 보고서 -> P2 탐지기 5종(큐 수율, 무변경 비율, CI 점유, 반복 실패, 반려 사유)과 소견 연결 -> P3 제안 생성(사람 승인) -> P4 DevEngine 통합 -> P5 이식 패키지.

## Consequences
- 비효율 발견이 사람의 우연한 분석에서 매일 기록되는 측정으로 바뀐다. 개선의 효과가 장부에 남아 누적 자산이 된다.
- 위험: 자동 개선이 지표를 악화시킬 수 있다 — 안전 원칙(shadow 먼저, 자동 강등, 변경 범위 제한, 측정 없이 완료 금지)과 "장치 자체도 감시 대상" 규칙으로 막는다. 탐지는 규칙·통계라 새로운 종류의 비효율은 사람이 한 번 발견해 규칙으로 만들어야 한다(장치는 발견을 반복 가능하게 한다).

## Rollback
개선 클래스는 개별로 끌 수 있고, 장부·보고서는 읽기 전용이라 제거해도 영향이 없다. 이 ADR을 Superseded로 두면 수동 분석 방식으로 돌아간다.
