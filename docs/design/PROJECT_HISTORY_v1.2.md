## 1. 프로젝트 개요

**미화프로젝트**는 AI 기반 투자 운영체제(AIOS)를 만드는 프로젝트다. 핵심 철학: "AI가 연구·전략생성·백테스트·검증·실행·모니터링·개선의 전 주기를 수행하되, 인간이 정책과 자본에 대한 최종 통제권을 가진다." **DevEngine**은 이 AIOS를 만드는 별도의 자율개발 도구다 — 두 프로젝트는 물리적으로 완전히 분리되어 있다(GitHub Repo부터 claude.ai 프로젝트까지).

**팀 구성**(2026-08 확인): Claude 계정 2개(AIOS 담당/DevEngine 담당으로 분리), Cursor AI 1개, Gemini 1개(레드팀 전용). 인간은 프로젝트 소유자 1인 — 이 사실이 여러 설계 결정(특히 Human Approval 이중승인 문제)에 직접 영향을 미쳤다(§6 참조).

## 2. 정책 문서의 진화 (v1.0 → v3.1)

### 2.1 초기 종합 단계 (v1.0~v1.4)
11개의 개별 원본 기획 문서를 하나로 종합하는 것에서 시작했다. v1.2에서 AIOSTask/FSMStrategyConfig의 JSON Schema가 확정되고 제품 인프라 뷰·DevEngine 연계 챕터가 신설됐다. v1.3에서 처음으로 "레드팀 관점 검토"라는 챕터(17장)가 생겼고, v1.4에서 이 프로젝트 전체를 관통하는 가장 중요한 단일 원칙이 확정됐다:

> **Master Authority 원칙(8.2-A)**: 결정론적 Risk 엔진이 LLM 판단보다 항상 상위에 있다. 실시간 주문 경로에는 LLM이 동기적으로 개입하지 않는다.

이 원칙은 이후 모든 레드팀 라운드에서 "이 공격이 실시간 거래를 막을 수 있는가"를 판단하는 기준선이 됐다.

### 2.2 DevEngine 병행 개발 모델 (v1.5)
"AIOS 설계 100% 완성 후 DevEngine 착수"라는 완전 순차 원칙을, 저장소를 FROZEN/SCAFFOLD/OPEN Zone으로 나누는 모델로 정교화했다. 이 Zone 시스템이 이후 모든 "무엇을 지금 만들어도 되는가" 판단의 기준이 됐다.

### 2.3 실증 조사 및 수치 확정 (v1.6~v1.7)
이 시점부터 "추상적 설계"에서 "검증 가능한 구체적 수치"로 전환됐다:
- Bitget은 공식 Demo Trading API 존재, Bithumb은 공식 Sandbox 부재를 **실제 웹 조사로 확인**(v1.0부터 공백이던 항목)
- Risk Engine 8개 지표(Daily Loss, MDD, 레버리지 등) Draft 수치 확정
- 거래소 카운터파티 리스크(운영파산/규제동결) 대응 원칙 신설

### 2.4 레드팀 경화 라운드 (v1.8~v2.8, 11차례)
이 프로젝트의 가장 특징적인 국면이다 — 매 라운드 외부 AI(주로 Gemini/ChatGPT)가 v(N) 문서를 공격하고, 발견된 항목을 v(N+1)에 반영하는 것을 11번 반복했다. 상세 요약은 §3.

### 2.5 DevEngine 아키텍처 불변성 (v2.7, 16장 신설)
외부 AI(Gemini·ChatGPT)가 제안한 "Step 0 7대 불변성(P0-1~P0-7)"을 비판적으로 검토·통합했다. 이때 우연히 비어있던 챕터 16번 결번(14→15→17)이 자연스럽게 해소됐다. 가장 중요한 채택: **메타 통제면 불변 원칙** — DevEngine이 자기 자신을 통제하는 보안 인프라(Policy/Audit/Kill Switch 등)에는 어떤 경우에도 쓰기 권한을 가질 수 없다는 원칙. 원안에 없던 보강 2가지를 추가했다: ①이 차단은 애플리케이션 로직이 아니라 IAM 권한의 물리적 부재로 구현해야 한다, ②Fail-Closed 원칙은 DevEngine에만 적용하고 AIOS 실시간 거래 경로에는 적용하지 않는다(비용구조가 다름).

### 2.6 실행 준비 전환 (v2.9~v3.1)
11차 레드팀이 "신규 발견 0건"이라는 첫 널 라운드(Null Round)를 기록한 직후, 설계 단계에서 실행 준비 단계로 공식 전환했다:
- 20.1-A Go/No-Go 체크리스트, 20.1-B 스켈레톤 착수 전 준비사항 신설
- **Kernel/Agent Layer를 Phase 2로 앞당기자는 제안을 반려**하고 기존 5단계 로드맵 재확정(§4.1)
- 실제 팀 구성 확인 → Human Approval 이중승인 문제가 추상적 우려에서 구체적 미해결 항목으로 전환(§6)
- **SK증권 → 한국투자증권(KIS)로 거래소 대상 교체**(§4.2) — 실제 API 조사 결과에 따른 결정
- Bithumb 보류(코드는 유지, 착수 대상에서만 제외)

## 4. 반려되거나 뒤집힌 결정들 (중요 — 재제안하지 말 것)

새 Agent가 같은 제안을 반복하지 않도록, **명시적으로 검토 후 거부된 것들**을 기록한다.

### 4.1 Kernel/Agent Layer를 Phase 2로 앞당기는 안 — 반려
외부 요약이 "Phase 2 = AIOS Kernel + Agent Layer"로 제안했으나, 기존 5단계 로드맵(Trading Core→Backtest→전략Lifecycle→Kernel→Marketplace)의 순서 원칙(6.5·12.3·17.9-A)에 따라 반려했다. **이유**: Kernel이 조율할 대상(전략·백테스트 결과)이 먼저 존재해야 조율 로직 자체를 검증할 수 있다. Day 1 구현 대상은 항상 "가장 단순한 것"이어야 한다는 원칙과도 충돌한다.

### 4.2 SK증권 — 실제 조사 후 교체
초기 계획은 "Bitget + SK증권"이었으나, 실제 웹 조사 결과 SK증권은 공식 개발자 API 포털이 확인되지 않았다(HTS "서버자동주문" 기능만 확인, 커뮤니티 자료도 없음). 국내 증권사 API 전수 비교 후 **한국투자증권(KIS)로 교체** — REST+WebSocket+OAuth2.0 공식 확인, Bitget과 대칭되는 구조(Demo/모의투자 등)라 기존 설계를 거의 그대로 재사용 가능.

### 4.3 SSL(System Stress Level) 통합 — 채택 보류, PROPOSED 상태 유지
10차 레드팀이 "패치 누적으로 인한 상태공간 폭발"을 지적했을 때, 히스테리시스·캐시TTL·SURGE 등을 하나의 중앙 신호(SSL)로 통합하는 설계를 제안했다. 그러나 **"검증 없이 새 메커니즘을 먼저 설계하지 말라"는 같은 라운드의 원칙과 충돌**한다는 걸 스스로 발견해, SSL은 확정 구현이 아니라 "상태 상호작용 테스트 매트릭스에서 실제 위험이 발견될 경우의 후보 설계"로 격하했다. 즉 **SSL은 아직 정식 채택된 아키텍처가 아니다** — 이 점을 후속 Agent가 오해하지 않아야 한다.

### 4.4 Fail-Closed 원칙의 전역 적용 — 명시적으로 범위 제한
16장에서 Fail-Closed(불확실하면 무조건 차단) 원칙을 DevEngine에 도입할 때, 이를 AIOS 실시간 거래 경로에도 그대로 적용하자는 암묵적 유혹이 있었으나 **명시적으로 거부**했다. 이유: AIOS 거래 경로에서 "불확실하니 무조건 차단"은 v2.5(17.12)에서 발견된 Approval Gridlock(진짜 위기에서 방어장치가 오히려 대응을 막는 역설)과 정확히 같은 실수를 반복하게 된다. DevEngine 개발행위(비용 낮음)와 AIOS 거래행위(비용 높음)는 다른 원칙을 따른다.

### 4.5 외부 메시지 브로커(Kafka/RabbitMQ) — 채택 안 함
개발명세서 05번에서 모듈 간 통신방식을 정할 때, 외부 브로커 대신 **In-process Async Event Bus**를 선택했다. 이유: Phase 1 스콥(심볼 5개, 거래소 1개)에서 외부 브로커는 과잉설계(17.9-A 원칙). 단, 인터페이스 뒤에 숨겨서 나중에 교체 가능하도록 설계했다 — "지금 안 쓴다"이지 "영원히 안 쓴다"가 아니다.

## 7. 작업 프로토콜 요약 (새 Agent가 지켜야 할 것)

1. **레드팀 검토는 1회성이 아니다**(17.4 원칙) — 새 챕터·기능 추가 시 "이것이 무엇을 무조건 믿고 있는가"를 항상 자문한다.
2. **FROZEN Zone은 15.6-D 종료조건 전까지 절대 건드리지 않는다** — 인간이 작성한 PR도 예외 없음.
3. **패치보다 통합을 우선한다**(10차 레드팀 이후 확정) — 새 메커니즘을 만들기 전에 기존 메커니즘으로 해결 가능한지 먼저 검토.
4. **모든 변경은 근거 문서를 인용한다** — "왜"가 없는 결정은 이 프로젝트에서 신뢰받지 못한다.
5. **AIOS-DevEngine 접점(공유접점문서 §2)을 변경할 때는 양쪽에 동시 반영** — 한쪽만 갱신된 상태가 가장 위험한 시나리오로 명시되어 있다.
6. **Draft라고 표시된 모든 수치는 실증 검증과 인간 승인 전까지 확정이 아니다.**

## 8. 용어 미니 글로서리

- **AIOS**: 이 프로젝트가 만드는 AI 투자 운영체제 본체.
- **DevEngine**: AIOS를 만드는 별도의 자율개발 도구. 별도 저장소.
- **FROZEN/SCAFFOLD/OPEN**: 저장소 Zone 분류. FROZEN=핵심 위험 로직(손대면 안 됨), SCAFFOLD=인터페이스(지금 가능), OPEN=문서/테스트 등.
- **Master Authority**: 결정론적 Risk가 LLM 위에 있다는 최상위 원칙.
- **SSL(System Stress Level)**: 아직 미채택 상태의 통합 안정성 신호 후보 설계.
- **널 라운드(Null Round)**: 레드팀 검토에서 신규 발견이 0건인 라운드(11차에서 최초 발생).
- **Capability Token**: DevEngine의 개별 작업 단위 인증 토큰(16.2).
