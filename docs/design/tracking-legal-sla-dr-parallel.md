# 병행 트랙 분리 — 법인·규제인가·SLA·DR은 MVP 코딩 게이트가 아니다

## 왜 이 문서가 필요한가

지금까지 만든 문서 세트 어디에도 "법인 형태·금융규제 인가 요건",
"정량적 SLA(지연시간·가용성)", "DR(재해복구) 전략"이 **MVP 코딩 착수를
막는 게이트인지 아닌지**를 명시적으로 선언한 곳이 없었다. 이 3가지는
설계 로직의 문제가 아니라 **외부 확정이 필요한 사업/조직 문제**이므로,
이 문서가 "이건 게이트가 아니다"를 명시하고 별도 트랙으로 분리한다.

## 1. 법인 형태·금융규제 인가 요건

**결론: MVP SCAFFOLD 코딩 착수를 막지 않는다.**

- 이미 정책문서 12.1(Phase 1→2 선결 게이트)이 "가시적 성과 = 19.1(규제
  카테고리 분류) 변호사 1차의견 수령"이라고 **Phase 1→Phase 2 전환**
  조건으로만 명시했지, **Phase 1 착수 자체**의 조건으로 삼은 적이 없다.
- 20.1-A(기술게이트)와 20.1-B(B그룹, 법률검토 포함)는 이미 "20.1-A는
  Phase1 완료조건, 20.1-B는 Phase1 코드작업과 **병행 트랙**"이라고
  명시적으로 분리돼 있다 — 이 문서는 그 원칙을 재확인·강화할 뿐 새로
  결정하는 것이 아니다.
- **실제 착수 가능 범위**: `src/api/routers/`, `src/services/`,
  `src/core/safety/` 등 SCAFFOLD Zone 전체는 법인·인가 여부와 무관하게
  지금 바로 코딩 가능하다. FROZEN Zone(`src/core/strategy|portfolio|
  risk|executor/`)만 15.6-D 종료조건(별도 기술 게이트, 법률 문제 아님)
  전까지 열리지 않는다 — 이것도 법률 문제가 아니라 안전 설계 문제다.
- **트래킹 방법**: PROJECT_HISTORY.md §6(현재 미해결 상태) 표에 이미
  "법률 자문 착수: 미착수 — KIS 실계좌 연동으로 자본시장법 관련성이
  실질적으로 상승, 12.1 게이트 우선순위 격상"으로 기록돼 있다. 이 문서는
  이 항목을 "병행 트랙"으로 재확인하고, Phase 2 전환 시점에 **반드시**
  재확인하도록 체크포인트만 명시한다.

## 2. 정량적 SLA (지연시간·가용성)

**결론: MVP SCAFFOLD 코딩 착수를 막지 않는다.**

- 15번 문서(API 스펙) §15.7이 이미 "정량적 NFR(TPS·동시접속자)는 사용자
  10인 규모에서 조기 확정이 오히려 과잉설계(정책문서 17.9-A 원칙),
  실사용 데이터 축적 후 Phase 2~3에서 재검토"라고 **의도적으로 미정**
  상태를 유지하기로 이미 결정했다 — 이 문서는 이 결정을 재확인한다.
- 유일하게 이미 확정된 정량 목표는 8.2-D(종단간 지연 정상단계 50ms
  이내/경고단계 200ms 이내)이며, 이건 SLA(외부 계약상 서비스 수준)가
  아니라 **내부 성능 벤치마크**(20.1-A A그룹, 기술게이트)로 이미 별도
  트랙에 있다 — 이것도 Phase 1 SCAFFOLD 코딩을 막지 않는다(측정 자체는
  완료조건, 통과는 FROZEN 착수 조건).
- **트래킹 방법**: Phase 2 진입 시점에 실사용 데이터(Phase 1 운영 로그)를
  근거로 정량적 SLA를 처음 확정한다 — 지금 임의로 숫자를 정하면 오히려
  근거 없는 목표가 되어 위험하다.

## 3. DR(재해복구) 전략

**결론: MVP SCAFFOLD 코딩 착수를 막지 않는다.**

- 정책문서 8.4-A(재해복구 우선순위표)가 이미 State DB·Audit Log의
  복구 우선순위(RPO 0, 실시간 복제)는 정의해뒀다 — 이건 **설계 원칙**
  으로 이미 확정돼 있고, 04번 DB스키마의 실제 백업 정책(pg_basebackup,
  WAL 아카이빙 등)만 미정이다.
- 11번 문서 §11.7(로컬 개발 환경)의 `docker-compose.dev.yml`은 로컬
  개발용이고, **프로덕션 DR 인프라(다중 리전, 자동 페일오버 등)는
  Phase 1 스콥에 원래부터 없다** — 06번 §6.4(명시적 제외)의 "다중
  프로세스/분산 처리" 항목과 동일한 이유(정책문서 5.4, 심볼 5개·거래소
  2개 규모에서는 불필요)로 자연스럽게 제외된다.
- **트래킹 방법**: 실제 사용자 자금이 걸리는 프로덕션 배포 직전(Phase 2
  진입과 대략 일치)에 최소 DR 정책(일 1회 백업, 복구 리허설 1회)을
  확정한다 — Phase 1 SCAFFOLD 단계는 로컬/Demo 환경이라 DR 자체가
  의미가 크지 않다.

## 4. 통합 트래킹 표 (PROJECT_HISTORY.md §6에 병합 권장)

| 항목 | Phase 1 코딩 착수 차단 여부 | 실제 확정 시점 | 근거 |
|---|---|---|---|
| 법인 형태·금융규제 인가 | **아니오** | Phase 1→2 전환 게이트(12.1) | 정책문서 12.1, 20.1-B |
| 정량적 SLA | **아니오** | Phase 2~3, 실사용 데이터 축적 후 | 15번 §15.7, 정책문서 17.9-A |
| DR 전략(프로덕션) | **아니오** | 실자금 프로덕션 배포 직전 | 정책문서 8.4-A, 06번 §6.4 |
| (대조군) FROZEN Zone 개방 | **예, 차단** | 15.6-D 종료조건 충족 시 | 정책문서 15.6-D |
| (대조군) 8.2-D 지연벤치마크 | **예, 차단**(FROZEN 진입만) | 20.1-A A그룹 통과 시 | 정책문서 8.2-D |

마지막 두 행("대조군")은 **실제로 Phase 1 코딩 자체를 막지는 않지만
FROZEN 진입은 막는** 항목들이다 — 이 문서가 다루는 3가지(법인/SLA/DR)와
혼동하지 않도록 나란히 표시했다. 법인·SLA·DR은 FROZEN 진입 여부와도
무관하게, 순수 병행 트랙이다.
